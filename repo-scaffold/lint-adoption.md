# Lint 接入作业规范([scaffolding.md](scaffolding.md) D 节的引用文档)

D 节决定「接不接、用哪个 linter」;本文规定接入怎么做:先坐实存量,再配规则集,再处置存量报错,最后接线并证明门禁能红。各步的判据与机制写在条文里;以 TS/JS + ESLint 为例写,其余技术栈照同一套判据换工具。

## 1. 动手前先试跑,拿到存量的真实形状

- **版本取最新,先查兼容约束**:装之前查 linter 与各插件当前最新版本的 peer 依赖与运行时版本要求,与项目的语言版本、CI 的运行时版本逐项对照;对不上的先定升级还是降级,不得装上再看报错。
- **先用候选配置对全仓试跑一次,输出机器可读格式落盘**,再按规则统计:报错数、涉及文件数、每条规则可自动修复的条数、解析失败数。**解析失败非零时不得往下走**——解析失败的文件一条规则都没被检查,而它在汇总里只是一行。
- 处置方案以这份统计为准,不以对代码的印象为准:「改掉」与「豁免」的取舍取决于存量的数量与所属规则,而这两样只有统计看得出。

## 2. 规则集(TS/JS + ESLint)

- **只用官方推荐集**:`@eslint/js` recommended + typescript-eslint `recommendedTypeChecked`(类型感知版,配 `projectService`)。不加自定义规则。选类型感知版的理由:漏 await 的 Promise、`any` 一路流下去这类值得 linter 拦的问题,没有类型信息看不见。
- **React 项目加 `eslint-plugin-react-hooks` 的 `recommended-latest`,只作用于前端代码目录**:hook 的调用顺序、effect 依赖、渲染期读 ref,类型检查一概看不见。
- **不属于任何 tsconfig 的纯 JS 文件**(构建脚本、`.mjs` / `.cjs`)用 `disableTypeChecked` 关掉类型感知规则——它们没有类型信息,强开只会得到解析失败。
- **仅当项目的 tsc 开了 `noUnusedParameters` 时**,给 `no-unused-vars` 配 `argsIgnorePattern: '^_'`,让两边对「有意未用的参数」采用同一约定;否则同一个参数会被一边放行、另一边报错。
- **lint 脚本必须带 `--max-warnings 0`**:不让运行失败的 warning 等于规则只开了个名;react-hooks 的 `exhaustive-deps` 在官方集里就是 warning。
- 检查范围:除原型/文档、第三方 vendored 代码与构建/测试产物外全部入查。
  - **被 git 忽略的目录必须同样排除在检查之外**:ESLint 不读 `.gitignore`,忽略列表漏掉的被忽略目录里只要有可 lint 文件就会被检查。干净检出(CI、新建的 worktree)里没有这些目录,门禁照绿;只有开发者的工作检出(带着本地产物与临时文件)会失败。linter 能读 `.gitignore` 时必须让它读,新增的忽略条目随之生效——ESLint 用 `eslint/config` 自带的 `includeIgnoreFile`,并传 `{ gitignoreResolution: true }`(缺省时模式按配置文件的位置解析,配置文件与 `.gitignore` 不在同一目录时就与 git 的解析不一致);不再另装 `@eslint/compat`,它是这个函数迁入 ESLint 之前所在的包;不能读时把被忽略的目录逐项列进忽略列表。**判据**:`.gitignore` 的每个目录条目都有结论——由 linter 读取覆盖、已列入忽略列表、或 linter 默认已排除(ESLint 的 `node_modules/`)。

## 3. 存量报错按三类处置

**不得改为只检查改动过的文件**——存量从此永远不会被看见,而它正是本节要处置的对象。**每条报错先归类再动手**,归类判据是「修它会不会改变运行行为或类型签名」:

| 类 | 判据 | 处置 |
|---|---|---|
| A 机械 | 修改不改变行为与签名(多余断言、多余转义、无用初值、`prefer-const`、源码里的裸不可见字符写成转义) | 本次修掉 |
| B 框架约束 | 规则与代码改变不了的外部约束冲突 | 在配置里**按文件范围**关闭,写明约束与退役条件 |
| C 需判断 | 修了会改变行为或签名,须逐处判断并补测试 | 规则**保持开启**,存量逐行豁免并建票(见下) |

- **自动修复只在确认过它只碰 A 类时用**:先按规则统计带修复的报错,确认全部属于 A 类再跑 `--fix`。修复后必查两类残留——被删掉的类型断言留下的孤立 import,以及包住它的多余括号——它们是本次改动造成的,按「只清理自己造成的孤儿」一并清掉。
- **判为 B 类前必须坐实约束存在**:实测替代写法确实不可行才算框架约束。替代写法可行的,它是 A 类,修掉。注释里写的约束只写已验证的事实,不写对工具行为的猜测。
  - 替代写法是「改用 import 引入类型声明」时,验证它在起作用要把**所有**引入点一起删掉再跑类型检查:全局类型扩展对整个程序生效,只删一处时其他文件的同一 import 仍把声明带进程序,变异落不到被测对象上,类型检查照样通过。
- **C 类不得在配置里按规则关闭**:规则级关闭会连同将来的新违规一起放过,豁免覆盖的是还不存在的代码。做法:规则保持开启,**每处存量在上一行加 `eslint-disable-next-line <规则> -- see #<票号>`**,每条规则建一张票,票里写明定位方式(`git grep "see #<票号>"`,插入注释后原行号会移位)、为什么不能机械修、验收标准(注释全部移除且 lint 通过)。
  - 不用 linter 自带的批量抑制文件:它按文件与规则记**数量**,删一处合法、加一处违规时总数不变,对替换失明。
  - 插注释前先确认目标行不在 JSX 子节点或多行模板字符串内部——那里插一行注释会改变语法。
- **`exhaustive-deps` 这类依赖类告警逐处判意图**:确实漏了依赖的补上(依赖是稳定引用的,补上不改变行为;依赖是每次渲染新建的函数的,先 `useCallback` 再补);**有意不写**的依赖用行内 disable 写明理由,不为了满足规则改写代码结构。有意不写的那条行为若是用户可见的,写进对应 spec 的边界节。

## 4. 接线

- 加 `lint` 脚本;项目有全量验证脚本时接在类型检查之后;`.github/workflows/` 里有检查 workflow 时加一个 lint 步骤,CI 门禁的规范以 `/github-ops` 的「CI 检查门禁与分支保护」节为准。**仓库的分支规则把这个 job 设为必需检查时,不得改它的名字**——分支规则按名字匹配,改名即脱钩。有没有这样的规则必须用 API 读出来核实,不凭印象:私有仓库在免费计划下规则集与分支保护均不可用(接口返回 403),此时没有任何必需检查,job 名可以随内容改。
- `capabilities.toml` 的 `lint` 段:`enabled = true`,`source` 指 linter 配置文件,`enforced-by` 指 lint 脚本。

## 5. 证明门禁能红

一道从没红过的门禁与没有门禁在证据上等价。下列探针各跑一次,**每个探针都是新建的文件,验完删除文件还原**——不改已有文件,还原就不会误伤正式改动。每次都直接取 lint 命令的退出码(不经管道),并核对报错指向探针文件本身:

| 探针 | 预期 |
|---|---|
| 一个普通 error(如漏 await 的 Promise) | 退出码非 0 |
| 一个 warning(如 effect 漏写依赖) | 退出码非 0,且提示超出 warning 上限 |
| 一个不属于任何 tsconfig 的 `.ts` 文件 | 退出码非 0(类型感知规则找不到工程) |
| C 类某条规则的一处新违规 | 退出码非 0——证明规则对新代码仍开着 |
| 一条不再对应任何违规的 disable 注释 | 退出码非 0——证明修掉存量后注释不会被遗忘 |

再做一次**覆盖核对**:版本库跟踪的可 lint 文件清单与 linter 实际报告检查过的文件清单逐个对比,**两个方向都必须为空**(按设计排除的目录单独计数):跟踪了却没查到的,是漏查;查到的文件里有被 git 忽略的(`git check-ignore` 命中),是 linter 读进了忽略文件(第 2 节的忽略要求)。后一方向只在带着被忽略文件的工作检出里看得见——干净检出里没有这些文件,差集恒为空——所以覆盖核对必须在开发者的工作检出上跑。退出码 0 只说明「查过的都没问题」,不说明「该查的都查了」。
