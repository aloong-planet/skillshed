# 文档一致性收口

## 文档一致性收口(一轮改动收尾)

下文称本轮工作的主 agent 为委派方,执行文档一致性回归的一方为执行方。一轮改动收尾的文档一致性回归,由委派方交给执行方执行,再由委派方核对交回。本节是委派方派出与核对交回的规则,其中「交回与文档的界定」一节同时约束执行方。回归本身的规则在 [regression.md](regression.md),由执行方完整读取;委派方不得读它,按本节「自己执行」一条自己执行回归、以及按「全 feature 收口」节执行收口的除外。

### 派出

当前工具能派子 agent 时,必须把回归交给一个不继承本次对话的子 agent 作为执行方,由它自己按当前工具的 skill 机制载入本 skill 并执行,不得在自己的会话里执行回归;不能派子 agent 的,按本节「自己执行」一条办。被派来执行回归的子 agent 不适用本条。

1. 当前工具能为子 agent 指定模型时,必须指定最新一代里比主会话所用模型低一档的那一档:工具给的是档位别名的,取该档的别名;只能填具体型号的,取该档最新一代的型号,不得因为更便宜而取旧一代的型号。主会话所用已是最小一档的,取最小一档。
2. 当前工具能为子 agent 指定推理强度时,必须取名为 `high` 的一级;没有这个名字的,取比工具默认高一级的那一级。
3. 工具不能指定模型或推理强度的,按工具给的运行,照常派出。
4. 派出前必须把本轮的改动全部提交为 commit,提交后检出里 `git status --porcelain` 的输出为空,才得派出;这时 `git branch --show-current` 与 `git rev-parse HEAD` 给出的,即派出时的分支与 commit。`git status --porcelain` 列出的路径里有不属本轮改动的,不得提交它们,也不得派出,必须停下报告用户:核对交回时,派出时的 commit 之后的每处改动都按执行方所改处置,带着它们派出,它们会被当作执行方的改动恢复掉。
5. 交给执行方的指示必须写明下列各项,缺任一项不得派出;不得写入哪些文档一致、哪些不一致的判断:
   1. 检出的绝对路径。
   2. 分叉点:先拉取远端,再取 `git merge-base HEAD origin/<默认分支>` 的输出;以及派出时的 commit 的完整 SHA。
   3. 本轮改动触碰的 spec 的 slug;一份都没触碰的,写明「无」。
   4. 本轮施工记录目录 `docs/.workings/<slug>/` 的绝对路径。
   5. 按票工作的,票的标识与位置(本地票文件的绝对路径,或 tracker 上的票号);不按票的,写明「无」。
   6. 按「核对交回」第 4 项重新派出的,修复的 commit 范围;首次派出的,写明「无」。
   7. 本轮发生、而检出与施工记录目录里没有任何文件记下的事件:新拍的通则、用户的验收反馈、工作状态的改变。只写发生了什么;没有的,写明「无」。
   8. 要求它按当前工具的 skill 机制载入本 skill、完整读取 [regression.md](regression.md),并作为执行方按其执行。
6. 回归结束必须以执行方的最终交回为准,它交回之前写下的任何东西都不是结束信号。等它交回按全局指令「等待后台工作」进行。执行方执行期间,委派方不得改动检出里的文件。

### 交回与文档的界定

- **文档**:本节与 regression.md 所说的文档,指检出里或本轮施工记录目录里、扩展名为 `.md`、且没有被任何测试读取的文件;是否被测试读取,按文件名在全部测试文件里检索判定。其余文件(代码、测试、配置、界面文案字典、包元数据、测试读取的数据,以及这两处之外的一切文件)都不是文档。
- **交回**:执行方的最终交回只得包含下列四项,不得把回归写成报告文件:本次回归的结论(有无未能解决的发现);它改动过的文档清单;它判过的陈述条数,连同为找出这些陈述所跑的每条检索;每条未能解决的发现,写全哪句陈述与什么不一致、要靠改什么才能消除。

### 核对交回

收到交回后必须依次执行:

1. 在检出里运行 `git branch --show-current` 与 `git rev-parse HEAD`,与「派出」第 4 项记下的分支与 commit(下称该 commit)对照。分支不是派出时的分支,或该 commit 不是 `HEAD` 的祖先(`git merge-base --is-ancestor <该 commit> HEAD` 的退出码非 0)的,不得改动检出,必须停下报告用户。`HEAD` 不是该 commit 的,即执行方提交了,必须先运行 `git reset --soft <该 commit>` 把它的提交撤回工作区,并报告用户。再运行 `git status --porcelain` 与 `git diff --name-only <该 commit>`,列出自该 commit 以来改动的全部路径(含未跟踪的新文件)。不是文档的路径,必须恢复到该 commit 的状态(`git checkout <该 commit> -- <路径>`;该 commit 里没有的新文件删除),并把恢复了哪些路径报告用户。当前工具支持一次请求发出多个调用时,必须把本项各条只读的命令与第 3 项要读的 `git diff -U0 <该 commit>` 放进同一次请求。
2. 交回缺「交回与文档的界定」的「交回」条所列判过的陈述条数或所跑的检索的(执行方没有交回就结束的,即全缺),不得采信交回:必须先按第 3 项提交留下的文档改动,再按「派出」重新派出;重新派出一次后仍如此的,必须停下报告用户。
3. 必须读完交回里的每条发现,再把留下的文档改动提交为 commit,之后才得处置其中任一条。回归由被派出的子 agent 执行的,提交前必须先读它对检出里各文档的改动——它看不到本次对话:取 `git diff -U0 <该 commit>` 的输出里这些文档的部分,该 commit 里没有的新文档读全文。其中每一处新增、改写或删去的陈述,都必须对照本轮的改动与本轮定下的决定判它是否属实,凭这些判不出的,读它所陈述的那处代码或文档再判:新增或改写后不属实的,必须改到属实;删去的陈述仍然成立的,必须恢复;并把改正了哪几处报告用户。留下的改动里有改写 ADR 的,必须把每一条这样的改写列进这次改动交给用户审查的记录(经 PR 交付的即 PR 描述);没有这样的记录的,把这些改写报告用户。只判这些改动里的陈述,不得借此重做回归。
4. 逐条处置发现:要改检出里文档以外的文件(代码、测试、测试读取的数据等)的,必须调 `/implement` 修改并提交,再按「派出」重新交给执行方,交接里写明修复的 commit 范围;其余的(需要新决策,或要由用户回答、决定的),必须报告用户并定下归宿,不得自行裁决。

### 自己执行

当前工具不能派子 agent 时,委派方必须自己完整读取 [regression.md](regression.md),作为执行方按其执行,并在给用户的结论里写明本次回归不是由子 agent 执行的;「核对交回」只执行第 3、4 项,其中重新派出改为自己重跑受影响的部分。

## 全 feature 收口(收口票才跑)

本票是 `/to-tickets` 切出的**收口票**时,在上面那道按票范围的回归之外,再跑一次覆盖整个 feature 的收口。这次收口由收口票自己的会话执行,不交给子 agent,不读也不写任何按票的状态记录(文档同步清单、审查记录、验证状态表):

- **覆盖单位全量查证**:必须依次执行以下两项:
  1. **定范围**:必须完整读取当前已确认的 feature spec,按 `/to-tickets` 的「The feature checklist」从 spec 枚举整个 feature 的有效覆盖单位,含共享约束与跨票组合;feature 级 `docs/.workings/<slug>/checklist.md` 里有哪张票承兑什么的映射的,读它定位各覆盖单位的承兑票,并从当前 spec 反查映射里的漏行与过期、无依据的条目。不得只看收口票自身列出的验收项。
  2. **逐项查证**:必须按 `/to-tickets` 的验证边界与证据规则,对照集成后的代码与它的测试查证每个有效覆盖单位及其适用路径。必须实际读取所引用的测试、门禁输出或人工验收材料,核对它们验证的条件、边界、结果及其对当前 spec 和集成后实现版本的适用性;不得把票已关闭、文件存在或「测试全绿」的摘要当作逐项证据。证据缺失、不可访问或无法证明对当前版本适用的,必须执行对应验证,无法执行的判为未验证并写明具体阻断,不得推断通过。
- **三个阶段按整个 feature 的范围重跑**:必须完整读取 [regression.md](regression.md),按其执行,三个阶段的行改由整个 feature 派生——阶段一的文件清单取全部票的改动并集,阶段三的事件清单取整个 feature 造成的事件。按票查时每次只看一票触碰的范围,而多票拼起来才出现的不一致(同一术语两票各译一次、后票改掉了前票写进 spec 的行为)落在每一票的范围之外,逐票查碰不到。回归未能解决的发现,由本会话按「文档一致性收口」节「核对交回」第 4 项逐条处置,其中重新派出改为由本会话重跑受影响的部分。
- **判定收口**:必须在全 feature 文档回归后执行最终判定;回归改变了 spec 或实现、影响已有证据适用性的,必须先按本节「逐项查证」重核受影响项。收口不写任何表:收口的结论必须写明查出未满足或未验证的覆盖单位与改正了的陈述;一个都没有的,写明查证了多少个覆盖单位。任一有效覆盖单位存在未解决的映射缺口、未验证或失败,或文档回归尚未完成时,不得宣称全 feature 收口完成;不得通过删行或缩小验收条件消除缺口。只有经批准并已同步到当前 spec 的范围调整,才可据此不再查证被移出的覆盖单位,不得将移出范围记成验收通过。

**判据**:票自己写明它是不是收口票,不靠数编号或数未完成票推断。
