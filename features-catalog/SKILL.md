# 功能目录(docs/features/)

使用本文件的文档同步规则时，必须完整读取 [文档同步与记录维护](../implement/document-sync.md)。

必须面向用户维护产品全景，不得将功能目录作为模型默认上下文、立项文档或历史记录，也不得写入决策的取舍过程；变更历史必须留给 git 与 Release Notes。

## 目录不变量

1. **出现即可用**：必须只收录当前版本已具备功能的现行行为，不得为未来功能预建条目或添加状态行。
2. **行为变更就地改写**：行为改变时必须更新现有描述，不得受“只追加”方式限制；历史归属按文首约定执行。
3. **功能移除即删文件**:连同索引行一起删;移除本身若够 ADR 门槛(判据见 domain-modeling),另落 ADR。

推论:默认分支上的 `docs/features/` 永远描述默认分支上的产品——改变用户可见行为的 PR 必须携带对应 features 更新。

## 内容规则

- **只写用户可见行为,零实现细节**:每句都能通过操作产品验证;无文件名、无字段、无协议、无架构词。
- 术语从 CONTEXT.md;分发渠道/安装方式等非产品内行为不入目录。
- 不确定的行为以实际产品为准核实后再写,不编造。

## 粒度判据

1. **用户可指认**：必须按 CONTEXT.md 术语簇与 UI 入口确定用户可指认的功能及其名称；不得按内部模块名划分功能。
2. **独立成篇**:能力清单落在 3–15 条之外时,必须按下列各支重判,条数本身不决定并入或拆分:从属某父功能、用户不单独指认的 → 并入父功能作一节;用户能单独指认的 → 单独成篇,条数再少也成立;不从属任何父功能、用户也不单独指认的 → 它不是一个功能,不入目录;一篇里有用户能分别指认的几簇的 → 按簇拆,拆后仍须满足判据 3;没有这样的簇的 → 保留一篇。
3. **变更局域性**:一次典型功能改进只碰一个文件;某类改动总要同时改两个 → 边界重划。

## 单文件模板

模板、README 与交叉回归报告中写进项目的固定名称（节名、表头、阶段名、收口结论），必须按 [产物固定名称](../repo-scaffold/artifact-names/features-catalog.md) 书写。

```md
# {功能名}

> 关联决策: {ADR-XXXX,可选,只链最相关的}

## 概述
{第一句:什么人/场景下的什么问题。第二句:本功能用什么方式解决。}

## 能力
- {用户可见行为,一行一条,每条可操作验证}

## 边界与不做
- {限制、明确不做的、用户可感知的前提(如系统权限)}
```

## README(索引)

```md
# 功能目录

{必须按本 skill 文首的目录定位、“目录不变量”和“内容规则”生成面向目录读者的说明；将规则展开成正文，不得将此占位指令或依赖本机 skill 路径的链接留在成品中。}

| 功能 | 一句话 |
|---|---|
| [{功能名}]({file}.md) | {一句话} |
```

必须按“阶段二 · 关系对读”的“文件 ↔ 它的索引行”和“规则 ↔ 模板及生成文档”处理索引与 README 说明的同步。

## 更新流程(第 8 步)

- **新功能**:新文件 + 索引行。素材 = 同 slug spec 的用户可见层(必须从 `docs/specs/<slug>.md` 的当前有效需求中提取用户可见行为，不得因需求位于 Functional Requirements、Quality Requirements、Constraints 或失败模式与边界而漏项；产品内部要求不得直接搬入功能目录)。同 slug 的 spec 不存在时,必须按「存量初始化」一条从产品现状提炼并逐条核实,不得因缺 spec 而不写。
- **行为变更**:就地改写对应文件的「能力」/「边界」。
- **功能移除**:按不变量 3 删文件与索引行,**同 slug 的 spec 一并删**。
- **存量初始化**:从现有文档与产品现状逆向提炼;逐条核实,不确定不写。

## 文档一致性收口(第 8 步收尾,本轮最后一道)

features 更新就位后,做一次交叉回归。回归的基本动作只有一个:**把一句陈述与它的对照端并置,判它现在还真不真**——对照端指该句派生自、复述着或引用着的那个东西:实现、同一事实的另一处陈述、索引行、守它的门禁、被它枚举的成员集。

**查验对象含 docs/ 之外的声明面**:凡对用户陈述产品行为的载体都算文档,界面文案字典、各语种 README、包元数据与 docs/ 下的文档同级,不因存放为代码而豁免——它们改起来属代码 diff,查起来却没人当文档查,于是成为最久没被读过的一批。字典是否入查按能力 `i18n` 判定(`capabilities.toml`)。

一句陈述的真值被本轮弄坏,只有三种方式,按**本轮 diff 覆盖了这对核对的几端**分成三个阶段。三个阶段只是取材规则不同,不是执行顺序(执行见「停止条件」,取出顺序不限):

| 阶段 | 谎怎么产生 | 行集从哪来 |
|---|---|---|
| 一 · 逐句核真 | 陈述与对照端都在改过的文件里,改了一端忘了另一端 | 本轮改动的声明面文件清单 |
| 二 · 关系对读 | 陈述在没改的文件里,它的对照端被改了——单看每一端都正确,并置才现身 | 关系目录(见该节) |
| 三 · 事件核销 | 两端都没被改,陈述引用的事实被本轮改变了 | 本轮事件清单(见该节) |

三条取材规则互相顶替不了:**跑多少遍阶段一也照不到后两阶段的行**——不是查得不够仔细,是那些句子根本不在它的取材范围内。范围的上界同样由取材规则给出,**不做全仓审计**:每个阶段只判自己行集里的行,行集之外的句子不看;查漏的救济不是扩大范围重扫,是按「发现之后」的归因规则补目录或事件清单。

**每个阶段的产出都是一张逐项带结论的表,不是一句「已收敛」**:只报命中项时,「漏看了」与「看过判合规」在产出上完全一样,而前者恰是要防的那个。**行集按上表机械派生,不得由执行者临场想**:想出来的清单必缺项,而缺的那项不会自己现身。

**用检索派生行集或核对陈述时，检索词必须覆盖被检文件实际用到的每一种语言**：同一事实用另一种语言写成的句子与单一语言的检索词互不匹配，漏掉的那批不报错，输出与「别处没有这种说法」逐字节相同。**判据**：先用一条按文字系统统计的命令（如文件里有没有汉字、有没有拉丁字母）一次得出本次检索范围用到的文字系统，不得为此逐个读文件，也不得按项目声明的工作语言推断（工作语言只约束新写的产物）；一种文字系统只对应一种语言的，即得出该语言；为多种语言共用的（如拉丁字母），必须另行确定用到其中哪几种（按 i18n 字典的语种目录、文件名里的语种标记），确定不了的问用户，不得把它当作其中一种；再为每个检索词写出它在每种语言里的说法（术语、译名、缩写）并逐一检索，记录的检索式里每种语言各有一条。缺了某种语言的检索，不得据以对用该语言写成的句子下结论。

**三张表必须落盘为第 8 步的交付报告**：必须写入 feature 级 `docs/.workings/<slug>/final-regression.md`，按票或全 feature 核对范围定位并维护对应报告，注明日期、范围及适用版本；按票执行时必须注明票身份。更新方式与原始证据保留必须按 [文档同步与记录维护](../implement/document-sync.md)处理，不得只在对话中交付。开 PR 前必须核对本轮范围的报告包含三个阶段的逐项表；某阶段无适用对象时必须记录行集为空及派生依据，缺少本轮范围的报告或任一阶段结论即不得判定第 8 步完成。

按票收尾时，必须完整读取 [Ticket 产物与文档同步清单](../to-tickets/ticket-artifacts.md) 与本票清单，将其中的对象纳入核对，并按下列三阶段取材规则补齐未预列的受影响对象。必须将本轮报告中的证据定位回链至对应同步项，字段及状态判定必须按该规范执行，记录维护必须按 [文档同步与记录维护](../implement/document-sync.md)执行。

### 阶段一 · 逐句核真(两端都在改过的文件里)

对本轮触碰的每一份声明面,逐句问「它现在还真吗」,并按下列各对核对:

1. **spec ↔ 实现**:`docs/specs/<slug>.md` 描述的是最终实现吗?「失败模式与边界」每条都有测试或已标注缺口?
2. **spec ↔ features**:同 slug 两篇不打架?features 的能力/边界是 spec 用户可见层的蒸馏——不该出现 spec 里没有的行为,也不该漏掉用户能感知的变化。
3. **ADR ↔ spec/features**:本次落的 ADR 结论没有被 spec/features 反向表述;spec 里够门槛的决策已落 ADR 并改为引用编号。
4. **CONTEXT ↔ 全体**:新术语已落 CONTEXT.md、新不变量已落项目 AGENTS.md,且本次回归涉及的每一份文档用同一套词(不出现同义异名)。
5. **原型 ↔ 实现**:界面点与已确认原型一致。不一致时,以哪方为准按 `/prototype` 的 UI.md 文首判定;判为实现偏离原型的:本轮内回到 `/implement` 修实现(代码改动,不属「发现之后」节的纯文档当场修);用户要留下实现的样子的,是一次界面改动,按 `/implement` 的准入检查先改原型并经用户确认。不得以给原型标失效代替这两条路。

### 阶段二 · 关系对读(另一端不在 diff 里)

本阶段要核的陈述从不出现在 diff 里(被改的是它的对照端),所以行集只能靠下面的目录去取,不能靠"顺手看见"。关系目录:

- **文件 ↔ 它的索引行**:凡带 README 索引的文档目录(features、specs、ADR、复盘等),新增、改名或改动一句话时索引同步改。漏一行,那份文件在只读索引的人眼里等于不存在。
- **规则 ↔ 模板及生成文档**：必须让模板的生成指令引用最先出现的规则定义，不得在模板中另维护一套手写规则。规则改变时，必须检查生成指令的引用是否仍有效，并更新本轮范围内按该规则生成的文档说明；成品文档必须让其读者无需访问本机 skill 即可理解。
- **一个事实 ↔ 它在别处的陈述**：必须按 [文档同步与记录维护](../implement/document-sync.md)中按变化对象核对关联陈述的规则，派生本阶段的对应关系行并逐项处理。
- **规则 ↔ 守它的门禁**:本轮若有规则由门禁守,核对门禁的检出面是否覆盖该规则的全部形态;覆盖不到的部分要么加宽门禁,要么写明它靠人守。**门禁绿不证明规则被守住,只证明它查的那部分绿。**

**关系目录是开放的**:以上是至今观察到的,不是全集;增补的触发条件见下方归因规则。

### 阶段三 · 事件核销(两端都不在 diff 里)

必须按本轮已发生的事件建立清单，不得只按文件改动面取材；开工时先列出已知事件，后续发生或发现的事件必须补入，并按“停止条件”处理。能用命令枚举的，必须同时记录检索式与输出。必须检查以下事件类别：

- **某个可枚举维度的成员数变了**(支持的数据源、平台、语言、渠道等)→ 该维度的枚举式措辞全部复查。**枚举式措辞 = 把成员逐个列出、或拿成员数说话的句子**;成员数一变它们同刻成谎,而没有任何一处代码 diff 会碰到它们。**按位置与成员一一对应的平行结构同样计入**——耗时表、默认值表、图标表这类按下标对齐的数组既不列成员名、也不报成员数,按「哪里写着成员名」或「哪里断言了数目」去检索都命不中它;少一项不报错,只让最后一个成员取到空值,再算下去整条链变成非数。**判据**:检索该维度时,除按成员名与成员数各检索一遍外,再问一遍「有没有另一个结构靠下标与它对齐」,答得出就把那个结构的长度一并核对。项目有对应门禁的(能力 `enumeration-wording-gate` 已启用,且该维度在其 `source` 所指门禁的检出面内),引用其本次运行结果、不重复人扫——**前提是该门禁的覆盖面已在阶段二核过**,覆盖不到的形态仍须人扫,否则门禁的绿会替它没查的那部分背书;没有门禁的人工扫一遍,并把「该不该为它建门禁」作为一条发现提出。
- **范围内有 `Pending:` 注记** → 逐条问「本轮是否使它到期」;到期的按 `/to-spec` 的 Pending 条款当场处置,不得留到下一轮;处置需要新决策的,按「发现之后」节办。
- **本轮新拍了通则** → 报出它的正本落在哪一层(项目 AGENTS.md 不变量 / ADR / 写作层 skill)。只活在代码注释、原型或 review 记录里的视为未落地,当场补写正本——那三处都不在下一个写代码的人的必经之路上,规则待在那里约束不到任何人。
- **验收反馈、缺陷修复或工作状态改变** → 必须按 [文档同步与记录维护](../implement/document-sync.md)核对关联现行状态及当前有效依据，将受影响的票、共享清单、索引和旧待办列为事件行；不得因这些文件不在 diff 中而跳过。

### 停止条件

必须将三个阶段已派生的表行放入同一个工作队列；后续新增事件或关系产生的表行也必须入队。

- **收敛判据**：必须逐项处理队列；判为无需改动的不产生新项，改动后必须将改后文本与受影响的关系端重新入队。队列为空后，必须执行 [文档同步与记录维护](../implement/document-sync.md) 的“核销前的范围复核”，将新发现的事件或关系按本节入队处理；没有遗漏且队列为空时才可结束核对，不得凭访问次数推断收敛。相同规则组合导致反复改写时，必须记录冲突并按“发现之后”处理；阻断未解决不得宣称完成。
- **取出顺序不限,除非某一行自己写明了前提**(如引用门禁结果的那行):写明前提的,前提那行先处置。
- **事件行去重**：同一事件的事实、适用范围和对照端均未改变时，必须复用已有核销行，不重复入队；任一发生变化或发现新事件时，必须新增或重新开启对应核销行。事件处置产生的文本改动必须按本节“收敛判据”回查。
- **重查的是改动的波及面,不是全集**——全量重跑绝大部分是空转。

### 发现之后

发现的不一致**当场修**(纯文档改动,无代码风险);修不了的(如需新决策)明确提出并定归宿,不留在对话里。

**事后又发现东西,先归因再动手**:该项在表里而判错 → 重判该项;**该项不在表里 → 关系目录或事件清单缺了一条,补进本节,再跑受影响的那部分**。补的是镜头,不是力气——"再多查一遍"对不在取材范围内的句子永远无效。

## 全 feature 收口(收口票才跑)

本票是 `/to-tickets` 切出的**收口票**时,在上面那道按票范围的回归之外,再跑一次覆盖整个 feature 的收口:

- 必须逐票检查本 feature 的文档同步清单及其证据，按 [Ticket 产物与文档同步清单](../to-tickets/ticket-artifacts.md) 的“文档同步清单结构与状态”判定各票同步项的当前状态；旧票缺少清单时必须按同一文件的旧票接续规则处理。任一待处理项未解决，必须阻止全 feature 收口；尚未发生的用户验收事件，必须在收口结论注明，不得以同步事件待触发为由跳过票已要求的人工验收；收口票自身 PR 的合并必须按 [文档同步与记录维护](../implement/document-sync.md) 的“合并事件按记录位置记录”记录。
- **清单全量核销**：必须依次执行以下三项：
  1. **读取映射并核对范围**：收口票必须完整读取当前已确认的 feature spec 和同 slug 的 `docs/.workings/<slug>/checklist.md`，定位“spec → tickets → 验证”映射及当前验证记录，按 `/to-tickets` 的“The feature checklist”核对整个 feature 的有效覆盖单位与承兑关系。不得只读收口票自身列出的 AC 或现有映射行；必须从当前 spec 检查漏行，并反查映射中的过期或无依据条目。清单缺失或映射不完整时，必须先按该节补齐，不得跳过，也不得把补表视为已验证。
  2. **逐项查证**：必须按 `/to-tickets` 的验证边界与证据规则，查证全部有效覆盖单位及其适用路径，包括共享约束和跨票组合。必须实际读取所引用的测试结果、门禁输出或人工验收材料，核对它们验证的条件、边界、结果及其对当前 spec 和最终集成实现版本的适用性；不得把勾选状态、票已关闭、文件存在或“测试全绿”摘要当作逐项证据。已有证据只有在上述核对成立时才能复用；证据缺失、不可访问或无法证明对当前版本适用时，必须执行对应验证，无法执行则记录未验证和具体阻断，不得推断通过。
  3. **记录查证结果**：必须将每个有效覆盖单位及适用路径的本轮查证结论、证据定位、spec 与实现版本更新到同一 `checklist.md` 的“当前验证”部分，维护规则必须遵守 `/to-tickets` 的“The feature checklist”。
- **上面各阶段按整个 feature 的范围重跑**:三张表的行改由整个 feature 派生——阶段一的文件清单取全部票的改动并集,阶段三的事件清单取整个 feature 造成的事件。按票查时每次只看一票触碰的范围,而多票拼起来才出现的不一致(同一术语两票各译一次、后票改掉了前票写进 features 的行为)落在每一票的范围之外,逐票查碰不到。
- **判定收口**：必须在全 feature 文档回归后执行最终判定；若回归改变了 spec 或实现、影响已有证据适用性，必须先按本节“逐项查证”和“记录查证结果”重核受影响项。必须在 `docs/.workings/<slug>/final-regression.md` 的本轮记录中引用这组查证记录并写明收口结论；不得在那里另维护一份需求映射，且必须保留本 skill 要求的三阶段文档回归表。任一有效覆盖单位存在未解决的映射缺口、未验证或失败，或文档回归尚未完成时，不得宣称全 feature 收口完成或将收口票标为完成；不得通过删行或缩小验收条件消除缺口。只有经批准并已同步到当前 spec 的范围调整，才可据此核对清单中的移除记录，不得将移出范围记成验收通过。
