# 功能目录(docs/features/)

给人看的产品全景:描述**当前版本已具备功能的现行行为**。不是给模型的默认上下文,不是立项文档,不是历史记录;未来计划归 roadmap,历史归 git/Release Notes,实现与决策归 docs/adr。

## 三条目录不变量

1. **出现即可用**:文件在目录里 = 该功能当前版本就有。无状态行——在场本身就是状态。
2. **行为变更就地改写**:这是现状描述,不受"只追加"约束(与 CONTEXT.md 同类的可改写持久文档);目录内不记变更史,不与 Release Notes 重复记账。
3. **功能移除即删文件**:连同索引行一起删;移除若属重大决策,另落 ADR。

推论:master 上的 `docs/features/` 永远描述 master 上的产品——改变用户可见行为的 PR 必须携带对应 features 更新。

## 内容规则

- **只写用户可见行为,零实现细节**:每句都能通过操作产品验证;无文件名、无字段、无协议、无架构词。
- 术语从 CONTEXT.md;分发渠道/安装方式等非产品内行为不入目录。
- 不确定的行为以实际产品为准核实后再写,不编造。

## 粒度(三判据)

1. **用户可指认**:功能名是使用中会说出口的词,锚点 = CONTEXT.md 术语簇 + UI 入口。
2. **独立成篇**:能力清单 3–15 条;不足且从属他人 → 并入父功能作一节;超出或明显分簇 → 拆。
3. **变更局域性**:一次典型功能改进只碰一个文件;某类改动总要同时改两个 → 边界重划。

## 单文件模板

```md
# {功能名}

> 关联决策: ADR-XXXX(可选,只链最相关的)

## 概述
{第一句:什么人/场景下的什么问题。第二句:本功能用什么方式解决。}

## 能力
- {用户可见行为,一行一条,每条可操作验证}

## 边界与不做
- {限制、明确不做的、用户可感知的前提(如系统权限)}
```

## README(索引)

```md
# 功能目录(Features)

本目录描述**当前版本已具备功能的现行行为**,面向人的产品全景。
- 不变量:出现在本目录 = 当前版本可用;行为变更就地改写;功能移除删除文件。
- 未来计划见 roadmap;历史见 git/Release Notes;实现与决策见 docs/adr。
- 内容规则:只写用户可见行为,零实现细节;术语从 CONTEXT.md。

| 功能 | 一句话 |
|---|---|
| [{功能名}]({file}.md) | {一句话} |
```

一句话变了连索引行一起改。

## 更新流程(七步流程之后的第 8 步)

- **新功能**:新文件 + 索引行。素材 = 施工 spec 的用户可见层(Problem/Solution/User Stories/Out of Scope 四节蒸馏)。
- **行为变更**:就地改写对应文件的「能力」/「边界」。
- **功能移除**:删文件 + 索引行。
- **存量初始化**:从现有文档与产品现状逆向提炼;逐条核实,不确定不写。
