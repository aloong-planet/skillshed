# 文档一致性收口

使用本文件的文档同步规则时，必须完整读取 [文档同步与记录维护](../implement/document-sync.md)。

## 文档一致性收口(第 8 步收尾,本轮最后一道)

下文称本轮工作的主 agent 为委派方,执行文档一致性回归的一方为执行方。一轮改动收尾的文档一致性回归,由委派方交给执行方执行,再由委派方核对交回。本节是委派方派出与核对交回的规则,其中「交回与文档的界定」一节同时约束执行方。回归本身的规则在 [regression.md](regression.md),由执行方完整读取;委派方不得读它,按本节「自己执行」一条自己执行回归、以及按「全 feature 收口」节执行收口的除外。

### 派出

当前工具能派子 agent 时,必须把回归交给一个不继承本次对话的子 agent 作为执行方,由它自己按当前工具的 skill 机制载入本 skill 并执行,不得在自己的会话里执行回归;不能派子 agent 的,按本节「自己执行」一条办。被派来执行回归的子 agent 不适用本条。

1. 当前工具能为子 agent 指定模型时,必须指定最新一代里比主会话所用模型低一档的那一档:工具给的是档位别名的,取该档的别名;只能填具体型号的,取该档最新一代的型号,不得因为更便宜而取旧一代的型号。主会话所用已是最小一档的,取最小一档。
2. 当前工具能为子 agent 指定推理强度时,必须取名为 `high` 的一级;没有这个名字的,取比工具默认高一级的那一级。
3. 工具不能指定模型或推理强度的,按工具给的运行,照常派出。
4. 派出前必须把本轮的改动全部提交为 commit,提交后检出里 `git status --porcelain` 的输出为空,才得派出;这时 `git branch --show-current` 与 `git rev-parse HEAD` 给出的,即派出时的分支与 commit。`git status --porcelain` 列出的路径里有不属本轮改动的,不得提交它们,也不得派出,必须停下报告用户:核对交回时,派出时的 commit 之后的每处改动都按执行方所改处置,带着它们派出,它们会被当作执行方的改动恢复掉。
5. 交给执行方的指示必须写明下列各项,缺任一项不得派出;不得写入哪些文档一致、哪些不一致的判断:
   1. 检出的绝对路径。
   2. 分叉点:先拉取远端,再取 `git merge-base HEAD origin/<默认分支>` 的输出;以及派出时的 commit 的完整 SHA。
   3. 本轮改动触碰的 spec 的 slug;一份都没触碰的,写明「无」。
   4. 本轮施工记录目录 `docs/.workings/<slug>/` 的绝对路径;执行方把回归的结果写成该目录下的 `final-regression.md`,下文称交叉回归报告。
   5. 按票工作的,票的标识与位置(本地票文件的绝对路径,或 tracker 上的票号);不按票的,写明「无」。
   6. 按「核对交回」第 5 项重新派出的,修复的 commit 范围;首次派出的,写明「无」。
   7. 本轮发生、而检出与施工记录目录里没有任何文件记下的事件:新拍的通则、用户的验收反馈、工作状态的改变。只写发生了什么;没有的,写明「无」。
   8. 要求它按当前工具的 skill 机制载入本 skill、完整读取 [regression.md](regression.md),并作为执行方按其执行。
6. 回归结束必须以执行方的最终交回为准,不得以交叉回归报告出现或被写入作为结束信号:报告在回归进行中就会被写入。等它交回按全局指令「等待后台工作」进行;交回之前读取交叉回归报告,即属该指令所说的查看进度。执行方执行期间,委派方不得改动检出里的文件。

### 交回与文档的界定

- **文档**:本节与 regression.md 所说的文档,指检出里或本轮施工记录目录里、扩展名为 `.md`、且没有被任何测试读取的文件;是否被测试读取,按文件名在全部测试文件里检索判定。其余文件(代码、测试、配置、界面文案字典、包元数据、测试读取的数据,以及这两处之外的一切文件)都不是文档。
- **交回**:执行方的最终交回只得包含下列四项:本次回归的结论(有无未能解决的发现);它改动过的文件清单;交叉回归报告的绝对路径;每条未能解决的发现一行,写明其编号与一句话标题。发现的正文、各阶段的表与证据只写进报告,不得写进交回——交回会常驻委派方的上下文,写进去就是报告的第二份副本。

### 核对交回

收到交回后必须依次执行:

1. 在检出里运行 `git branch --show-current` 与 `git rev-parse HEAD`,与「派出」第 4 项记下的分支与 commit(下称该 commit)对照。分支不是派出时的分支,或该 commit 不是 `HEAD` 的祖先(`git merge-base --is-ancestor <该 commit> HEAD` 的退出码非 0)的,不得改动检出,必须停下报告用户。`HEAD` 不是该 commit 的,即执行方提交了,必须先运行 `git reset --soft <该 commit>` 把它的提交撤回工作区,并报告用户。再运行 `git status --porcelain` 与 `git diff --name-only <该 commit>`,列出自该 commit 以来改动的全部路径(含未跟踪的新文件)。不是文档的路径,必须恢复到该 commit 的状态(`git checkout <该 commit> -- <路径>`;该 commit 里没有的新文件删除),并把恢复了哪些路径报告用户。
2. 交回缺「交回与文档的界定」的「交回」条所列任一项的(执行方没有交回就结束的,即四项全缺),不得采信交回,改按第 3 项读报告判定。
3. 必须读交叉回归报告的本轮记录:先核对它含三个阶段各自的逐项表(阶段名见 [产物固定名称](../repo-scaffold/artifact-names/features-catalog.regression.md)),行集为空的阶段记录了为空及派生依据;报告不存在、其中没有本轮记录或缺其中任一的,不得判定第 8 步完成,必须先按第 4 项提交留下的文档改动,再按「派出」重新派出;重新派出一次后仍如此的,必须停下报告用户。再完整读其「发现」小节,读完才得处置其中任一条。交回与报告对不上的(一边有某个编号而另一边没有,或标题与该条内容不符),以报告为准。
4. 必须把留下的文档改动提交为 commit,再处置发现。
5. 逐条处置发现:要改检出里文档以外的文件(代码、测试、测试读取的数据等)的,必须调 `/implement` 修改并提交,再按「派出」重新交给执行方,交接里写明修复的 commit 范围;其余的(需要新决策,或要由用户回答、决定的),必须报告用户并定下归宿,不得自行裁决。

### 自己执行

当前工具不能派子 agent 时,委派方必须自己完整读取 [regression.md](regression.md),作为执行方按其执行,并在交叉回归报告的本轮记录里写明本次回归不是由子 agent 执行的;「核对交回」只执行第 3 至 5 项。

## 全 feature 收口(收口票才跑)

本票是 `/to-tickets` 切出的**收口票**时,在上面那道按票范围的回归之外,再跑一次覆盖整个 feature 的收口。这次收口由收口票自己的会话执行,不交给子 agent:

- 必须逐票检查本 feature 的文档同步清单及其证据，按 [Ticket 产物与文档同步清单](../to-tickets/ticket-artifacts.md) 的“文档同步清单结构与状态”判定各票同步项的当前状态；旧票缺少清单时必须按同一文件的旧票接续规则处理。任一待处理项未解决，必须阻止全 feature 收口；尚未发生的用户验收事件，必须在收口结论注明，不得以同步事件待触发为由跳过票已要求的人工验收；收口票自身 PR 的合并必须按 [文档同步与记录维护](../implement/document-sync.md) 的“合并事件按记录位置记录”记录。
- **清单全量核销**：必须依次执行以下三项：
  1. **读取映射并核对范围**：收口票必须完整读取当前已确认的 feature spec 和同 slug 的 `docs/.workings/<slug>/checklist.md`，定位“spec → tickets → 验证”映射及当前验证记录，按 `/to-tickets` 的“The feature checklist”核对整个 feature 的有效覆盖单位与承兑关系。不得只读收口票自身列出的 AC 或现有映射行；必须从当前 spec 检查漏行，并反查映射中的过期或无依据条目。清单缺失或映射不完整时，必须先按该节补齐，不得跳过，也不得把补表视为已验证。
  2. **逐项查证**：必须按 `/to-tickets` 的验证边界与证据规则，查证全部有效覆盖单位及其适用路径，包括共享约束和跨票组合。必须实际读取所引用的测试结果、门禁输出或人工验收材料，核对它们验证的条件、边界、结果及其对当前 spec 和最终集成实现版本的适用性；不得把勾选状态、票已关闭、文件存在或“测试全绿”摘要当作逐项证据。已有证据只有在上述核对成立时才能复用；证据缺失、不可访问或无法证明对当前版本适用时，必须执行对应验证，无法执行则记录未验证和具体阻断，不得推断通过。
  3. **记录查证结果**：必须将每个有效覆盖单位及适用路径的本轮查证结论、证据定位、spec 与实现版本更新到同一 `checklist.md` 的“当前验证”部分，维护规则必须遵守 `/to-tickets` 的“The feature checklist”。
- **三个阶段按整个 feature 的范围重跑**:必须完整读取 [regression.md](regression.md),按其执行,三张表的行改由整个 feature 派生——阶段一的文件清单取全部票的改动并集,阶段三的事件清单取整个 feature 造成的事件。按票查时每次只看一票触碰的范围,而多票拼起来才出现的不一致(同一术语两票各译一次、后票改掉了前票写进 spec 的行为)落在每一票的范围之外,逐票查碰不到。回归记进交叉回归报告「发现」小节的发现,由本会话按「文档一致性收口」节「核对交回」第 5 项逐条处置,其中重新派出改为由本会话重跑受影响的部分。
- **判定收口**：必须在全 feature 文档回归后执行最终判定；若回归改变了 spec 或实现、影响已有证据适用性，必须先按本节“逐项查证”和“记录查证结果”重核受影响项。必须在 `docs/.workings/<slug>/final-regression.md` 的本轮记录中引用这组查证记录并写明收口结论（按 [产物固定名称](../repo-scaffold/artifact-names/features-catalog.md) 书写）；不得在那里另维护一份需求映射，且必须保留本 skill 要求的三阶段文档回归表。任一有效覆盖单位存在未解决的映射缺口、未验证或失败，或文档回归尚未完成时，不得宣称全 feature 收口完成或将收口票标为完成；不得通过删行或缩小验收条件消除缺口。只有经批准并已同步到当前 spec 的范围调整，才可据此核对清单中的移除记录，不得将移出范围记成验收通过。

**判据**:票自己写明它是不是收口票,不靠数编号或数未完成票推断。
