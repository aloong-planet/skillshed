# 功能目录(docs/features/)

面向用户的产品全景:描述**当前版本已具备功能的现行行为**。不是给模型的默认上下文,不是立项文档,不是历史记录;未来计划归 roadmap,历史归 git/Release Notes,实现与决策归 docs/adr。

## 三条目录不变量

1. **出现即可用**:文件在目录里 = 该功能当前版本就有。无状态行——在场本身就是状态。
2. **行为变更就地改写**:这是现状描述,不受"只追加"约束(与 CONTEXT.md 同类的可改写持久文档);目录内不记变更史,不与 Release Notes 重复记账。
3. **功能移除即删文件**:连同索引行一起删;移除若属重大决策,另落 ADR。

推论:master 上的 `docs/features/` 永远描述 master 上的产品——改变用户可见行为的 PR 必须携带对应 features 更新。

## 内容规则

- **只写用户可见行为,零实现细节**:每句都能通过操作产品验证;无文件名、无字段、无协议、无架构词。
- 术语从 CONTEXT.md;分发渠道/安装方式等非产品内行为不入目录。
- 不确定的行为以实际产品为准核实后再写,不编造。

## 粒度(三判据)

1. **用户可指认**:功能名是使用中会说出口的词,锚点 = CONTEXT.md 术语簇 + UI 入口。
2. **独立成篇**:能力清单 3–15 条;不足且从属他人 → 并入父功能作一节;超出或明显分簇 → 拆。
3. **变更局域性**:一次典型功能改进只碰一个文件;某类改动总要同时改两个 → 边界重划。

## 单文件模板

```md
# {功能名}

> 关联决策: ADR-XXXX(可选,只链最相关的)

## 概述
{第一句:什么人/场景下的什么问题。第二句:本功能用什么方式解决。}

## 能力
- {用户可见行为,一行一条,每条可操作验证}

## 边界与不做
- {限制、明确不做的、用户可感知的前提(如系统权限)}
```

## README(索引)

```md
# 功能目录(Features)

本目录描述**当前版本已具备功能的现行行为**,面向人的产品全景。
- 不变量:出现在本目录 = 当前版本可用;行为变更就地改写;功能移除删除文件。
- 未来计划见 roadmap;历史见 git/Release Notes;实现与决策见 docs/adr。
- 内容规则:只写用户可见行为,零实现细节;术语从 CONTEXT.md。

| 功能 | 一句话 |
|---|---|
| [{功能名}]({file}.md) | {一句话} |
```

一句话变了连索引行一起改。

## 更新流程(第 8 步)

- **新功能**:新文件 + 索引行。素材 = 同 slug spec 的用户可见层(`docs/specs/<slug>.md` 的 Problem/Solution/User Stories/Out of Scope 四节蒸馏——spec 是持久产物,与本目录 slug 一一对应)。
- **行为变更**:就地改写对应文件的「能力」/「边界」。
- **功能移除**:删文件 + 索引行(同 slug 的 spec 一并删)。
- **存量初始化**:从现有文档与产品现状逆向提炼;逐条核实,不确定不写。

## 文档一致性收口(第 8 步收尾,本轮最后一道)

features 更新就位后(此时四类文档都已改完),做一次交叉回归——**只在本次改动触碰的功能范围内查**,不做全仓审计:

1. **spec ↔ 实现**:`docs/specs/<slug>.md` 描述的是最终实现吗(实现期偏离已由第 7 步回写)?「失败模式与边界」每条都有测试或已标注缺口?
2. **spec ↔ features**:同 slug 两篇不打架?features 的能力/边界是 spec 用户可见层的蒸馏——不该出现 spec 里没有的行为,也不该漏掉用户能感知的变化。
3. **ADR ↔ spec/features**:本次落的 ADR 结论没有被 spec/features 反向表述;spec 里够门槛的决策已落 ADR 并改为引用编号。
4. **CONTEXT ↔ 全体**:新术语/不变量已落 CONTEXT.md,且四类文档用同一套词(不出现同义异名)。
5. **原型 ↔ 实现**:界面点与已确认原型一致(不一致按 prototype skill 防腐烂条款:同步或标失效)。

发现的不一致**当场修**(纯文档改动,无代码风险);修不了的(如需新决策)明确提出并定归宿,不留在对话里。

## 全 feature 收口(收口票才跑)

本票是 `/to-tickets` 切出的**收口票**时,在上面那道按票范围的回归之外,再跑一次覆盖整个 feature 的收口:

- **清单全量核销**:`docs/.workings/<slug>/checklist.md` 逐条过,判据同 `/implement` 第 4 步的清单核销,范围从本票承兑项扩到全部条目。按票做时只核了本票承兑的那几条,**跨票才成立的组合行为一条都没被核过**——它不落在任何单张票的承兑范围内,于是每张票都合规地跳过了它。答不出的条目就是这个 feature 没做完,「票都关了」不是判据。
- **上面五项按整个 feature 的范围重跑**:按票查时每次只看一票触碰的范围,而多票拼起来才出现的不一致(同一术语两票各译一次、后票改掉了前票写进 features 的行为)落在每一票的范围之外,逐票查碰不到。

**判据**:票自己写明它是不是收口票,不靠数编号或数未完成票推断。feature 只切了一张票时不设收口票,本节不适用——单票没有跨票组合,该票自己的第 8 步已覆盖它的全部范围。
