# The feature checklist

本文适用于建立、映射、审核与更新 feature checklist 的一切场合。入口:[SKILL.md](SKILL.md)「The feature checklist」节;`/to-spec` 建立清单时直接读本文。

清单模板的标题与模板里的其它固定名称写进项目时,必须按 [产物固定名称](../repo-scaffold/artifact-names/to-tickets.feature-checklist.md)与[to-spec 的固定名称](../repo-scaffold/artifact-names/to-spec.md) 书写。

必须按 `/to-spec` 流程中的[准备：核对记录约定](../to-spec/SKILL.md#准备核对记录约定)使用同一份 feature checklist；本文规定其 spec 到 tickets 的映射及验证责任。

**来源核对只在写 spec 时做**：“已确认来源 → spec”的核对是合成或改写 spec 的一部分，结果记在清单的“来源 → spec”部分。不合成、不改写 spec 时，不得例行重做这项核对；只在发现具体需求歧义、冲突或缺失时，才追溯相关来源或回到 `/to-spec` 处理。“来源 → spec”部分缺失或缺少逐项结论时，必须在当前工作的产出里写明来源核对未记录，不得写成已核对。

1. **枚举 spec**：必须以当前已确认的 spec 为需求基线，完整读取并逐节盘点需求、背景或明确不做的归类，按共享规范的“核对范围与旧格式接续”确定本轮范围并记录其余条目不受影响的依据。必须在本文引言指定的同一份清单的“spec → tickets → 验证”部分枚举本轮覆盖单位，包括适用的质量要求、共享约束及散落在其它章节的义务；复合条件未拆清时必须回到 /to-spec 补齐，不得只在清单中拆出隐藏的新要求。必须按本文“双向审核后再确认拆票”条核对 spec 与 tickets 的双向覆盖。

2. **分配责任**：必须让共享规范规定的本轮核对范围内每个覆盖单位直接对应承兑 ticket 及其引用的相同标识，允许一票承兑多个单位。共享条件必须列全所有适用票和各自验证范围，允许合并为一行或按适用路径拆行；拆行时必须沿用同一覆盖单位的完整标识、注明各行适用路径，并核对各行合计覆盖全部适用范围，各行对原要求的表述不得相互矛盾或改变原意。跨票组合必须列出实现贡献票并指定收口验证责任，不得因此延期各票自身可完成的验收。既有行为无需修改时，必须分配明确的回归验证责任；不得以宽泛票名或组件名代替覆盖。技术前提和流程验收必须按共享规范分类，不得成为无来源的范围扩张。

3. **定验证边界**：必须按 [SKILL.md](SKILL.md)「Every acceptance criterion must name what guarantees it」的 Gate/Test/Evidence 规则为每个承兑项说明保障机制。用户可见行为必须列出入口、动作、可观察结果，并让计划验证经过该用户路径；内部约束必须在对应内部边界验证。执行前必须标为未验证；执行后必须记录实现版本、一句结论和指向证据的位置（测试审查记录里的用例编号、日志文件与节），不得复述证据内容，见 [文档同步与记录维护](../implement/document-sync.md) 的“一个事实只写一处”。计划验证一栏只写计划（入口、动作、可观察结果），不得改写为由哪些测试实现——那一对应只写在测试审查记录的用例设计表里。不得用低层通过替代用户路径验收。

4. **双向审核后再确认拆票**：必须按 [SKILL.md](SKILL.md)「3. Draft vertical slices」规定的审核时点，完成本轮核对范围内 spec 覆盖单位 → ticket → 验证责任的正向核对，以及每个票内验收项 → spec 或明确技术前提/流程依据的反向核对。必须逐项记录漏项、无承兑方、语义收窄、验证边界错误和未批准扩张及其处置；有未解决缺口不得发布。用户调整拆票后必须重核受影响范围，再按现有确认与发布流程执行；不得以行数、已填单元格或关闭票数宣称覆盖。

5. **变更与当前验证**：需求或票范围变化时，必须先按共享规范“稳定身份与变更授权”处理确认及权威来源，再按共享规范更新身份对应与清单，重做受影响的双向核对；票内的需求引用或验收项因此要改写的，必须完整读取 [ticket-templates.md](ticket-templates.md) 并按其改写。必须按 [文档同步与记录维护](../implement/document-sync.md)维护下方“当前验证”部分，不得把旧版本通过无条件沿用到变化后的需求。清单的工作索引定位必须遵守本文引言所引用的“准备：核对记录约定”；不得因历史上有一条通过记录就略过本轮验收。

接续只有“验证历史”的旧清单时，必须按本文“定验证边界”及“变更与当前验证”逐项核对本轮覆盖单位与适用路径，在同一清单建立对应的“当前验证”记录；不得将最后一条历史结果直接当作当前有效结论。未涉及的旧材料必须按 [文档同步与记录维护](../implement/document-sync.md)处理，不得借格式接续扩大本轮验收范围。

必须按本文枚举结果逐项展开下面的清单模板，不得将示例行集当作完整范围。来源核对由 `/to-spec` 填写，本阶段补承兑与验证计划，实施和收口必须更新受影响覆盖单位及适用路径的真实验证结果。
