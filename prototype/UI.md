# UI 原型

**文字选型在前,生成在后**:先用文字描述几种结构方向供用户选择,选定后生成**一个**自包含 HTML 变体——双击/浏览器直开,零构建、零服务、**零后端**。("逻辑对不对"→ [LOGIC.md](./LOGIC.md))

## 流程

1. **文字选型(必须,先于一切生成)**:提出 2–4 个**结构性迥异**的方向,纯文字描述,每案三要素:
   - **布局结构**(双栏/顶栏/两屏导航/全景表……)
   - **信息层级与主操作入口**(什么最显眼、第一动作是什么)
   - **这个方案押什么**(适用场景与取舍,一句话)

   方向之间必须在结构上有分歧——只差颜色/文案的不算方向。**用户选定(或提出混合)前,不生成任何 HTML**——批量预生成多个变体是浪费。

2. **按选择生成单变体**:`docs/prototypes/<功能模块>/prototype-<主题>.html` 单文件——
   - mock 数据内联为 JS 常量,**刻意覆盖边界与罕见但重要的情形**——方案之间的差异往往只在边界上显形,常规数据下几个方案看起来都一样,评判就无从下手;样式内联,视觉对齐项目(色板/字体/密度可抄项目主题变量),不依赖项目构建;
   - **凡随语言、数据源、平台等可枚举维度变化的文案与标签,mock 必须取该维度的实测最长值**,不得只填源语言或首个成员——只填一种时几个方案在挤压态下的差异根本不显形,而挤压态恰是方案高下所在。做不到实测就在页头写明"本页未覆盖 X 维度",别让读者以为已经覆盖;
   - **零后端 + 必要交互**:切换、展开折叠、悬停态、表单聚焦等用内联 vanilla JS 实现;一切"写"操作只做视觉反馈,不落任何数据;
   - **防真空条款**:被原型化的东西若属于某现有界面,内嵌该界面的**简化外壳**(仿头部/侧栏/真实数据密度的 mock)——孤立的设计在真空里都好看,评判语境必须在场。

3. **交付预览与迭代**:写完或改完 HTML 后,**立即在回复中给出 `file://` 绝对预览链接**(规则见 SKILL.md 通用规则 9);不得只丢相对路径。反馈驱动就地改:"换 X 方向试试"→ 替换;"这个头部配那个的侧栏"→ 融合。每轮改完同样再给链接。单变体迭代闭环,始终只维护一份。

4. **例外——用户明确要求多方案并排对比时**,才在同一 HTML 内生成多变体 + 内建切换条:底部居中高对比 pill(与被评判的设计视觉区分),←/→ 循环 + 变体标签,键盘 ←/→(input/textarea/contenteditable 聚焦时不劫持),当前变体写 `location.hash`(file:// 下可分享、刷新稳定)。上限 5 个。

5. **捕获(原型保留)**:定稿方向**按产线标准重写**进真代码(原型约束下写的代码禁止直接晋升);答案(选了什么方向、为什么)记入 issue/commit。**HTML 留在 `docs/prototypes/` 不清空**(持久资产:界面结构方向的活样本)——界面大改时同步更新或标注失效,见 SKILL.md 的防腐烂条款。

## /ui-design 接线

生成或修改任何 UI 原型前,先调 `/ui-design`(Skill 工具)载入界面硬性规范。**其全部规则以该 skill 为唯一事实源,在原型阶段同等生效,本节不复述**——它新增规则时本节自动覆盖。本节只写原型载体(自包含 HTML、零构建)与真代码不同之处的适配:

- **图标**:原型页不 import 项目图标模块,改为把图标内部元素直接内联进 HTML——项目已实现的图标照抄其 path,未实现的照抄图标库官方。
- **颜色**:原型页不引用项目主题文件,色值可内联定义,但语义对应关系须与主题文件一致。两个及以上原型页用到主题文件的同一批 token 时,必须由脚本从主题文件生成一份共享 token 表供各页引用,并写成一致性检查的断言(生成结果与重新生成一致);各页不得各自手抄 token 值——手抄的副本互不相知,主题文件改一处,各页就各自过期。
- **选型预览的载体是原型页本身**:选型触发时不另开对比页,候选按 /ui-design 的预览要求呈现在原型内,随「确认门」一并定稿。
- **豁免范围**:演示 harness、画廊壳、Logic 驾驶面板等原型工装不受 /ui-design 约束(见「演示基建」)。

## 确认门

原型交付后**停下等用户确认,确认前不动真代码**。交付成立的前提是回复里已含可点开的浏览器预览链接(SKILL.md 规则 9);无链接不算已交付。新建原型与修改既有原型(含修 UI bug)都适用——后者不走"文字选型→生成"流程,同样需要这道门。

原型的价值就是在实现之前提供低成本反悔窗口;与实现同轮一起改,等于让用户在已完成的实现面前做选择,窗口就没了。

推论:等待确认期间,"原型已改、真代码未跟进"是**预期状态**,针对两者一致性的检查此时应静默(见「共享视觉块」的分档)。

## 演示基建(harness)条款

原型里一切**非设计本身**的控件——变体切换条、mock 状态开关、页面切换等演示脚手架——必须与被评判的设计隔离,防止读原型的人或模型把脚手架当成功能的一部分:

1. **独立悬浮层**:harness 一律放**独立于页面的悬浮层**(默认停在底部居中的暗色 pill,同多变体切换条形态),**绝不嵌入页面内容流**(页头/分栏标题行/列表内都不行);带「演示·」前缀标签;**禁止复用被评判设计的控件样式**(tab/seg/按钮同款即违规——看起来像设计就会被当成设计)。多组开关共用一条悬浮条,分组用分隔线,上下文相关的组仅在相关分栏时出现。
   - **页面必须在 harness 元素之后引入停靠脚本** `<script src="../demo-harness.js"></script>`(正本 [demo-harness.js](./demo-harness.js),复制时机见 SKILL.md「画廊」节的懒创建):停在固定位置的悬浮条总会盖住某一页的被评判内容,读者必须能把它拖开或收成悬浮球,且拖到哪里都不越出视口;脚本同时把条宽收到最宽一行——换行后的弹性容器仍占满提供给它的宽度,行的两侧留下大片空白。页面不得自行实现拖动或收起,也不得在页面脚本里改写 harness 元素的位置与宽度(会覆盖停靠脚本写入的值)。
   - **居中用两侧定位 + 自动外边距,不用位移变换**:固定定位元素只给左侧定位时,它的可用宽度是从该点到视口右缘;位移变换只把它挪回视觉中心,可用宽度并没变,于是内容一多就在半个视口里换行甚至压成竖排,而写多大的最大宽度都不管用。位移变换还会给内部的固定定位后代造出新的包含块,顺带避开。
   - **内部间距一律用内边距与间隙,不用外边距**:按内容宽度收缩的容器求最大内容宽时不计子项外边距,于是容器按少算的宽度定形,再把内容挤到下一行——表现是"明明放得下却换行了"。
2. **范围限定**(2026-08-01 用户裁定):harness 只承载**被演示功能的 mock 状态开关**(数据/状态组合切换);页面导航、路由切换、视图跳转一律不入 harness——需要页面切换说明原型越了单页职责(见下)。
3. **机器可判标记**:DOM 加 `data-demo-harness` 属性,模型/脚本读取原型时按此过滤。
4. **注记闭环**:页头注释列出全部演示基建并注明"非设计的一部分,勿实现";涉及状态开关的,正文 note 写明真实判定来源(实现由什么决定、app 内无此控件)。
5. **产品维度只在设置原型页切换**:产品维度——**判据**:产品源码以取值列表定义该维度(界面语言、外观明暗、主题配色;模拟的系统语言、系统明暗与加载中/已载入这类功能状态不是)——的取值一律只由设置原型页(产品里改这项设置的那个界面的原型)经维度脚本(正本 [demo-dimensions.js](./demo-dimensions.js),复制时机见 SKILL.md「画廊」节的懒创建)写出;其余原型页不得提供在该维度的取值之间切换的控件,harness、页面内容与共享件(见「共享视觉块」)里都不得。各页各自的开关各存一份取值,读者在一页选的语言或明暗换一页就丢,也无从知道眼前的取值是在哪一页选的;由设置原型页写出,读者换语言、换外观的动作就与产品里一致。
   - **写出的是生效值**:设置原型页必须写出它实际呈现的取值(生效语言、生效明暗、配色),不得写出「跟随系统」这类策略值——策略值要对照设置原型页模拟的系统输入才能解析出实际呈现的取值,其余页拿不到那份输入。设置原型页自身的偏好与模拟输入必须经维度脚本一并保存,重开时原样恢复,否则读者回到设置页看到的不是自己留下的设置。
   - **项目的维度登记表 `docs/prototypes/dimensions.js` 的取值与顺序必须与产品源码的列表去掉策略值(如 `system`)后逐项一致**,并写成一致性检查的断言(写法见「共享视觉块」的一致性检查):登记表是手抄的副本——自包含页面引用不了产品源码——没有断言,产品增删一个取值,副本就静默过期。登记表的默认值必须等于设置原型页未经操作时呈现的取值——否则读者从未动过设置时,设置原型页与其余页呈现的取值就对不上。产品源码为该维度定义了回退值(如缺文案时改用的语言)时,登记表必须写同一个回退值(`fallback`),并纳入同一断言。
   - **跟随以声明为准**:页面要随某维度变化,必须在引入维度脚本的标签上声明 `data-follow="<维度> …"`;未声明某维度的页面一律按登记表的默认值呈现该维度,其中有随该维度变化的文案的,按流程第 2 步写明未覆盖。页面与共享件一律经维度脚本取当前值——脚本的接口(`DemoDimensions.on` / `DemoDimensions.get`),或样式里按根元素上的 `data-demo-<维度>` 属性选择;跟随某维度的页面与它引用的共享件不得再从别的来源取该维度(如按 `prefers-color-scheme` 切明暗):两个来源一旦不一致,页面就一半跟着设置、一半跟着别处。
   - **跟随的页面只画了该维度的部分取值时**,必须在声明里写明画了哪些取值(`<维度>=<取值>,<取值>`),且其中必须含该维度的回退值(登记表的 `fallback`,未写则为默认值):维度脚本据此把未画的取值换成回退值显示,并在页面可见处写明。不得绕过声明自行替换——读者会把代为显示的取值当成未画的那个取值去评判。

**单页职责**:一个原型文件只演示一个页面/模块的形态;要展示另一页面的形态,归该页面自己的原型文件,用跨原型跳转(data-goto)接线,不在单文件内造第二个页面+页切换。**同一屏内同框出现的东西属于同一个原型**——按实现位置切开、把同框的两半分给两个原型文件,评判时就看不到它们之间的视觉关系(对齐、间距、色彩配合),而那正是要评判的对象。
**判据**:发现自己要在原型里加"页面/视图切换"控件时,说明这个文件正在越权演示第二个页面——去查该页面**是否已有自己的原型**(有就改那个并接线,没有就新建),而不是内嵌。

流程第 4 步的多变体切换条是本条款的特例,同样适用上述五条。

## 共享视觉块

同一视觉块(图表、卡片组、复杂控件)出现在多个原型页,**且两处需要保持一致演化**(改一处必须改另一处)时,抽成共享件;仅仅长得像、将来各自演化的不抽——错误耦合以后拆比复制更痛。

- 位置 `docs/prototypes/_shared/<块名>.{css,js}`;JS 挂 `window.<Name>`(file:// 下 ES module import 受 CORS 限制),CSS 走 `<link rel="stylesheet">`(不受此限)。共享件在仓库内、相对路径引用,**双击原型页照常打开,零构建零服务不变**。
- 每个使用点在容器上声明所属块:`data-shared-block="<块名>"`。声明是一致性检查的识别键,**不能用 `.chart` 这类通用类名代替**——同页可能有多种同类控件,按通用类名匹配会把不相干的也纳进来。
- 抽共享消除的是逻辑重复,不消除挂载差异(各页的容器 id、尺寸仍可不同),所以**多个使用点仍要逐个实测**。

**一致性检查**:共享块的契约——必须引用哪些资源、必须有哪些挂载点、样式不变量、真代码里对应组件的必需 props——写成可执行断言,让"哪些地方用了它"从记忆变成脚本能枚举的事实。三条要点:识别键用块身份(页面声明的属性)而非通用类名,否则同类控件会被误纳;加反向检查(引用了资源却没声明 → 报错),否则漏声明就逃出了检查网;**按工作流分档**——默认只查原型侧,跨端一致性单独一档,因为确认门期间"原型已改、真代码未跟进"是预期状态,混在一起查会让检查长期报红而失效。

## 跨原型跳转

功能上相互关联的 UI 原型(导航图标、列表行、tab 等指向的功能已有对应原型时)接线跳转;目标原型不存在的保持静态示意,不造死链。

- 可跳转元素加两个属性:`data-goto="<module>/<id>"`(画廊 manifest 的路由键)与 `data-goto-href="../<module>/<文件>.html"`(独立打开时的相对路径回退)。两者缺一不可:独立打开没有 manifest 可查路径,画廊 hash 路由不认文件路径。
- 页尾统一贴导航 helper(正本如下,自包含零依赖)。file:// 下 iframe 与画廊壳异源,子页改不了父 hash——画廊内走 postMessage 由壳改 hash,独立打开回退为文件导航:

<!-- asset -->
```html
<script>
  // Cross-prototype navigation: inside the gallery ask the parent page to switch; when opened alone, go to the file directly
  document.addEventListener('click', (e) => {
    const el = e.target.closest('[data-goto]');
    if (!el) return;
    if (window.parent !== window) parent.postMessage({ type: 'proto-nav', target: el.dataset.goto }, '*');
    else if (el.dataset.gotoHref) location.href = el.dataset.gotoHref;
  });
</script>
```

- 接收端在 gallery-template.html(`proto-nav` 消息 → 对 manifest 校验 → 改 hash);壳是复制实例,改行为改正本后重新复制。
- 防腐烂(manifest 同步规则的姊妹条):删除原型时,同步撤掉其他原型里指向它的 `data-goto` 接线。
- 带既有点击行为的元素接线时留意分工:跳转属性只放在"打开语义"的子元素上(如名称),别盖住行内按钮(隐藏/恢复等)。

## 实现约束

原型里"看起来该好使却不好使"的问题,按类别定位比逐个属性猜快。反复出现的两类:

### 一、元素在 DOM 里,用户却看不见

"存在"到"可见"之间是一串必要条件,逐环查:**存在 → 有非零尺寸 → 未被祖先裁剪 → 未被遮挡 → 在视口内 → 不透明**。断在哪环,修哪环。

其中最隐蔽的是**祖先裁剪**:任何祖先的 `overflow !== visible` 都会切掉超出它的内容,绝对定位元素与伪元素一并计入。所以溢出型元素(提示框、下拉、浮层)出问题时,从它向上遍历到 body,逐级检查裁剪属性与包含块——根因多半在某个为了圆角或滚动而设的容器上,而那个容器与出问题的元素往往不是同一次改动写的。

定位到根因后的取舍只有两条路:**让容器不裁**(把它原本要的效果下放给子元素承担,如圆角交给最外侧子段),或**把溢出元素移出该容器**(挂到更高层级并自行定位)。前者改动小,后者更彻底。

### 二、依赖浏览器原生行为

原生控件的时机与外观不可控——原生 `title` 有约 1s 延迟,原生 `disabled` 元素不触发 hover 事件。需要控制反馈时机或外观时自行实现,不要在原生行为上叠加补丁(补丁通常改不动时机,只能改外观)。

## 实测纪律

原型交付前在浏览器里跑一遍**行为**,断言必须是渲染级:

- **禁止用"属性存在"冒充"用户看得见"**。`getAttribute('data-tip')` 有值不等于提示框画得出来——它可能被祖先的裁剪盒切掉。
- 溢出型元素的检验方式是**几何**:按同款定位造一个真实元素,量它的 rect,逐级祖先检查是否有 `overflow !== visible` 的盒子会切到它。**元素自己的包围盒不构成证据**——被裁掉或被盖住的元素报出的 rect 与正常元素完全一样;能分辨两者的是对它自己中心点做命中测试,确认那一点属于它。
- 有多个使用点时逐个验,不能验一处推断其余。
- **量之前先确认对象还在文档里**(`document.contains(el)`)。脱离文档的元素,`getBoundingClientRect()` 返回**全零而不报错**——重建过 DOM(innerHTML 重写、重新渲染、切换视图)之后,此前取得的引用全部失效,拿它们算出的尺寸与前后差值是凭空捏造的数字,且形态上与真实测量毫无区别。跨越任何一次重渲染的引用一律重新查询,不复用。

## 反模式

- **未经文字选型直接批量生成多个 UI 变体**——生成成本花在用户没选的方向上
- 只换色/换文案冒充"不同方向"
- "写"操作接真实后端(问题是"长什么样",不是"后端通不通")
- 原型代码直接晋升产线
- **需要一致演化的视觉块在多个原型页各复制一份**——改一处漏一处,漏改的第一成因
- **用属性存在/元素数量冒充视觉验证**——被裁掉的提示框、被遮住的元素都能"验证通过"
