# UI 原型

一个**自包含 HTML 文件**:多个结构性迥异的变体 + 内建切换条,双击/浏览器直开,零构建、零服务、**零后端**。用户翻着看,选一个(或各取所长),其余扔掉。("逻辑对不对"→ [LOGIC.md](./LOGIC.md))

## 产物

`docs/prototypes/<功能模块>/prototype-<主题>.html` 单文件:

- 全部变体在同一文件内;mock 数据内联为 JS 常量;样式内联——视觉对齐项目(色板/字体/密度可抄项目主题变量),但不依赖项目构建。
- **零后端 + 必要交互**:切换、展开折叠、悬停态、表单聚焦等用内联 vanilla JS 实现;一切"写"操作只做视觉反馈,不落任何数据。
- **防真空条款**:被原型化的东西若属于某现有界面,每个变体内嵌该界面的**简化外壳**(仿头部/侧栏/真实数据密度的 mock)——孤立的变体在真空里都好看,评判语境必须在场。

## 流程

1. **定问题与 N**:默认 3 个变体,上限 5(再多不是迥异,是噪音)。计划一行写在文件顶部注释:"设置页三变体,#A/#B/#C 切换"。
2. **生成结构性迥异的变体**:不同布局/不同信息层级/不同主操作入口——只换色换文案不算("三个微调的卡片栅格不是原型,是壁纸");两稿太像,带显式反约束(如"禁用卡片栅格")重做一稿;命名 VariantA/B/C。
3. **内建切换条**:底部居中高对比 pill,与被评判的设计视觉明显区分——←/→ 循环切换(回绕)+ 变体标签(如 `B — 侧栏布局`);键盘 ←/→ 同样可切(input/textarea/contenteditable 聚焦时不劫持);当前变体写 `location.hash`(#A/#B/#C),`file://` 下可分享、刷新稳定。
4. **交付预览**:把 HTML 发给用户(会话内渲染或浏览器打开),给出变体键。有价值的反馈通常是"我要 B 的头部配 C 的侧栏"——那才是用户真正要的设计。
5. **捕获与清理**:赢家**按产线标准重写**进真代码(原型约束下写的代码禁止直接晋升);答案(哪个变体、为什么)记入 issue/commit;HTML 整文件上一次性分支,main 的 docs/prototypes/ 清空。

## 反模式

- 只换色/换文案的"变体"——那是微调,真变体在结构上有分歧
- 变体间共享太多(共享一个 Header 可以,共享 Layout 违背目的——每个变体都该有权扔掉布局)
- "写"操作接真实后端(问题是"长什么样",不是"后端通不通")
- 原型代码直接晋升产线
