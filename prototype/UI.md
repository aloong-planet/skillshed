# UI 原型

**文字选型在前,生成在后**:界面结构未定时,先用文字描述几种结构方向供用户选择(流程第 1 步),选定后生成**一个**自包含 HTML 变体——双击/浏览器直开,零构建、零服务、**零后端**。("逻辑对不对"→ [LOGIC.md](./LOGIC.md))

**原型是 app 界面的基准**:app 的界面照原型实现,界面改动先改原型(见 SKILL.md「原型门」节);原型不得从 app 取样式、文案与取值,也不得拿 app 来校对。唯一例外是**首次画入**:app 已有而尚无原型的界面(连同它在已有原型的界面上的入口,如导航栏上进入它的按钮),以及 /ui-design 要求复用、已有原型里却还没有的既有写法(见「/ui-design 接线」节的「项目既有」条),首次画进原型时以 app 现状为准,画成之后同样以原型为准;其中 app 现状与 /ui-design 不符之处,按该节的首次画入条处理。除上述入口外,已有原型的界面上 app 多出、少了或改了的部分不属首次画入——那是实现偏离了原型。

## 流程

1. **文字选型(先于一切生成)**:原型里结构未定的部分(界定见本步末段)必须先做文字选型——提出 2–4 个**结构性迥异**的方向,纯文字描述,每案三要素:
   - **布局结构**(双栏/顶栏/两屏导航/全景表……)
   - **信息层级与主操作入口**(什么最显眼、第一动作是什么)
   - **这个方案押什么**(适用场景与取舍,一句话)

   方向之间必须在结构上有分歧——只差颜色/文案的不算方向。**用户选定(或提出混合)前,不生成任何 HTML**——批量预生成多个变体是浪费。

   **结构已定的部分不做选型**:照已有原型或 app 既有界面(首次画入时,见文首)画、不改其结构的部分,与用户已确认结构方向的部分,属结构已定,说明文件(见「说明文件」节)必须写明依据——照的是哪个原型、哪个 app 既有界面(按界面名称写,源码路径按 SKILL.md 通用规则 7 不写),或用户所确认的方向;为已定的结构编造备选方向,是让读者在不存在的分歧之间选。已确认的方向内仍有够得上方向的分歧(按上段判据,如同一组选项用分段控件还是下拉、新增的区块排在哪一行)的,该分歧属结构未定。原型里没有结构未定的部分时跳过本步。

2. **按选定的结构生成单变体**:`docs/prototypes/<功能模块>/prototype-<主题>.html` 单文件,连同它的说明文件(见「说明文件」节)——
   - mock 数据内联为 JS 常量,**刻意覆盖边界与罕见但重要的情形**——方案之间的差异往往只在边界上显形,常规数据下几个方案看起来都一样,评判就无从下手;样式内联(共享件按「共享视觉块」链接引用),不依赖项目构建;
   - **凡随语言、数据源、平台等可枚举维度变化的文案与标签,mock 必须取该维度的实测最长值**,不得只填源语言或首个成员——只填一种时几个方案在挤压态下的差异根本不显形,而挤压态恰是方案高下所在。做不到实测就在说明文件里写明"本页未覆盖 X 维度",别让读者以为已经覆盖。页面按演示基建条款第 5 条跟随、且读者能经统一设置或设置原型页切换的产品维度不在此列:挤压态切过去即可见,默认取值按该条的登记表规则定;
   - **零后端 + 必要交互**:切换、展开折叠、悬停态、表单聚焦等用内联 vanilla JS 实现;一切"写"操作只做视觉反馈,不落任何数据;
   - **防真空条款**:被原型化的东西若属于某现有界面,内嵌该界面的**简化外壳**(仿头部/侧栏/真实数据密度的 mock)——孤立的设计在真空里都好看,评判语境必须在场。

3. **迭代**:反馈驱动就地改:"换 X 方向试试"→ 替换;"这个头部配那个的侧栏"→ 融合。单变体迭代闭环,始终只维护一份。

4. **例外——用户明确要求多方案并排对比时**,才在同一 HTML 内生成多变体 + 内建切换条:切换条是 harness 里的一组变体选项(写法按演示基建条款第 1 条),键盘 ←/→ 循环切换(input/textarea/contenteditable 聚焦时不劫持),当前变体写 `location.hash`(file:// 下可分享、刷新稳定)。上限 5 个。用户选定变体后,同一轮内必须删去落选变体及其切换组,页面回到单变体,选中的是哪个变体作为答案按第 5 步处理——落选变体是候选(判据见「候选页」节),定稿之后不再展示,理由见该节的选定即删条。

5. **捕获(原型保留)**:定稿方向**按产线标准重写**进真代码(原型约束下写的代码禁止直接晋升);答案(选了什么方向、为什么)记入 issue/commit。**HTML 留在 `docs/prototypes/` 不清空**(持久资产:界面结构方向的活样本,也是 app 界面的基准,见文首)——其中被推翻、改由别的原型承载的结论,按 SKILL.md 的防腐烂条款标失效。

## 说明文件

本 skill 要求 UI 原型页写给评审者的说明(下称评审说明,各项见本节「分节」条)必须写在页面旁的说明文件里,不得写在页面里:`prototype-<主题>.html` 的说明文件是同一目录下的 `prototype-<主题>.md`,候选页 `candidates-<主题>.html` 的是 `candidates-<主题>.md`。演示条上的说明行不是评审说明,按演示基建条款第 4 条照旧写在演示条里。页面的页头注释(`<!doctype>` 行之后、根元素之前的注释)必须只有一行,写出说明文件的文件名;页面不得加载说明文件,双击直开不受影响。评审说明写在页面里时,读页面源码与它的 diff 的人和模型每读一次都要连同读进来,在浏览器里看页面的人却看不到它。

- **分节**:说明文件按下列顺序分节,节名是固定名称(按项目的 `working-language` 书写,见 [artifact-names/prototype.UI.md](../repo-scaffold/artifact-names/prototype.UI.md)),没有内容的节不写:
  1. 「问题」:本页回答的问题与原型化的目标功能(SKILL.md 通用规则 1)。必须写本页现在回答的问题;前提已不成立的问题必须当场改写,不得留着旧问题另附更正。
  2. 「结构依据」:流程第 1 步要求写明的结构已定部分及其依据。
  3. 「演示基建」:演示基建条款第 4 条要求的清单。
  4. 「待选项」:「候选页」节要求列出的待选项、暂放的推荐项与候选页的文件名。
  5. 「首次画入待定」:「/ui-design 接线」节首次画入条要求逐处列出的待定处。
  6. 「未覆盖维度」:流程第 2 步要求写明的未覆盖维度。
  7. 「已失效结论」:SKILL.md 通用规则 7 的失效标注(写法见该条)。
- **只写现状**:说明文件与页内注释一律不得出现下列形态——带日期的条目、版本号(如 v2、v5.1)、「用户裁定」「定稿」一类的裁决记录、「原为 / 改为 / 撤掉 / 并入」一类的变化记录、为已定形态辩护的理由;答案与决策按 SKILL.md 通用规则 6 处理。「已失效结论」节写的是哪部分现在不能信、以什么为准,不算变化记录;说明代码本身怎么工作的短注释(某个宽度怎么算、某条规则为什么写回被覆盖的默认值)不在此列,留在页内。**判据**:删去这条注释后,改这段代码的人会不会把代码改错——会,是说明代码的注释;不会、只是少知道当初为什么选这个形态,是理由。只增不减的记录会让后写的条目推翻先写的,读者按顺序读到的是互相矛盾的结论。
- **迁移旧页**:改动一个页头注释仍写着评审说明的原型页时,必须先把它迁成本节的写法再做本次改动:评审说明按「分节」条移进说明文件,页头注释只留指向说明文件的一行;页头注释与页内注释里的裁决与历史,删前逐条确认仍成立的已在 spec、ADR 或功能目录里写成结论,找不到的先补进该页所画功能的 spec,已不成立的(被后来的裁决取代的形态、app 已经做到却仍在警告做不到的、已经变了的计数与列表)直接删去。迁移本身不得改变页面的渲染与行为。

## /ui-design 接线

本节只写 `/ui-design` 的规则在原型里的适配,不复述其条文——它新增规则时本节自动覆盖。适配针对的是原型载体(自包含 HTML、零构建)与真代码的不同,以及原型作为 app 界面基准(见文首)带来的不同:

- **「项目既有」指已有原型**:/ui-design 要求复用或对齐项目既有写法的条文(既有的图标按钮样式、颜色变量、文案 key、周边组件的写法),在原型里以已有原型里的为准;已有原型里还没有的,见文首的首次画入。
- **首次画入时与 /ui-design 不符的由用户定以哪边为准**:首次画入(见文首)的部分,app 现状与 /ui-design 的条文不符的,原型页上先照 app 现状画,说明文件逐处列为待定(哪一处、不符的是 /ui-design 哪一条),交付时必须逐处请用户确认以哪边为准;不得自行按 /ui-design 改正,也不得照 app 画而不列——前者在需求之外改了界面,后者让违规不声不响地成了基准。用户定以 /ui-design 为准的,照该条改正,该条要求的流程(如图标选型)照走;无论定哪边,都从说明文件删去该处,决定按 SKILL.md 通用规则 6 处理。
- **图标**:原型页不 import 项目图标模块,改为把图标内部元素直接内联进 HTML(共享件渲染出的也是内联 SVG)。画法按「项目既有」条取;已有原型画过的图标,图标库后来重画了也不跟——换字形是一次图标选型,按 /ui-design 第 1 节走;原型里与 app 里都没有的,照抄图标库官方。
- **颜色与文案**:原型页不引用项目主题文件与产品字典,颜色一律用原型自己定义的 token,界面文案写在原型自己的文案表里。两个及以上原型页用到同一批 token 或同一批文案时,必须分别抽成共享 token 表、共享文案表(`docs/prototypes/_shared/` 下)供各页引用;各页不得各自手抄——手抄的副本互不相知,改一处,各页就各自过期。共享表是原型侧的基准,不由项目主题文件或产品字典生成,也不断言与它们一致(见文首)。/ui-design 以 i18n 字典为对象的条文(各语言成对补齐、同义动作复用既有 key 等),在原型里以文案表为对象,是否适用照 /ui-design 第 0 节对能力 `i18n` 的判定。
- **样式写在类规则里**:/ui-design 要求落在主题样式文件里的样式(交互态的 base 值与交互态规则),原型里必须写在原型页样式表的类规则里——页内 `<style>`,或按「共享视觉块」引用的共享样式表——代替主题样式文件:原型不改产品源码,主题样式文件在原型里无处可写。
- **选型预览画在候选页上**:/ui-design 第 1 节要求的 Artifact 预览页,在原型里由候选页(见「候选页」节)代替。

## 候选页

原型里一处有几种呈现时,先判它们是 mock 状态还是候选。**判据**:定稿之后仍要全部留在原型上供切换的——产品的功能与状态——是 mock 状态,画在原型页上、用 harness 切换(演示基建条款第 2 条);定稿之后只留一个、其余不再展示的是候选。候选按分歧大小分两处:够得上流程第 1 步所说结构分歧的,按该步做文字选型,用户明确要求并排对比时按第 4 步在原型页上做变体切换;其余——/ui-design 第 1 节的图标选型,以及配色、文案等局部的取舍——一律画在候选页上,随「确认门」一并定稿。下列各条里的「候选」「待选项」都指画在候选页上的这一种。

- **位置与登记**:候选页是 `docs/prototypes/<功能模块>/candidates-<主题>.html`,模块与主题同它所服务的原型页 `prototype-<主题>.html`,一个原型页的全部待选项画在同一张候选页上;待选项落在被几个原型页共用的共享件上的,候选页服务其中在注册表 `manifest.js` 里排在最前的那个。候选页在 `manifest.js` 里以 `type: 'candidates'` 登记,画廊据此给它标上候选标签。
- **原型页上只放推荐项**:被评判的界面里只放推荐项;不得为切换候选加开关——页面里不得,harness 里按演示基建条款第 2 条同样不得(第 4 步的变体切换组不是这种候选的开关)——在同一处切来切去看不到 /ui-design 要求的并排。原型页的说明文件必须列出每项待选、暂放的推荐项与候选页的文件名。
- **按原型页对待,下列几处除外**:候选页适用原型页的全部规则,唯下列几处不适用:
  - 流程第 2 步的文件命名与防真空条款,以及「演示基建」节单页职责里同框不得切开的一条——候选页只画格子(见下),评判语境由格子里的相邻元素提供,整屏在原型页上。
  - 流程第 5 步与 SKILL.md 通用规则 6 的保留——它选定后即删(见本节的选定即删条)。
  - 各条里「两个及以上原型页」「多个原型页」的计数——它选定后即删,为它抽出的共享文件随即少一个使用者。
  - 「跨原型跳转」节——候选页不作任何入口的对应原型,格子里照抄来的入口去掉 `data-goto` 与 `data-goto-href`:它不是产品里的一屏,入口落不到它上面。
- **格子**:每个候选连同 /ui-design 选型预览([icon-preview.md](../ui-design/icon-preview.md),画格子前必须完整读取)要求的相邻元素画在一个格子里,按其预览要求摆放;配色、文案等非图标的候选同样照它摆放。格子里与原型页同一处的部分照原型页现有的写法画:原型页引用的共享文件照样引用,原型页内联的样式与标记照抄(跳转属性按上条去掉;一页只许出现一次的元素,如 `main`,换成 `div` 并保留其类名,照抄的样式规则里以元素名选中它的,元素名随之换成 `div`);同一轮里改了原型页上的这一处,候选页必须跟着改——两处写法不一,读者在格子里选中的就不是原型页上的样子。
- **原型页的根样式写在 app 窗口容器上**:原型页上 app 窗口的根样式(底色、文字色、字体、整窗高度、禁止滚动、排布等)必须写在画 app 窗口的那个容器上,不得写在页面的 `html`、`body` 上(页面没有这一层容器的,先加上);共享样式表里的同样如此。其中可继承属性(以 CSS 规范给该属性标的继承性为准,如 `color`、`font` 各属性、`line-height`)与 `background` 各属性的声明,同时以候选页上的每个格子为目标——格子画的是 app 窗口里的一块,外观要与 app 窗口里同一处一致,而它不在 app 窗口之内,继承不到 app 窗口上的声明;其余声明只以 app 窗口容器为目标——它们定的是 app 窗口这个盒子自身的尺寸、排布与滚动,格子的盒子由候选页排布。写在页面 `html`、`body` 上的根样式被候选页照引照抄,锁定整窗高度与滚动的规则让视口外的格子滚不到,排布规则(如弹性布局)把格子排进同一行;候选页随时会被加出来,不得等有了候选页才这样写。**判据**:选择器最终选中的是 `html` 或 `body` 本身才算写在它们上面(如 `body`、`html, body`、`html.dark body`);token 表(「/ui-design 接线」的颜色与文案条)里的自定义属性声明不是根样式,照常写在根元素上;去掉页面默认外边距的声明(如 `body { margin: 0 }`)属页面自身的外框,也不是根样式,照常写在 `body` 上;`*` 这类通配选择器不算,照原样保留——格子同样要靠它(如 `box-sizing: border-box`),改挂到容器上,格子就失去它,尺寸随之走样。
- **深浅两栏固定明暗**:深浅色并排时,深浅两栏必须各自固定呈现一种明暗、不跟随明暗维度——这是并排对照,不是在维度取值之间切换的控件,演示基建条款第 5 条「跟随以声明为准」整条对这两栏的明暗不适用。做法:把主题 token 的深浅两套声明分别挂到两栏的容器上。
- **交付时点明**:交付回复里必须写明候选页上有哪几项待选、原型页上暂放的是哪个候选,并给出候选页的链接(SKILL.md 通用规则 9)——候选页不在原型页上,读者不经提示不会知道还有待选项。
- **选定即删**:用户选定某项后,同一轮内必须:原型页换上选中项(选中的是推荐项时不动);从原型页的说明文件删去该项,候选页上不再有待选项时一并删去候选页的文件名;从候选页删去该项,候选页上不再有待选项时删除候选页、它的说明文件及其 `manifest.js` 条目。答案按 SKILL.md 通用规则 6 处理。不得为留作对照保留落选的候选,也不得把它们移进原型页——落选项仍在眼前,读者与读原型的模型都分不出哪个是定稿;要换候选,按 /ui-design 第 1 节重走预览,另出候选页。

## 确认门

原型交付后**停下等用户确认,确认前不动真代码**。新建原型与修改既有原型(含修 UI bug)都适用——后者不走"文字选型→生成"流程,同样需要这道门。

原型的价值就是在实现之前提供低成本反悔窗口;与实现同轮一起改,等于让用户在已完成的实现面前做选择,窗口就没了。

## 演示基建(harness)条款

原型里一切**非设计本身**的控件——变体切换条、mock 状态开关、页面切换等演示脚手架——必须与被评判的设计隔离,防止读原型的人或模型把脚手架当成功能的一部分:

1. **独立悬浮层**:harness 一律放**独立于页面的悬浮层**,**绝不嵌入页面内容流**(页头/分栏标题行/列表内都不行);带「演示·」前缀标签(固定名称,按项目的 `working-language` 书写,见 [artifact-names/prototype.UI.md](../repo-scaffold/artifact-names/prototype.UI.md))。多组开关共用一条悬浮条,上下文相关的组仅在相关分栏时出现。
   - **页面必须在 harness 元素之后引入停靠脚本** `<script src="../demo-harness.js"></script>`(正本 [demo-harness.js](./demo-harness.js),复制时机见 SKILL.md「画廊」节的懒创建):停在固定位置的悬浮条总会盖住某一页的被评判内容,读者必须能把它拖开或收成悬浮球,且拖到哪里都不越出视口;脚本同时把条宽收到最宽一行——换行后的弹性容器仍占满提供给它的宽度,行的两侧留下大片空白。页面不得自行实现拖动或收起,也不得在页面脚本里改写 harness 元素的位置与宽度(会覆盖停靠脚本写入的值)。
   - **外观只由停靠脚本给出**:harness 的内容必须按停靠脚本文件头的标记约定写(前缀标签、组卡片、动作组、说明行各用什么元素与类名,都在那里);页面不得为 harness 及其内部元素写样式:样式规则的选择器里不得出现 `data-demo-harness` 或脚本约定的类名,harness 内的元素不得带 style 属性,也不得用约定之外的元素与类名。各页自写的演示条外观各不相同,读者每换一页就要重新辨认哪个是标题、哪个是选项;页面的类名与样式带进 harness,它就会长得像被评判的设计(tab、分段、按钮同款),被当成设计的一部分。**判据**:在页面源码里检索 `data-demo-harness` 与 `dh-`,命中只落在 harness 的标记与页面脚本对它的读写上,不落在任何样式规则里;harness 内的元素没有 style 属性,元素与类名都在脚本的约定之内。
2. **范围限定**:harness 里的控件只限**被演示功能的 mock 状态开关**(数据/状态组合切换),流程第 4 步的变体切换组除外;页面导航、路由切换、视图跳转一律不入 harness——需要页面切换说明原型越了单页职责(见下)。
3. **机器可判标记**:DOM 加 `data-demo-harness` 属性,模型/脚本读取原型时按这个属性过滤。
4. **注记闭环**:说明文件列出全部演示基建并注明"非设计的一部分,勿实现";涉及状态开关的,必须在 harness 的说明行(停靠脚本标记约定里的 `dh-note`)写明这些状态在产品里由什么决定、app 内无此控件——写进页面内容流就成了被评判的设计,只写在说明文件里则读者在页面上看不到。
5. **产品维度只在设置原型页与画廊的统一设置里切换**:产品维度——**判据**:产品以一份取值列表定义该维度,整体切换界面的呈现(界面语言、外观明暗、主题配色;加载中/已载入这类功能状态不是)——的取值一律经维度脚本(正本 [demo-dimensions.js](./demo-dimensions.js),复制时机见 SKILL.md「画廊」节的懒创建)写出,写出方只有两处:设置原型页(产品里改这项设置的那个界面的原型)可写全部维度;画廊侧栏头部的设置按钮打开的统一设置(画廊壳自带)只写常规维度——界面语言与外观明暗,项目的维度登记表 `docs/prototypes/dimensions.js` 里必须给这两个维度标 `general: true`,其余维度不得标,它们只在设置原型页里切换。两处都必须在引入维度脚本的标签上声明 `data-settings`;其余原型页不得提供在任何维度的取值之间切换的控件,harness、页面内容与共享件(见「共享视觉块」)里都不得。各页各自的开关各存一份取值,读者在一页选的语言或明暗换一页就丢,也无从知道眼前的取值是在哪一页选的;两处写出方存的是同一份取值,在哪一处改,另一处与全部跟随的页面都随之变化。
   - **写出的是生效值,演示条不模拟系统输入**:设置原型页上被评判的设置控件(含「跟随系统」这类策略选项)必须照常可选;设置原型页必须写出它实际呈现的取值(生效语言、生效明暗、配色),不得写出「跟随系统」这类策略值——其余页只能按具体取值呈现。设置原型页的 harness 里不得加模拟策略值据以解析的系统输入(系统语言、系统明暗等)的开关:系统输入如何解析成生效值,问的是「这样运转对不对」,按 SKILL.md 的形态判据归 Logic 原型,放进 UI 原型的 harness 只给读者添一组与评判对象无关的开关。偏好是策略值的维度,呈现维度脚本给出的当前生效值,不另行解析:读者在设置原型页改选策略值时生效值不变,只保存状态;之后统一设置改了该维度的取值,设置原型页照着呈现,偏好仍是策略值——统一设置在这里充当系统。设置原型页自身的偏好必须经维度脚本保存,重开时原样恢复,否则读者回到设置页看到的不是自己留下的设置。
   - **设置原型页必须随统一设置对齐**:设置原型页必须对每个常规维度用 `DemoDimensions.on` 监听生效值(载入时与统一设置改动时都会收到);该项偏好明确选中某个取值、而收到的取值与它不同时,必须把偏好改成明确选中收到的取值,并以 `DemoDimensions.set({}, 新状态)` 只保存状态;偏好是策略值时不改偏好,按「写出的是生效值,演示条不模拟系统输入」呈现收到的取值。两种情形都不得把按自身偏好推出的取值写回——写回会撤销读者在统一设置里的选择;且载入时逐个维度对齐,先对齐的维度若连同其余维度一起写出,其余维度写出的还是按旧状态推出的值,会盖掉统一设置刚改的取值。**判据**:两项偏好都明确选中时,在统一设置里先后改语言与明暗,再打开设置原型页,两项都明确选中刚改的取值;两项偏好都是策略值时,同样操作后两项偏好不变、页面按刚改的取值呈现;两种情形下其余设置都不变,重开设置原型页仍是。
   - **维度登记表列出各维度的取值与顺序,不含「跟随系统」这类策略值(如 `system`)**:登记表是原型侧的基准,不由产品源码生成,也不断言与它一致(见文首)。登记表的默认值:设置原型页未经操作时明确选中某个取值的维度,必须等于该取值——否则读者从未动过设置时,设置原型页与其余页呈现的取值就对不上,而且维度脚本在未存任何取值时给出的是登记表默认值,设置原型页收到后按「设置原型页必须随统一设置对齐」对齐,把偏好悄悄改成明确选中登记表默认值,不报任何错。**判据**:清空浏览器本地存储后打开设置原型页,各维度的生效值等于登记表默认值,且偏好仍是未经操作时的样子;改了设置原型页偏好的初值或登记表默认值之后必须重跑。尚无设置原型页,或设置原型页未经操作时该维度的偏好是策略值时,取登记表为该维度写的回退值(`fallback`,如缺文案时改用的语言),未写回退值的取登记表的第一个取值。
   - **跟随以声明为准**:页面要随某维度变化,必须在引入维度脚本的标签上声明 `data-follow="<维度> …"`(声明 `data-settings` 的两处写出方跟随全部维度,不另写);未声明某维度的页面一律按登记表的默认值呈现该维度,其中有随该维度变化的文案的,按流程第 2 步写明未覆盖。页面与共享件一律经维度脚本取当前值——脚本的接口(`DemoDimensions.on` / `DemoDimensions.get`),或样式里按根元素上的 `data-demo-<维度>` 属性选择;跟随某维度的页面与它引用的共享件不得再从别的来源取该维度(如按 `prefers-color-scheme` 切明暗):两个来源一旦不一致,页面就一半跟着设置、一半跟着别处。
   - **跟随的页面只画了该维度的部分取值时**,必须在声明里写明画了哪些取值(`<维度>=<取值>,<取值>`),且其中必须含该维度的回退值(登记表的 `fallback`,未写则为默认值):维度脚本据此把未画的取值换成回退值显示,并在页面可见处写明。不得绕过声明自行替换——读者会把代为显示的取值当成未画的那个取值去评判。

**单页职责**:一个原型文件只演示一个页面/模块的形态;要展示另一页面的形态,归该页面自己的原型文件,用跨原型跳转(data-goto)接线,不在单文件内造第二个页面+页切换。**同一屏内同框出现的东西不得切开分给两个原型文件各画一半**——按实现位置切开、把同框的两半分给两个原型文件,评判时就看不到它们之间的视觉关系(对齐、间距、色彩配合),而那正是要评判的对象。同一屏上回答不同问题的几个原型(如一个评判列表的加载状态、一个评判详情区新增的编辑区)各画整屏即不算切开:本原型不评判的部分作为语境画出。**判据**:同框的某一部分只出现在另一个原型文件里、本文件缺了它,即为切开。
**判据**:发现自己要在原型里加"页面/视图切换"控件时,说明这个文件正在越权演示第二个页面——去查该页面**是否已有自己的原型**(有就改那个并接线,没有就新建),而不是内嵌。

**同一份数据的加载状态属于同一个原型**:产品在同一块区域上按同一份数据的加载结果择一呈现的状态——尚未加载完(启动骨架、加载中)、加载为空(空态)、加载失败(出错)与加载成功(正式内容)——必须画在同一个原型文件里,用 harness 的状态开关切换,不得各占一个原型文件。这类状态之间要评判的恰是替换时的关系(占位与内容是否同位同高、替换时有无位移);各占一个文件时它们各自演化,只能拿另一个文件里的旧副本去比。**判据**:两种呈现占用同一块区域、且哪一种出现由同一份数据的加载结果决定,即归同一文件;哪一种出现由读者的导航或选择决定的(选中一项前后的详情区、进入另一页),不归本条,按单页职责判。这种开关切的是同一份数据的加载状态,不是单页职责的判据所说的「页面/视图切换」,不构成越权演示第二个页面。

流程第 4 步的多变体切换条同样适用上述五条,第 2 条对它的例外见该条。

## 共享视觉块

同一视觉块(图表、卡片组、复杂控件)出现在多个原型页,**且两处需要保持一致演化**(改一处必须改另一处)时,抽成共享件;仅仅长得像、将来各自演化的不抽——错误耦合以后拆比复制更痛。

**app 外壳件一律抽成共享件**:防真空条款的简化外壳里,在产品里是同一个部件、出现在多个界面上的(导航栏、列表栏等)一律按「需要保持一致演化」判,被两个及以上原型页内嵌时必须抽成共享件——它们本就是同一个部件,不存在各自演化的情形;各页手画的副本只会各自走样(宽度、入口、选中态各不相同),评判语境随之失真。外壳件的样式只写在共享件里,使用它的页面不得为它另写样式规则:页面的覆盖只在那一页生效,恰好造出共享件要消除的那种走样。

- 位置 `docs/prototypes/_shared/<块名>.{css,js}`;JS 挂 `window.<Name>`(file:// 下 ES module import 受 CORS 限制),CSS 走 `<link rel="stylesheet">`(不受此限)。共享件在仓库内、相对路径引用,**双击原型页照常打开,零构建零服务不变**。
- 每个使用点在容器上声明所属块:`data-shared-block="<块名>"`。声明是一致性检查的识别键,**不能用 `.chart` 这类通用类名代替**——同页可能有多种同类控件,按通用类名匹配会把不相干的也纳进来。
- 抽共享消除的是逻辑重复,不消除挂载差异(各页的容器 id、尺寸仍可不同),所以**多个使用点仍要逐个实测**。

**一致性检查**:共享块的契约——必须引用哪些资源、必须有哪些挂载点、样式不变量——写成可执行断言,让"哪些地方用了它"从记忆变成脚本能枚举的事实。两条要点:识别键用块身份(页面声明的属性)而非通用类名,否则同类控件会被误纳;加反向检查(引用了资源却没声明 → 报错),否则漏声明就逃出了检查网。断言只对照原型自身,不拿原型去对照真代码或产品源(见文首)。

## 跨原型跳转

功能上相互关联的 UI 原型(导航图标、列表行、tab 等入口已有对应原型时,对应关系与对应原型就是本页时的处理见下条)接线跳转;目标原型不存在的保持静态示意,不造死链。

- **对应原型按入口的落点定**:入口在产品里打开的那一屏及其打开时的状态是它的落点(如导航按钮进入的是尚未选中任何条目的列表,列表行进入的是该条目的详情);评判对象落在落点上的原型才是对应原型(评判落点的一部分即算),只把落点当语境画出的不算。对应原型只有一个时取它,不止一个时取注册表 `manifest.js` 里排在最前的那个。取定的原型就是入口所在的页本身时,该入口不得跳转——独立打开与画廊内点它都不重载页面、不换页,与静态示意一样——由共享件渲染的入口同样按它所在的页判定:落点就是眼前这一屏,接回本页只会在独立打开时重载页面,丢掉读者在演示条上切好的状态。取定的是别的原型时,必须接到它。**判据**:对每个接了线的入口,说得出它的落点,以及目标原型评判的是落点上的哪一部分;对每个取定原型是本页的入口,独立打开与画廊内各点一次,页面不重载、画廊不换页。
- 可跳转元素加两个属性:`data-goto="<module>/<id>"`(画廊 manifest 的路由键)与 `data-goto-href="../<module>/<文件>.html"`(独立打开时的相对路径回退)。两者缺一不可:独立打开没有 manifest 可查路径,画廊 hash 路由不认文件路径。
- 凡在任一 mock 状态下渲染出 `data-goto` 元素的原型页,页尾都必须贴导航 helper(正本如下,自包含零依赖),入口由共享件渲染、页面自身标记里没有 `data-goto` 的页同样要贴——缺 helper 的页上点入口毫无反应,也不报错。file:// 下 iframe 与画廊壳异源,子页改不了父 hash——画廊内走 postMessage 由壳改 hash,独立打开回退为文件导航:

<!-- asset -->
```html
<script>
  // Cross-prototype navigation: inside the gallery ask the parent page to switch; when opened alone, go to the file directly
  document.addEventListener('click', (e) => {
    const el = e.target.closest('[data-goto]');
    if (!el) return;
    if (window.parent !== window) parent.postMessage({ type: 'proto-nav', target: el.dataset.goto }, '*');
    else if (el.dataset.gotoHref) location.href = el.dataset.gotoHref;
  });
</script>
```

- 接收端在 gallery-template.html(`proto-nav` 消息 → 对 manifest 校验 → 改 hash);壳是原样复制的资产,改法见 SKILL.md「本 skill 的文件」节。
- **新建原型时回头接线**:已有原型页与共享件里按「对应原型按入口的落点定」应接到新原型的入口,先前因目标不存在保持静态示意,新建时必须一并接上——不接,这些入口就一直停在静态示意,读者从它们进不到新原型。**判据**:每接一个入口(新原型自己的与回头接的),独立打开与画廊内各点一次,都到达目标原型;只在某个 mock 状态下出现的入口,先切到该状态再点。
- 防腐烂(manifest 同步规则的姊妹条):删除原型时,同步处理其他原型里指向它的 `data-goto` 接线——该入口另有对应原型的,按「对应原型按入口的落点定」重新取定并照该条处理;没有的撤掉接线,恢复静态示意。
- 带既有点击行为的元素接线时留意分工:跳转属性只放在"打开语义"的子元素上(如名称),别盖住行内按钮(隐藏/恢复等)。

## 实现约束

原型里"看起来该好使却不好使"的问题,按类别定位比逐个属性猜快。反复出现的两类:

### 一、元素在 DOM 里,用户却看不见

"存在"到"可见"之间是一串必要条件,逐环查:**存在 → 有非零尺寸 → 未被祖先裁剪 → 未被遮挡 → 在视口内 → 不透明**。断在哪环,修哪环。

其中最隐蔽的是**祖先裁剪**:任何祖先的 `overflow !== visible` 都会切掉超出它的内容,绝对定位元素与伪元素一并计入。所以溢出型元素(提示框、下拉、浮层)出问题时,从它向上遍历到 body,逐级检查裁剪属性与包含块——根因多半在某个为了圆角或滚动而设的容器上,而那个容器与出问题的元素往往不是同一次改动写的。

定位到根因后的取舍只有两条路:**让容器不裁**(把它原本要的效果下放给子元素承担,如圆角交给最外侧子段),或**把溢出元素移出该容器**(挂到更高层级并自行定位)。前者改动小,后者更彻底。

### 二、依赖浏览器原生行为

原生控件的时机与外观不可控——原生 `title` 有约 1s 延迟,原生 `disabled` 元素不触发 hover 事件。需要控制反馈时机或外观时自行实现,不要在原生行为上叠加补丁(补丁通常改不动时机,只能改外观)。

## 实测纪律

原型交付前在浏览器里跑一遍**行为**,断言必须是渲染级:

- **禁止用"属性存在"冒充"用户看得见"**。`getAttribute('data-tip')` 有值不等于提示框画得出来——它可能被祖先的裁剪盒切掉。
- 溢出型元素的检验方式是**几何**:按同款定位造一个真实元素,量它的 rect,逐级祖先检查是否有 `overflow !== visible` 的盒子会切到它。**元素自己的包围盒不构成证据**,能分辨裁掉与正常的是中心点命中测试(判据见 ui-design 的 [state-and-cascade.md](../ui-design/state-and-cascade.md) 第 5 节)。
- 有多个使用点时逐个验,不能验一处推断其余。
- **量之前先确认对象还在文档里**(`document.contains(el)`)。脱离文档的元素,`getBoundingClientRect()` 返回**全零而不报错**——重建过 DOM(innerHTML 重写、重新渲染、切换视图)之后,此前取得的引用全部失效,拿它们算出的尺寸与前后差值是凭空捏造的数字,且形态上与真实测量毫无区别。跨越任何一次重渲染的引用一律重新查询,不复用。
