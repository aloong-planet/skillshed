# UI 原型

**文字选型在前,生成在后**:界面结构未定时,先用文字描述几种结构方向供用户选择(流程第 1 步),选定后生成**一个**自包含 HTML 变体——双击/浏览器直开,零构建、零服务、**零后端**。("逻辑对不对"→ [LOGIC.md](./LOGIC.md))

## 流程

1. **文字选型(先于一切生成)**:原型里结构未定的部分(界定见本步末段)必须先做文字选型——提出 2–4 个**结构性迥异**的方向,纯文字描述,每案三要素:
   - **布局结构**(双栏/顶栏/两屏导航/全景表……)
   - **信息层级与主操作入口**(什么最显眼、第一动作是什么)
   - **这个方案押什么**(适用场景与取舍,一句话)

   方向之间必须在结构上有分歧——只差颜色/文案的不算方向。**用户选定(或提出混合)前,不生成任何 HTML**——批量预生成多个变体是浪费。

   **结构已定的部分不做选型**:照 app 现有界面画、不改其结构的部分,与用户已确认结构方向的部分,属结构已定,页头注释必须写明依据——照的是哪个现有界面,或用户所确认的方向;为已定的结构编造备选方向,是让读者在不存在的分歧之间选。已确认的方向内仍有够得上方向的分歧(按上段判据,如同一组选项用分段控件还是下拉、新增的区块排在哪一行)的,该分歧属结构未定。原型里没有结构未定的部分时跳过本步。

2. **按选定的结构生成单变体**:`docs/prototypes/<功能模块>/prototype-<主题>.html` 单文件——
   - mock 数据内联为 JS 常量,**刻意覆盖边界与罕见但重要的情形**——方案之间的差异往往只在边界上显形,常规数据下几个方案看起来都一样,评判就无从下手;样式内联(共享件与派生的共享样式表按「共享视觉块」链接引用),视觉对齐项目(色板/字体/密度可抄项目主题变量),不依赖项目构建;
   - **凡随语言、数据源、平台等可枚举维度变化的文案与标签,mock 必须取该维度的实测最长值**,不得只填源语言或首个成员——只填一种时几个方案在挤压态下的差异根本不显形,而挤压态恰是方案高下所在。做不到实测就在页头写明"本页未覆盖 X 维度",别让读者以为已经覆盖。页面按演示基建条款第 5 条跟随、且读者能经统一设置或设置原型页切换的产品维度不在此列:挤压态切过去即可见,默认取值按该条的登记表规则定;
   - **零后端 + 必要交互**:切换、展开折叠、悬停态、表单聚焦等用内联 vanilla JS 实现;一切"写"操作只做视觉反馈,不落任何数据;
   - **防真空条款**:被原型化的东西若属于某现有界面,内嵌该界面的**简化外壳**(仿头部/侧栏/真实数据密度的 mock)——孤立的设计在真空里都好看,评判语境必须在场。

3. **交付预览与迭代**:写完或改完 HTML 后,**立即在回复中给出 `file://` 绝对预览链接**(规则见 SKILL.md 通用规则 9);不得只丢相对路径。反馈驱动就地改:"换 X 方向试试"→ 替换;"这个头部配那个的侧栏"→ 融合。每轮改完同样再给链接。单变体迭代闭环,始终只维护一份。

4. **例外——用户明确要求多方案并排对比时**,才在同一 HTML 内生成多变体 + 内建切换条:底部居中高对比 pill(与被评判的设计视觉区分),←/→ 循环 + 变体标签,键盘 ←/→(input/textarea/contenteditable 聚焦时不劫持),当前变体写 `location.hash`(file:// 下可分享、刷新稳定)。上限 5 个。

5. **捕获(原型保留)**:定稿方向**按产线标准重写**进真代码(原型约束下写的代码禁止直接晋升);答案(选了什么方向、为什么)记入 issue/commit。**HTML 留在 `docs/prototypes/` 不清空**(持久资产:界面结构方向的活样本)——界面大改时同步更新或标注失效,见 SKILL.md 的防腐烂条款。

## app 已实现的部分照 app 画

原型页上 app 已经实现、而本原型并不在重新设计的部分——流程第 2 步防真空条款的简化外壳、启动骨架、已有界面文案等——必须取自 app 的实现,不得凭印象重画,新建与修改原型同样适用:这些是评判语境而非评判对象,与 app 不一致就是在错的语境里评判,读者也分辨不出哪些差异是本原型提出的。图标与主题 token 按「/ui-design 接线」的图标条与颜色条取;其余按内容分三种:

- **样式规则**:能从 app 的样式源按选择器取出、且两个及以上原型页都用到的(共享件的样式规则对每个嵌入它的页都算用到,不论该页的 mock 状态是否画出它),由脚本生成共享样式表,并写成一致性检查的断言(生成器的要求见「共享视觉块」的派生文件条);其余照 app 手抄,并在原型源码注释里写明对应的 app 源文件,app 改动时据此回查。
- **尺寸与结构**:样式源里取不出的(写在组件模板里的宽高、占位排布),同样照 app 手抄并注明 app 源文件。
- **界面文案**:项目能力声明的 `i18n` 启用时(判定按全局指令的「项目能力声明」节),逐字取自产品字典,字典里没有的才自拟;两个及以上原型页用到字典文案时,必须由脚本从字典生成共享文案表供各页引用,并写成一致性检查的断言(生成器的要求见「共享视觉块」的派生文件条)——各页手抄的文案互不相知,字典改一处,各页就各自过期。未启用时照 app 界面上的原文抄。

## /ui-design 接线

生成或修改任何 UI 原型前,先调 `/ui-design`(Skill 工具)载入界面硬性规范。**其全部规则以该 skill 为唯一事实源,在原型阶段同等生效,本节不复述**——它新增规则时本节自动覆盖。本节只写原型载体(自包含 HTML、零构建)与真代码不同之处的适配:

- **图标**:原型页不 import 项目图标模块,改为把图标内部元素直接内联进 HTML——项目已实现的图标照抄其 path,未实现的照抄图标库官方。
- **颜色**:原型页不引用项目主题文件,色值可内联定义,但语义对应关系须与主题文件一致。两个及以上原型页用到主题文件的同一批 token 时,必须由脚本从主题文件生成一份共享 token 表供各页引用,并写成一致性检查的断言(生成结果与重新生成一致);各页不得各自手抄 token 值——手抄的副本互不相知,主题文件改一处,各页就各自过期。
- **样式落点**:/ui-design 要求落在主题样式文件里的样式(交互态的 base 值与交互态规则),原型里必须写在原型页样式表的类规则里——页内 `<style>`,或按「共享视觉块」引用的共享样式表——代替主题样式文件:原型不改产品源码,主题样式文件在原型里无处可写。
- **选型预览的载体是原型页本身**:选型触发时不得另开对比页,候选一律画在选型预览区——原型页内排在被评判界面之后、与它分开的区块——里,随「确认门」一并定稿:
  - 被评判的界面里只放推荐项;不得为切换候选在 harness 或页面里加开关——候选不是 mock 状态(演示基建条款第 2 条),在同一处切来切去也看不到 /ui-design 要求的并排。
  - 预览区必须标 `data-demo-preview`,标题带「演示·」前缀(写法见演示基建条款第 1 条),并在页头注释里与演示基建一并列出(演示基建条款第 4 条);页面原本不滚动的,改成可滚动。
  - 预览区内候选按 /ui-design 的预览要求摆放;深浅色并排时,深浅两栏必须各自固定呈现一种明暗、不跟随明暗维度——这是并排对照,不是在维度取值之间切换的控件,演示基建条款第 5 条「跟随以声明为准」里不得从别的来源取该维度的要求对这两栏不适用。做法:把主题 token 的深浅两套声明分别挂到两栏的容器上。
- **豁免范围**:演示 harness、画廊壳、Logic 驾驶面板等原型工装不受 /ui-design 约束(见「演示基建」)。

## 确认门

原型交付后**停下等用户确认,确认前不动真代码**。交付成立的前提是回复里已含可点开的浏览器预览链接(SKILL.md 规则 9);无链接不算已交付。新建原型与修改既有原型(含修 UI bug)都适用——后者不走"文字选型→生成"流程,同样需要这道门。

原型的价值就是在实现之前提供低成本反悔窗口;与实现同轮一起改,等于让用户在已完成的实现面前做选择,窗口就没了。

推论:等待确认期间,"原型已改、真代码未跟进"是**预期状态**,针对两者一致性的检查此时应静默(见「共享视觉块」的分档)。

## 演示基建(harness)条款

原型里一切**非设计本身**的控件——变体切换条、mock 状态开关、页面切换等演示脚手架——必须与被评判的设计隔离,防止读原型的人或模型把脚手架当成功能的一部分:

1. **独立悬浮层**:harness 一律放**独立于页面的悬浮层**(默认停在底部居中的暗色 pill,同多变体切换条形态),**绝不嵌入页面内容流**(页头/分栏标题行/列表内都不行);带「演示·」前缀标签(固定名称,按项目的 `working-language` 书写,见 [artifact-names.md](../repo-scaffold/artifact-names.md));**禁止复用被评判设计的控件样式**(tab/seg/按钮同款即违规——看起来像设计就会被当成设计)。多组开关共用一条悬浮条,分组用分隔线,上下文相关的组仅在相关分栏时出现。
   - **页面必须在 harness 元素之后引入停靠脚本** `<script src="../demo-harness.js"></script>`(正本 [demo-harness.js](./demo-harness.js),复制时机见 SKILL.md「画廊」节的懒创建):停在固定位置的悬浮条总会盖住某一页的被评判内容,读者必须能把它拖开或收成悬浮球,且拖到哪里都不越出视口;脚本同时把条宽收到最宽一行——换行后的弹性容器仍占满提供给它的宽度,行的两侧留下大片空白。页面不得自行实现拖动或收起,也不得在页面脚本里改写 harness 元素的位置与宽度(会覆盖停靠脚本写入的值)。
   - **居中用两侧定位 + 自动外边距,不用位移变换**:固定定位元素只给左侧定位时,它的可用宽度是从该点到视口右缘;位移变换只把它挪回视觉中心,可用宽度并没变,于是内容一多就在半个视口里换行甚至压成竖排,而写多大的最大宽度都不管用。位移变换还会给内部的固定定位后代造出新的包含块,顺带避开。
   - **内部间距一律用内边距与间隙,不用外边距**:按内容宽度收缩的容器求最大内容宽时不计子项外边距,于是容器按少算的宽度定形,再把内容挤到下一行——表现是"明明放得下却换行了"。
   - **开关样式用覆盖悬浮条内全部开关的选择器写**(如全部开关共用的一个类名),不得按各组开关的数据属性逐组列出:逐组列出时,新加的一组没补进列表,就继承页面正文色压在暗色条上、也没有选中高亮,不报任何错,看起来像功能坏了。
2. **范围限定**:harness 里的控件只限**被演示功能的 mock 状态开关**(数据/状态组合切换);页面导航、路由切换、视图跳转一律不入 harness——需要页面切换说明原型越了单页职责(见下)。
3. **机器可判标记**:DOM 加 `data-demo-harness` 属性(选型预览区标 `data-demo-preview`,见「/ui-design 接线」),模型/脚本读取原型时按这两个属性过滤。
4. **注记闭环**:页头注释列出全部演示基建并注明"非设计的一部分,勿实现";涉及状态开关的,必须在 harness 内写明这些状态在产品里由什么决定、app 内无此控件——写进页面内容流就成了被评判的设计,只写在页头注释里则读者在页面上看不到。
5. **产品维度只在设置原型页与画廊的统一设置里切换**:产品维度——**判据**:产品源码以取值列表定义该维度(界面语言、外观明暗、主题配色;模拟的系统语言、系统明暗与加载中/已载入这类功能状态不是)——的取值一律经维度脚本(正本 [demo-dimensions.js](./demo-dimensions.js),复制时机见 SKILL.md「画廊」节的懒创建)写出,写出方只有两处:设置原型页(产品里改这项设置的那个界面的原型)可写全部维度;画廊侧栏头部的设置按钮打开的统一设置(画廊壳自带)只写常规维度——界面语言与外观明暗,项目的维度登记表 `docs/prototypes/dimensions.js` 里必须给这两个维度标 `general: true`,其余维度不得标,它们只在设置原型页里切换。两处都必须在引入维度脚本的标签上声明 `data-settings`;其余原型页不得提供在任何维度的取值之间切换的控件,harness、页面内容与共享件(见「共享视觉块」)里都不得。各页各自的开关各存一份取值,读者在一页选的语言或明暗换一页就丢,也无从知道眼前的取值是在哪一页选的;两处写出方存的是同一份取值,在哪一处改,另一处与全部跟随的页面都随之变化。
   - **写出的是生效值**:设置原型页必须写出它实际呈现的取值(生效语言、生效明暗、配色),不得写出「跟随系统」这类策略值——策略值要对照设置原型页模拟的系统输入才能解析出实际呈现的取值,其余页拿不到那份输入。设置原型页自身的偏好与模拟输入必须经维度脚本一并保存,重开时原样恢复,否则读者回到设置页看到的不是自己留下的设置。
   - **设置原型页必须随统一设置对齐**:设置原型页必须对每个常规维度用 `DemoDimensions.on` 监听生效值(载入时与统一设置改动时都会收到);收到的取值与按自身偏好与模拟输入推出的取值不同时,必须把该项偏好改成明确选这个取值,并以 `DemoDimensions.set({}, 新状态)` 只保存状态,不得把按自身状态推出的取值写回——写回会撤销读者在统一设置里的选择;且载入时逐个维度对齐,先对齐的维度若连同其余维度一起写出,其余维度写出的还是按旧状态推出的值,会盖掉统一设置刚改的取值。**判据**:在统一设置里先后改语言与明暗,再打开设置原型页,两项按设置原型页自身偏好与模拟输入推出的取值都是刚改的取值、其余设置不变,重开设置原型页仍是。
   - **维度登记表的取值与顺序必须与产品源码的列表去掉策略值(如 `system`)后逐项一致**,并写成一致性检查的断言(写法见「共享视觉块」的一致性检查):登记表是手抄的副本——自包含页面引用不了产品源码——没有断言,产品增删一个取值,副本就静默过期。登记表的默认值:有设置原型页时必须等于设置原型页未经操作时呈现的取值——否则读者从未动过设置时,设置原型页与其余页呈现的取值就对不上,而且维度脚本在未存任何取值时给出的是登记表默认值,设置原型页收到后按「设置原型页必须随统一设置对齐」对齐,把偏好悄悄改成明确选中,不报任何错。**判据**:清空浏览器本地存储后打开设置原型页,各维度的生效值等于登记表默认值,且偏好仍是未经操作时的样子;改了设置原型页模拟输入的初值或登记表默认值之后必须重跑。尚无设置原型页时取产品源码为该维度定义的回退值,未定义回退值的取登记表的第一个取值。产品源码为该维度定义了回退值(如缺文案时改用的语言)时,登记表必须写同一个回退值(`fallback`),并纳入同一断言。
   - **跟随以声明为准**:页面要随某维度变化,必须在引入维度脚本的标签上声明 `data-follow="<维度> …"`(声明 `data-settings` 的两处写出方跟随全部维度,不另写);未声明某维度的页面一律按登记表的默认值呈现该维度,其中有随该维度变化的文案的,按流程第 2 步写明未覆盖。页面与共享件一律经维度脚本取当前值——脚本的接口(`DemoDimensions.on` / `DemoDimensions.get`),或样式里按根元素上的 `data-demo-<维度>` 属性选择;跟随某维度的页面与它引用的共享件不得再从别的来源取该维度(如按 `prefers-color-scheme` 切明暗):两个来源一旦不一致,页面就一半跟着设置、一半跟着别处。
   - **跟随的页面只画了该维度的部分取值时**,必须在声明里写明画了哪些取值(`<维度>=<取值>,<取值>`),且其中必须含该维度的回退值(登记表的 `fallback`,未写则为默认值):维度脚本据此把未画的取值换成回退值显示,并在页面可见处写明。不得绕过声明自行替换——读者会把代为显示的取值当成未画的那个取值去评判。

**单页职责**:一个原型文件只演示一个页面/模块的形态;要展示另一页面的形态,归该页面自己的原型文件,用跨原型跳转(data-goto)接线,不在单文件内造第二个页面+页切换。**同一屏内同框出现的东西不得切开分给两个原型文件各画一半**——按实现位置切开、把同框的两半分给两个原型文件,评判时就看不到它们之间的视觉关系(对齐、间距、色彩配合),而那正是要评判的对象。同一屏上回答不同问题的几个原型(如一个评判列表的加载状态、一个评判详情区新增的编辑区)各画整屏即不算切开:本原型不评判的部分作为语境画出,app 已实现的按「app 已实现的部分照 app 画」取自 app。**判据**:同框的某一部分只出现在另一个原型文件里、本文件缺了它,即为切开。
**判据**:发现自己要在原型里加"页面/视图切换"控件时,说明这个文件正在越权演示第二个页面——去查该页面**是否已有自己的原型**(有就改那个并接线,没有就新建),而不是内嵌。

**同一份数据的加载状态属于同一个原型**:产品在同一块区域上按同一份数据的加载结果择一呈现的状态——尚未加载完(启动骨架、加载中)、加载为空(空态)、加载失败(出错)与加载成功(正式内容)——必须画在同一个原型文件里,用 harness 的状态开关切换,不得各占一个原型文件。这类状态之间要评判的恰是替换时的关系(占位与内容是否同位同高、替换时有无位移);各占一个文件时它们各自演化,只能拿另一个文件里的旧副本去比。**判据**:两种呈现占用同一块区域、且哪一种出现由同一份数据的加载结果决定,即归同一文件;哪一种出现由读者的导航或选择决定的(选中一项前后的详情区、进入另一页),不归本条,按单页职责判。这种开关切的是同一份数据的加载状态,不是单页职责的判据所说的「页面/视图切换」,不构成越权演示第二个页面。

流程第 4 步的多变体切换条是本条款的特例,同样适用上述五条。

## 共享视觉块

同一视觉块(图表、卡片组、复杂控件)出现在多个原型页,**且两处需要保持一致演化**(改一处必须改另一处)时,抽成共享件;仅仅长得像、将来各自演化的不抽——错误耦合以后拆比复制更痛。

**app 外壳件一律抽成共享件**:防真空条款的简化外壳里,在 app 中由同一个组件画在多个界面上的部件(导航栏、列表栏等)一律按「需要保持一致演化」判,被两个及以上原型页内嵌时必须抽成共享件——它们在 app 里本就是同一个部件,不存在各自演化的情形;各页手画的副本只会各自走样(宽度、入口、选中态各不相同),评判语境随之失真。外壳件的样式只写在共享件里,或按「app 已实现的部分照 app 画」的样式规则条生成进共享样式表,使用它的页面不得为它另写样式规则:页面的覆盖只在那一页生效,恰好造出共享件要消除的那种走样。

- 位置 `docs/prototypes/_shared/<块名>.{css,js}`;JS 挂 `window.<Name>`(file:// 下 ES module import 受 CORS 限制),CSS 走 `<link rel="stylesheet">`(不受此限)。共享件在仓库内、相对路径引用,**双击原型页照常打开,零构建零服务不变**。
- 每个使用点在容器上声明所属块:`data-shared-block="<块名>"`。声明是一致性检查的识别键,**不能用 `.chart` 这类通用类名代替**——同页可能有多种同类控件,按通用类名匹配会把不相干的也纳进来。
- 抽共享消除的是逻辑重复,不消除挂载差异(各页的容器 id、尺寸仍可不同),所以**多个使用点仍要逐个实测**。

**一致性检查**:共享块的契约——必须引用哪些资源、必须有哪些挂载点、样式不变量、真代码里对应组件的必需 props——写成可执行断言,让"哪些地方用了它"从记忆变成脚本能枚举的事实。三条要点:识别键用块身份(页面声明的属性)而非通用类名,否则同类控件会被误纳;加反向检查(引用了资源却没声明 → 报错),否则漏声明就逃出了检查网;**按工作流分档**——默认只查原型侧,跨端一致性单独一档,因为确认门期间"原型已改、真代码未跟进"是预期状态,混在一起查会让检查长期报红而失效。**分档判据**:断言把原型提出、真代码尚未跟进的设计与真代码对照的,确认门期间必然报红,归跨端一档;对照的只是原型自身,或原型照 app 画的部分(由脚本从产品源生成的共享文件、手抄的外壳与骨架值)与 app 的,归默认档——它报红说明原型自身有误或已落后于 app,必须当场修。

**派生文件的生成器要另行核对**:由脚本从产品源生成的共享文件(主题 token 表、取自 app 样式的共享样式表、取自产品字典的共享文案表)的一致性断言是「重新生成的结果与文件一致」——它只证明文件与生成器一致,证明不了生成器没漏掉源里的内容:断言重跑的是同一个生成器,生成器丢掉的东西断言同样看不见,对这类遗漏永远报绿。故:
- 生成器读样式源时必须按原文切出规则块与声明,不得经 CSS 对象模型解析:对象模型丢掉它解析不了的声明、改写它能解析的声明,丢哪些、改成什么随解析器版本而变(jsdom 30 实测:`font` 简写之后的 `font-size` 与 `font-weight`、`content: attr()` 被静默丢弃,`flex: 1` 被改写成 `flex: 1 1 0%`;jsdom 25 则保留 `font` 简写之后的长写)。产物少一条声明与产物正确在形态上无从分辨。
- 生成器新写成或改了读取方式时,必须用不经过该生成器的手段核对一次产物:逐条对照源与产物里的同一条目(样式按选择器对照声明,文案按键对照原文),或把源样式与产物分别套在同一份标记上比对计算样式。**判据**:说得出用了哪种手段、核了哪些选择器或条目、结果如何;说不出即未核。

## 跨原型跳转

功能上相互关联的 UI 原型(导航图标、列表行、tab 等指向的功能已有对应原型时)接线跳转;目标原型不存在的保持静态示意,不造死链。

- 可跳转元素加两个属性:`data-goto="<module>/<id>"`(画廊 manifest 的路由键)与 `data-goto-href="../<module>/<文件>.html"`(独立打开时的相对路径回退)。两者缺一不可:独立打开没有 manifest 可查路径,画廊 hash 路由不认文件路径。
- 凡在任一 mock 状态下渲染出 `data-goto` 元素的原型页,页尾都必须贴导航 helper(正本如下,自包含零依赖),入口由共享件渲染、页面自身标记里没有 `data-goto` 的页同样要贴——缺 helper 的页上点入口毫无反应,也不报错。file:// 下 iframe 与画廊壳异源,子页改不了父 hash——画廊内走 postMessage 由壳改 hash,独立打开回退为文件导航:

<!-- asset -->
```html
<script>
  // Cross-prototype navigation: inside the gallery ask the parent page to switch; when opened alone, go to the file directly
  document.addEventListener('click', (e) => {
    const el = e.target.closest('[data-goto]');
    if (!el) return;
    if (window.parent !== window) parent.postMessage({ type: 'proto-nav', target: el.dataset.goto }, '*');
    else if (el.dataset.gotoHref) location.href = el.dataset.gotoHref;
  });
</script>
```

- 接收端在 gallery-template.html(`proto-nav` 消息 → 对 manifest 校验 → 改 hash);壳是复制实例,改行为改正本后重新复制。
- **新建原型时回头接线**:已有原型页与共享件里指向新原型所演示功能的入口,先前因目标不存在保持静态示意,新建时必须一并接上——不接,这些入口就一直停在静态示意,读者从它们进不到新原型。**判据**:每接一个入口(新原型自己的与回头接的),独立打开与画廊内各点一次,都到达目标原型;只在某个 mock 状态下出现的入口,先切到该状态再点。
- 防腐烂(manifest 同步规则的姊妹条):删除原型时,同步撤掉其他原型里指向它的 `data-goto` 接线。
- 带既有点击行为的元素接线时留意分工:跳转属性只放在"打开语义"的子元素上(如名称),别盖住行内按钮(隐藏/恢复等)。

## 实现约束

原型里"看起来该好使却不好使"的问题,按类别定位比逐个属性猜快。反复出现的两类:

### 一、元素在 DOM 里,用户却看不见

"存在"到"可见"之间是一串必要条件,逐环查:**存在 → 有非零尺寸 → 未被祖先裁剪 → 未被遮挡 → 在视口内 → 不透明**。断在哪环,修哪环。

其中最隐蔽的是**祖先裁剪**:任何祖先的 `overflow !== visible` 都会切掉超出它的内容,绝对定位元素与伪元素一并计入。所以溢出型元素(提示框、下拉、浮层)出问题时,从它向上遍历到 body,逐级检查裁剪属性与包含块——根因多半在某个为了圆角或滚动而设的容器上,而那个容器与出问题的元素往往不是同一次改动写的。

定位到根因后的取舍只有两条路:**让容器不裁**(把它原本要的效果下放给子元素承担,如圆角交给最外侧子段),或**把溢出元素移出该容器**(挂到更高层级并自行定位)。前者改动小,后者更彻底。

### 二、依赖浏览器原生行为

原生控件的时机与外观不可控——原生 `title` 有约 1s 延迟,原生 `disabled` 元素不触发 hover 事件。需要控制反馈时机或外观时自行实现,不要在原生行为上叠加补丁(补丁通常改不动时机,只能改外观)。

## 实测纪律

原型交付前在浏览器里跑一遍**行为**,断言必须是渲染级:

- **禁止用"属性存在"冒充"用户看得见"**。`getAttribute('data-tip')` 有值不等于提示框画得出来——它可能被祖先的裁剪盒切掉。
- 溢出型元素的检验方式是**几何**:按同款定位造一个真实元素,量它的 rect,逐级祖先检查是否有 `overflow !== visible` 的盒子会切到它。**元素自己的包围盒不构成证据**——被裁掉或被盖住的元素报出的 rect 与正常元素完全一样;能分辨两者的是对它自己中心点做命中测试,确认那一点属于它。
- 有多个使用点时逐个验,不能验一处推断其余。
- **量之前先确认对象还在文档里**(`document.contains(el)`)。脱离文档的元素,`getBoundingClientRect()` 返回**全零而不报错**——重建过 DOM(innerHTML 重写、重新渲染、切换视图)之后,此前取得的引用全部失效,拿它们算出的尺寸与前后差值是凭空捏造的数字,且形态上与真实测量毫无区别。跨越任何一次重渲染的引用一律重新查询,不复用。

## 反模式

- **未经文字选型直接批量生成多个 UI 变体**——生成成本花在用户没选的方向上
- 只换色/换文案冒充"不同方向"
- "写"操作接真实后端(问题是"长什么样",不是"后端通不通")
- 原型代码直接晋升产线
- **需要一致演化的视觉块在多个原型页各复制一份**——改一处漏一处,漏改的第一成因
- **用属性存在/元素数量冒充视觉验证**——被裁掉的提示框、被遮住的元素都能"验证通过"
