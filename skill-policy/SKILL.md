# Skill 写作规范

适用于一切 skill 的新建与修改:SKILL.md、其引用文档、资产内的说明文字。

## 1. 条文必须是命令式的明确语句

- 用「必须 / 不得 / 一律 / 缺任一则不得 X」陈述;主语是执行者的动作,不是现象。
- 每条规则自带可执行判据:读者无需任何额外上下文即可判断"此刻是否违反"。
- 不得用现象描述代替规则:"X 会发生"不是规则,"不得做导致 X 的 Y"才是。

## 2. 实例必须抽象成规则后才准进入

- 促成规则的事故先抽象:写进 skill 的是抽象后的规则,不是事件经过。
- 抽象完成的判据:删去日期、**事发**项目名、当事文件名后,条文仍完整、仍可执行。删的是事故的身份,不是被测技术的名字——后者可能是判据的前提,按 §4 的限定词测试判去留。
- 事件叙事另有归宿:项目复盘文档或 memory;skill 内不得保留"某日发生过某事"式内容。
- 例外必须写成触发条件("仅当 A 且 B 时可 X"),不得写成豁免叙事。**软化词(一般、通常、多半、尽量、原则上)出现在规则里即违反本条**:要么写出例外的触发条件,要么删掉软化词——它把例外藏了起来,读者无从判断自己是不是例外。出现在理由或举例里不算。
- 理由允许保留,但必须是**机制性**的且并入条文本身;不得以括号轶事、事件叙事的形式追加。
- **纯出处标记合法,不算叙事**:「(某日定案)」这类只标何时定的、不讲发生了什么的标注可以留;日期一旦与叙事词同现就成了故事,按上一条删。判据是同一处有没有叙事词,不是有没有日期。
- 支撑技术判断的**实测数据**(量级、比值、行为差异)视为判据的一部分,可以保留;须标注其适用前提,不得叙述取得它的过程。**判据**:能在同一处指出哪句话是前提即合规,不要求特定句式、也不要求单独成句;指不出才算缺前提。

## 3. 选择器(frontmatter)的写法

**`description` 与可选的 `when_to_use` 共同构成选择器,下列条文对两者各自生效——唯「做什么」一项只要求 `description` 写明,`when_to_use` 按其定义只补触发场景。** 写了 `when_to_use` 就必须与 `description` 分工:只补 description 没覆盖的触发场景,不得复述它已经说过的话——两个字段都常驻上下文,复述一遍等于把同一份匹配预算花两次。

- 必须用第三人称陈述;出现「我 / 你」即违反。
- 必须同时写明「做什么」与「何时触发」,触发条件用具体场景词;只写用途不写触发,或用「帮助处理…」式空泛措辞,均视为未完成。
- 不得概括正文的规则、流程或步骤;流程只准在正文里出现。**选择器只负责被选中**:两个字段都常驻上下文,唯一职责是让模型从全部可用 skill 中选中该用的那个;正文在 skill 被触发时必定完整加载,不需要在此预告。写进流程摘要要付两笔代价——一是占掉本该用于匹配的字符、从而稀释触发关键词的密度,二是把执行指导放进一个只在「要不要加载」那一刻起作用的字段。(依据:官方 Agent Skills 文档对 description 的定位与 progressive disclosure 机制。)
- 判据:遮住正文只读选择器,应能回答"什么时候该用它",且推不出"具体怎么做"。

## 4. 自检(两阶段,阶段一收敛后才准进阶段二)

**两种用法,只差范围**:改完自审时,范围由本次改动圈定;**审一份没动过的 skill 时范围由文件圈定**——阶段一过全部条文,阶段二拿每一条问「它在约束什么」取对象。后者不得只盯可疑处抽查:抽查漏掉的正是"两条都没被怀疑、合起来才冲突"的那类。

**阶段一 逐条审措辞,循环到收敛**——对在审范围内的每条条文(不论落在 SKILL.md、引用文档还是资产说明里)逐一问:
- 是命令还是描述?描述 → 改写为命令或删除。
- 删去具体人、事、时、地后还成立吗?不成立 → 抽象未完成,继续提炼。
- 判据能当场执行吗?不能 → 补判据,或整条删除。
- 句中的指代有锚点吗?**判据**:在上文指得出一个名词性词组,把指代词换成它之后句子仍读得通、意思不变。指不出、或代入后意思变了,即为失锚 → 补锚点或改写成直述。
- 泛化或收紧措辞时,原有的限定词丢了吗?**判据**:去掉它后试举一个「符合新表述、但机制不成立」的反例——举得出,它是条件,必须留;举不出才是载体,可以删。**审既有 skill 时本条读作**:条文有没有作出它的机制支撑不了的断言,用同一个反例测试。但**只对承载判据的条文生效**——举例与机制性理由里的陈述即便偏宽,若不改变读者该做的动作,记录即可、不动手;**只有当过宽会让读者少做该做的事时才必须改**。

**这一轮只要动过手,就得重跑整轮**——改动是否带进新问题,不重跑一遍是不知道的。**改了某节的标题、引言或适用范围,该节全部条文都算被改动**,逐条重审。**收敛判据:一整轮下来零发现**,这一阶段才算完成。

**凡可枚举的检查,先全量提取成表,再对着表逐项判**(指代、软化词、条文清单皆然)——通读着找必漏,而漏掉的那条不会自己现身。**表里每一项都要留下结论**,不得只报命中项:只报命中时,「漏看了」与「看过判合规」在产出上无从分辨,而前者恰恰是要防的。

**阶段二 对读**:拿每条条文问「它在约束什么」,答案即受约束对象;把约束同一对象的条文归到一堆(不论同节异节),堆内逐对给出「相容」或「冲突」结论——**每一对都要留结论**,不只报冲突的。判定冲突的,要么改一方,要么补一条写明前提的条文使两者相容。

**冲突的判据**:举得出一个具体情形,使两条**无法同时满足**、或该情形**落不进任何一支**,即为冲突;每种情形都有唯一归宿、只是措辞宽窄不同则为相容。

**同一条规则在两处各写一遍即为缺陷**,不因两处措辞一致就放行——一致只是此刻一致,改了一处另一处不会跟着变,而改的人不会想起去查另一处。**判据**:删掉其中一处,规则是否仍完整可执行?是 → 那处是重述,改成指针或删掉。

**凡判据要求"举得出一个例子",先找它的可枚举结构改成照表核对**:一条给分类、另一条给归属时,把分类的每一项与归属的每一支列成两列对齐,任何一项找不到唯一归宿即为冲突。构造例子依赖灵感,灵感不可复现;对齐表只依赖眼睛,且检出率更高。

**归堆必须可核,不是抽查**:**条文的单位定死**——一个列表项、一个独立段落、表格的一行,各算一条;标题与代码块不算。按此逐条编号列出,每条至少归入一个堆,末了报出「条文总数 / 堆数 / 各堆成员编号」。有条文一个堆都没进,就是还有对象没被取出来。

**先归堆再对读,不要两两穷举全文**:堆通常只有两三条,而穷举会把工作量推到没人跑得完,跑不完的检查等于没有。本阶段的每次改动都退回阶段一过一轮,再重跑本阶段,直到两阶段都零发现。

**顺序是硬的。** 阶段一每次只有一条条文在视野内,**单看每条都正确、合起来才互相锁死的冲突在其中永远不会现身**——跑多少轮都一样,而"已经审过 N 轮"恰恰会盖住它;阶段二必须排在阶段一收敛之后,因为改措辞本身就会造出新的冲突。

**对读范围是整个 skill,不止 SKILL.md**:引用文档、资产内的说明文字(含门禁脚本自己的注释)与 SKILL.md 同属一份规范——SKILL.md 对某个资产的**描述**与该资产自己的说明尤其容易对不上。**判据**:枚举该 skill 管辖的全部文件——目录内的引用文档,**加上正文或引用文档里以路径引用的资产**(资产常放在多个 skill 共用的目录下,按目录枚举必然漏掉它们)——对本次未触碰的每一个也给出「需不需要跟着改」的结论;答不上来的文件,就是没审。

## 门禁

可机械判定的条款由 `scripts/check-skill-policy.mjs` 强制,本地经 pre-push 钩子在推送前跑、CI 在每次落地时复跑。安装 `ln -s ../../scripts/pre-push .git/hooks/pre-push`,每个 clone 一次;为什么用钩子而不是服务端 required check,由该脚本头部注释单独记载,此处不复述。

- **机判项**:选择器两字段的第三人称、触发词、无箭头链式流程摘要;正文的日期事故叙事。
- **覆盖范围分两档**:选择器三项只对 SKILL.md 生效(只有它有 frontmatter),日期事故叙事一项覆盖仓库内全部 `.md`——引用文档同样在内。
- **本地绿不等于待推的 commit 干净**,以 CI 为准:钩子查的是工作树而非 commit,缺口的几种形态见该脚本头部注释。
- **豁免**一律写成谓词并附理由,不得用计数;不再挡任何东西的豁免由脚本自己报死。
- **上列机判项之外的条款一律归 review**——按机判项反推,不再逐条罗列语义条款:枚举会随正文增删而腐烂,而被漏掉的那条不会自己现身。
- **机判项拦的是形态,不是整条规则**:如流程摘要一项,只有箭头链这一形态会红,同一条规则换个写法照样落地,其余形态仍归 review——被列进机判清单不等于该规则已经交出去了。

## 暂缓收编
