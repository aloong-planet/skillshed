# Skill 写作规范

适用于一切 skill 的新建与修改:SKILL.md、其引用文档、资产内的说明文字。

## 1. 条文必须是命令式的明确语句

- 用「必须 / 不得 / 一律 / 缺任一则不得 X」陈述;主语是执行者的动作,不是现象。
- 每条规则自带可执行判据:读者无需任何额外上下文即可判断"此刻是否违反"。
- 不得用现象描述代替规则:"X 会发生"不是规则,"不得做导致 X 的 Y"才是。

## 2. 实例必须抽象成规则后才准进入

- 促成规则的事故先抽象:写进 skill 的是抽象后的规则,不是事件经过。
- 抽象完成的判据:删去日期、项目名、当事文件名后,条文仍完整、仍可执行。
- 事件叙事另有归宿:项目复盘文档或 memory;skill 内不得保留"某日发生过某事"式内容。
- 例外必须写成触发条件("仅当 A 且 B 时可 X"),不得写成豁免叙事。
- 理由允许保留,但必须是**机制性**的且并入条文本身;不得以括号轶事、日期事件的形式追加。
- 支撑技术判断的**实测数据**(量级、比值、行为差异)视为判据的一部分,可以保留;须标注其适用前提,不得叙述取得它的过程。

## 3. description(frontmatter)的写法

- 必须用第三人称陈述;出现「我 / 你」即违反。
- 必须同时写明「做什么」与「何时触发」,触发条件用具体场景词;只写用途不写触发,或用「帮助处理…」式空泛措辞,均视为未完成。
- 不得概括正文的规则、流程或步骤;流程只准在正文里出现。**description 是选择器**:它常驻上下文,唯一职责是让模型从全部可用 skill 中选中该用的那个;正文在 skill 被触发时必定完整加载,不需要在此预告。写进流程摘要要付两笔代价——占掉本该用于匹配的字符、稀释触发关键词的密度,以及把执行指导放进一个只在「要不要加载」那一刻起作用的字段。(依据:官方 Agent Skills 文档对 description 的定位与 progressive disclosure 机制。)
- 判据:遮住正文只读 description,应能回答"什么时候该用它",且推不出"具体怎么做"。

## 4. 每次修改后的自检

对每条新增或改动的条文逐一问:
- 是命令还是描述?描述 → 改写为命令或删除。
- 删去具体人、事、时、地后还成立吗?不成立 → 抽象未完成,继续提炼。
- 判据能当场执行吗?不能 → 补判据,或整条删除。

## 暂缓收编

已调研、尚未并入正文的框架与回溯触发条件见同目录 `deferred-frameworks.md`。命中其触发条件时再按该文收编,收编前先跑 baseline 对照评测。
