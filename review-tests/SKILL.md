# Review 测试——审写成的测试

审的是测试写成之后的样子:被审的是一段改动里新写或改动的测试(下称被审测试),以及它们与既有测试的关系。

- **受交接执行独立审查的**(交接给出检出的绝对路径、分叉点与交出的 commit,要求载入本 skill 与 `/review-code`):必须完整读取 [independent-review.md](../review-code/independent-review.md) 并按其执行,被审测试是该文件「审什么」一节所定范围内新写或改动的测试。
- **单独激活的**:被审测试是用户指定的测试;没有指定的,是从分叉点(`git merge-base HEAD origin/<默认分支>`)到 `HEAD` 的范围内与工作区里新写或改动的测试。发现按 independent-review.md「交回」节第 1、2 项写,不得为没有发现的维度写结论。

## 审查的执行

- **时点**:必须在被审测试写成之后执行。
- **请求数**:当前工具支持一次请求发出多个调用时,结果互不依赖的检查必须放进同一次请求,只有后一项取决于前一项的结果才分开。工具的单次输出有上限(如 Claude Code 的 Bash 约 3 万字符,超出的落盘,读回要多一次请求),预计超过上限的读取必须拆成多个调用,不得拼进一条命令。一条发现所依赖的事实,必须查完再写这条发现。不得为减少请求跳过本节要求的检查,也不得放弃尚未查实的线索。
- **内容**,四项缺一不可:
  1. 维度 1 的全部检查,含测试文件头的缺口注明。
  2. 维度 3 的全部检查,其中变异检验按该维度「变异检验按能力声明」一条判定做不做。
  3. 维度 4 的全部检查,含运行时核对:资源的加载或构建有可观测输出(日志、计时、计数)时,必须从一次运行了全部被审测试的运行里数出每份昂贵资源的实际加载或构建次数,按 `/tdd`「测试资源复用」节判它是否只加载了应有的次数。该次运行只跑了部分用例的,没跑到的用例清空资源引起的重新加载在计数里看不到,必须按该节「执行顺序取自收集结果」一条核对,不得以该次计数代替。
  4. 维度 2 的全部检查。
- **可枚举的检查先全量列表再逐项判**(用例清单、fixture 清单、资源清单、形态清单),通读着找必漏;列表只用于判定,不写成文件。

## 发现的范围

维度 4 与维度 2「用例落层」「用例放置」「重复的用例」三条的发现按其所指 `/tdd` 各节的判据报;其余发现必须属于下列三类之一,不属于的不得报——只报会改变结论的问题,不在审查里发散:

- **缺陷**:被测行为与 spec 不符,或测试假通过、掩盖了这样的不符。
- **会漏掉的回归**:spec 规定的行为,或实现中保障某条 spec 行为的细节(删改它时本应有测试变红),没有被驱动;只在默认取值或想象的数据形态下测过、断言没有对照 spec 原文的,都算。
- **不实的证据**:测试文件头的缺口注明、测试名或注释所声称的覆盖与证据,其陈述与事实不符,或证据撑不起它写出的结论。

**只报真问题**:「缺陷」与「会漏掉的回归」的每条发现,必须写明失败情景:具体的用户操作、数据形态或对被测代码的一处改动,它造成的错误结果,以及现有的测试为什么不会因此变红。「不实的证据」的每条发现,必须写明哪条陈述与哪项事实不符,以及哪个结论因此不成立或缺了依据。写不出的不得报,不影响任何结论的记账(格式、编号、措辞)与不指向缺陷的观察都在此列;情景要靠公开路径不可达的状态才成立的,同样不得报。

**不做过度防范**:问题出现的前提要求改动下列任一项的,不得报——项目已锁定版本的依赖、测试框架或测试客户端自身的行为、运行环境(操作系统、解释器、硬件)。被测代码的改动带来的问题不属于本条,按前三类判。

## 维度 1:覆盖是否完整

必须对照 `/tdd`「覆盖来源」节的覆盖清单逐项核对,不按 spec 的「失败模式与边界」节逐条核对;漏的按「发现的范围」的「会漏掉的回归」报。
**测不到的**:必须按 `/tdd`「覆盖来源」节「测不到的」一条核对测试文件头的缺口注明。

**声称覆盖与驱动输入**:必须按 `/tdd`「覆盖来源」节「声称覆盖的边界必须真被驱动」一条逐个用例核对。

**fixture 不得与 spec 同源**:读外部数据的用例,必须按 `/tdd`「覆盖来源」节「读外部数据的用例」一条与「fixture 形态的判据」一条核对每份 fixture 的形态来源。

## 维度 2:case 设计是否合理

**基础检查**:必须按 `/tdd`「什么是好测试」节「基础要求」一条逐个用例核对三条。

**会掩盖缺陷的写法**:必须按 `/tdd`「反模式」节「实现耦合」一条中的旁路验证,与「Seam——测试站在哪」节「可达状态规则」一条核对;命中的,必须按「发现的范围」的「缺陷」或「会漏掉的回归」报。

**用例落层**:被审测试里的用例,必须按 `/tdd`「用例落在哪一层」节核对落层,不符该节任一条的即为发现。

**用例放置**:被审测试里新写、改动或移动的穿过整个应用的用例及其用到的 helper,必须按 `/tdd`「用例与 helper 放在哪里」节对照写成的测试核对,不符该节任一条的即为发现。同一 helper 是否只有一份定义,必须检索全部测试文件得出。

**重复的用例**:被审测试里的每个用例(下称被审用例)都必须按 `/tdd`「不写重复的用例」节核对,不符该节任一条的即为发现。比较对象中经同一 seam 的既有用例必须检索全部测试得出。「只差取值的合并」一条比函数体;「红的情形已被覆盖的不写」一条里会红的情形取维度 3 的作答,比较对象不运行,对照其断言与被测代码作答。发现必须写明合并或删除哪个用例、由哪个用例顶替它。

## 维度 3:有没有假通过

必须按 `/tdd`「反模式」节「假通过」一条,对每个测试作答「它在什么情况下会红」,并对照该条的形态清单逐项判。

**变异检验按能力声明**:必须先按全局指令「项目能力声明」节读项目能力 `mutation-testing`。启用的,必须完整读取 [变异检验](./mutation-testing.md) 并执行;未启用的,不做变异检验,按全局指令写明跳过,上一条的作答必须对照被测代码与期望值来源逐个给出。

**`/tdd` 那份形态清单按单元测试写成。** 同一个判据("它在什么情况下会红")同样适用于界面/浏览器断言、关卡(CI 门禁、告警)与命令行验收,而那些地方常常不被当作"需要设计的断言"。本次改动若引入了这几类验证,按 [review-code/false-greens.md](../review-code/false-greens.md) 的形态清单一并审(清单只在那一处维护,此处不复述)。

## 维度 4:资源是否复用

必须按 `/tdd`「测试资源复用」节核对被审测试用到的每份昂贵资源,不符该节任一条的即为发现;运行时核对按「审查的执行」节「内容」第 3 项执行。
