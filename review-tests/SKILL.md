# Review 测试——写测试前审设计,写成后复核

使用本文件的文档同步规则时，必须完整读取 [文档同步与记录维护](../implement/document-sync.md)。

## 审查时点与产出

测试审查必须分两个时点执行:先做设计审查,再做实现后复核。按 `/implement` 编排且其判定某时点跳过的(设计审查见其第 4 步第 4 项,实现后复核见其 [post-implementation-check.md](../implement/post-implementation-check.md)「首轮判定」条),不执行该时点。

### 设计审查

- **时点**:必须在写或改第一个测试之前执行;按 `/implement` 编排时即第 4 步的「用例设计审查」。单独激活且测试已写成的,按「单独激活与产出」节办。
- **对象**:用例设计表——每个计划新写或改动的测试一行,必须写明:覆盖的 spec 条目;seam;把执行带进目标分支的输入;断言对象及期望值来源;fixture 的形态来源;所用的昂贵资源(定义见维度 4)及其提供方式。缺任一项的行即为未设计完成,补齐后才可审。
- **内容**:必须做维度 1、维度 2、维度 4 的全部检查,以及维度 3 中凭设计即可判定的三项——恒真断言(计划的数据量能否撑满阈值)、同义反复(期望值来源)、守旧路径(断言对象是否活路径)。
- **增量**:`/tdd` 循环中新增、删除或改变某个用例的设计时,必须先改用例设计表并按本节审过改动的行,再写或改该测试。测试必须仍按 `/tdd` 一次一纵切地写。

### 实现后复核

- **时点**:必须在测试写成、全量验证网关的复核前运行通过之后执行;按 `/implement` 编排时即第 6 步。增量复核(见本节「增量复核」条)不得以修复后未重跑全量验证网关为由推迟,修复后的运行证据按「运行证据」条取用。
- **请求数**:当前工具支持一次请求发出多个调用时,结果互不依赖的检查必须放进同一次请求,只有后一项取决于前一项的结果才分开。工具的单次输出有上限(如 Claude Code 的 Bash 约 3 万字符,超出的落盘,读回要多一次请求),预计超过上限的读取必须拆成多个调用,不得拼进一条命令。测试审查记录(路径见「记录归属」节)里的陈述所依赖的事实,必须查完再写记录。不得为减少请求跳过本节要求的检查,也不得放弃尚未查实的线索。
- **内容**,四项缺一不可:
  1. 逐用例核对写成的测试与用例设计表一致(seam、驱动输入、断言对象、期望值来源、fixture、资源取法),并按维度 1 核对测试文件头的缺口注明;不一致时改测试或改用例设计表,改表的必须按设计审查重审该行。
  2. 维度 3 的全部检查,其中变异检验按该维度「变异检验按能力声明」一条判定做不做。
  3. 维度 4 的运行时核对:资源的加载或构建有可观测输出(日志、计时、计数)时,必须从一次运行了全部被复核测试的运行里数出每份昂贵资源的实际加载或构建次数,与用例设计表对照;按 `/implement` 第 6 步的交接执行时,取数来源见「运行证据」条。该次运行只跑了部分用例的,没跑到的用例清空资源引起的重新加载在计数里看不到,必须按维度 4「执行顺序取自收集结果」一条核对,不得以该次计数代替。
  4. 维度 2「重复的用例」一节的全部核对。
- **运行证据**(按 `/implement` 第 6 步的交接执行时适用):不得自行重跑全量验证网关的复核前运行或全量。首轮复核的运行结果必须取自交接的复核前运行日志,增量复核时下方「增量复核」条所列对象的运行结果取自交接的定向验证日志;日志缺 [full-verification-gate.md](../implement/full-verification-gate.md) 对日志要求的任一项,或所记版本与交接的 commit 范围对不上的,必须记为发现交回,不得自行重跑补证。复核需要实测的(如回答维度 3「它在什么情况下会红」),只得运行本次复核对象中的测试:首轮复核为本次改动新写或改动的测试,增量复核为下方「增量复核」条列出的对象。
- **增量复核**:交接给出修复的 commit 范围时,上述四项内容必须只对以下对象执行:该范围内改动的测试;依赖该范围内改动的测试辅助代码(共享 setup、fixture、helper)的测试,按导入关系检索得出;用例设计表中该范围内改动的行。检索命令与结果必须写进测试审查记录;范围之外的各维度结论沿用上一轮,记录里注明沿用的是哪一轮。读测试审查记录时,必须按节标题定位,只读用例设计表(含其增量)与上一轮的结论、发现及其处置,不得读其余各节:其余各节是更早版本上的结论,增量复核沿用而不重判;已用的发现编号用检索取得。增量复核时第 3 项改从交接的定向验证日志里数,不用复核前运行日志。「记录归属」要求的文档同步核对,变化的事实只从该范围内的改动及其定向验证结果确定,核对的文件只限「记录归属」所列的三项,其中测试审查记录只限上述读取的内容。
- **交回**(按 `/implement` 第 6 步的交接执行时适用):复核结束时最终交回的内容只得包含本轮结论(有无发现)、测试审查记录的路径,以及本轮每条发现的编号与一句话标题;发现的正文、各维度结论、证据与复核过程只写进记录,不得写进交回——交回会常驻主 agent 的上下文,写进去就是记录的第二份副本。

### 单独激活与产出

单独激活且测试已写成时,必须先从写成的测试逆向填出用例设计表,再依次做设计审查与实现后复核的全部检查。

**每个时点的产出都必须按维度分列,本时点审查的每个维度都要留结论**,不得只报有发现的维度:只报命中时,「这个维度没查」与「查过判无发现」在产出上无从分辨,而前者恰是要防的。可枚举的检查(用例清单、fixture 清单、资源清单、形态清单)先全量列表再逐项判,通读着找必漏。

**每个时点的发现必须集中列在该时点一节下的「发现」小节**:逐条编号,同一份测试审查记录里不得有两条发现用同一个编号;本时点没有发现的,该小节写明无发现。

## 发现的范围

维度 4 的发现按该维度的判据报;其余发现必须属于下列四类之一,不属于的不得报、不得处置——每一轮只处理这四类问题,不在审查里发散:

- **缺陷**:被测行为与 spec 不符,或测试假通过、掩盖了这样的不符。
- **会漏掉的回归**:spec 规定的行为,或实现中保障某条 spec 行为的细节(删改它时本应有测试变红),没有被驱动;只在默认取值或想象的数据形态下测过、断言没有对照 spec 原文的,都算。
- **不实的记录与证据**:用例设计表、测试文件头、测试审查记录与证据,其陈述与事实不符,或证据撑不起它写出的结论。必须先把陈述改到与证据一致;仅当该结论是前两类所需时,改为加强证据。
- **多余的测试**:用例命中维度 2「重复的用例」的判据。报出时必须写明合并或删除哪个用例、由哪个用例顶替它。

**不考虑防过度防范**:问题出现的前提要求改动下列任一项的,不得报——项目已锁定版本的依赖、测试框架或测试客户端自身的行为、运行环境(操作系统、解释器、硬件)。被测代码的改动带来的问题不属于本条,按上列各类判。不影响任何结论的记账(格式、编号、措辞),同样不得报。

## 维度 1:覆盖是否完整

对照 spec 的「失败模式与边界」节逐条核销:边界值、错误/失败路径、异步 race、本次改动触碰的回归点、空/异常输入。漏的必须补进用例设计表,按设计审查审过再写(仍走 `/tdd` 循环)。
**测不到的**(无行为触发点的接线、需真实环境的路径):在测试文件头**注明缺口与补测条件**——诚实的缺口好过造假的绿;不许用私测内部状态凑覆盖率。

**用例声称覆盖的边界,与它实际驱动的输入必须对得上**:用例名或注释说"覆盖 X 态",而构造的数据根本进不了 X 分支时,这条覆盖在清单上算已完成、实际为零。判据:指出该用例里哪个输入把执行带进了 X——指不出就是覆盖记账不实。

### fixture 不得与 spec 同源

覆盖清单来自 spec,测试数据若也由"我以为数据长什么样"构造,**两者同源**——spec 的盲点会被 fixture 原样继承,测试再多也只是把同一个想象验证多遍(多层防御但相关性失效)。

凡功能读取**外部/他方产生的数据**(用户文档、agent 生成物、第三方配置、外部 API),fixture **至少一例取自真实样本的形态**:去真实数据目录看一眼实际长什么样,照着造(可脱敏、可裁剪,但结构与特征要保留)。真实样本是唯一与 spec 独立的样本源。

**判据**:对每份 fixture 问"它的形态是我想出来的,还是我看过真实数据后照着造的?"——前者与 spec 同源,不构成独立验证。
**核对的是形态而非数值**:真实数据里有而我没想到的**结构特征**(嵌套、引用、链接、混合类型、异常但合法的写法)才是盲点所在;字段值随便造无妨。

## 维度 2:case 设计是否合理

基础检查:是否孤立可复现;是否真的驱动了目标行为(而非只调用一下不断言效果);断言是否针对正确的对象。

**会掩盖缺陷的写法**(命中的,必须按「发现的范围」的「缺陷」或「会漏掉的回归」报):

- 绕过公开接口旁路验证(读文件/查库/读内部字段,代替经接口读回):经接口读回的结果错了,测试照样通过。
- 构造公开路径不可达的状态(含 cast 绕过可见性、直写内部状态做 setup 造出的状态):测的是不存在的情形,公开路径上的错误不会被测到。

### 重复的用例

只报缺失的审查,每一轮都只会让用例变多,所以每个用例都必须核对重复。必须对本时点审查范围内的每个用例(下称被审用例,范围见「审查时点与产出」节)依次执行下列各项;命中的,必须按「发现的范围」的「多余的测试」报。每个被审用例的比较对象与结论(命中哪一项或未命中)、所用的检索命令与结果都必须写进测试审查记录。

1. **取比较对象**:用例设计表里覆盖同一 spec 条目的其他行,加上检索全部测试得到的、调用被审用例所在 seam 公开接口的既有用例。
2. **只差取值**:被审用例与某个比较对象只有字面量或传入的取值不同(实现后复核比函数体,设计审查比用例设计表的 seam、驱动输入与断言对象)的,即命中,处置必须是合并成一个参数化用例。测试框架不支持参数化的,跳过本项。
3. **红的情形被包含**:被审用例与每个比较对象,两个方向各判一次:甲会红的每种情形都指得出乙里同样会红的断言的,即甲命中,处置必须是删除甲。会红的情形,实现后复核取维度 3 的作答,设计审查由驱动输入与断言对象推出;比较对象不运行,对照其断言与被测代码作答。下列两种情形不算命中:乙的运行条件比甲苛刻(只在 CI、需要真实账户或需要独占桌面才运行),它的红来得更晚;spec 的 Testing Decisions 要求甲的行为在甲的 seam 上验证,而乙不在这个 seam 上。两个用例互相命中时只删一个:保留运行条件宽松的,运行条件相同时保留 seam 较高的,seam 也相同时保留其中一个。

## 维度 3:有没有假通过

形态清单(样例见 tdd/tests.md):

- **恒真断言**:数据量撑不满阈值(5 条数据断 ≤200)、断言恒成立、`toBeTruthy` 断恒真值
- **同义反复**:期望值与实现同算法重算 / 期望=输入对象别名 / 断言 import 进来的同一常量
- **守旧路径**:断言对象是废弃常量/已被取代的行为(grep 生产代码核对是否活路径)
- **条件跳过静默绿**:环境不满足时 `return` 而非显式 `skip`,报告里绿得心安理得
- **断言可能不执行**:async 未 await、断言在可能不触发的 callback 里、空集合循环体零断言仍绿(先断言集合非空)

**检验法:对每个测试问"它在什么情况下会红"——答不出来的就是嫌疑假通过。**

**变异检验按能力声明**:必须先按全局指令「项目能力声明」节读项目能力 `mutation-testing`。启用的,必须完整读取 [变异检验](./mutation-testing.md) 并执行;未启用的,不做变异检验,按全局指令写明跳过,每个测试「在什么情况下会红」仍必须按上一条检验法,对照被测代码与期望值来源逐个作答。

识别出的假信号按诚实原则处理:如实说明,不把假通过当真,不硬改代码去凑测试。

**上面这份清单只覆盖单元测试。** 同一个判据("它在什么情况下会红")同样适用于界面/浏览器断言、关卡(CI 门禁、告警)与命令行验收,而那些地方常常不被当作"需要设计的断言"。本次改动若引入了这几类验证,按 [review-code/false-greens.md](../review-code/false-greens.md) 的形态清单一并审(清单只在那一处维护,此处不复述)。

## 维度 4:资源是否复用

**昂贵资源**:一次加载或构建耗时 1 秒以上的测试资源,如模型、建好的数据库与索引、编译产物、替身服务进程、大体积 fixture;耗时不确定的,必须先实测一次再判。

- **只加载一次**:内容由同一组参数决定的同一份昂贵资源,必须在测试框架允许共享的最大范围内只加载或构建一次:框架能跨文件共享的(如 pytest 的 session fixture,或写到磁盘、由 Jest/Vitest 的 globalSetup 构建的模板),按整个测试进程共享;框架按文件隔离内存对象的,按文件共享(如 beforeAll)。不得在每个用例里重新加载或构建;例外只有本节的「被测构建」与「独立标识」两条。
- **可写资源用复制品**:用例会改动的资源(写入的库、目录、文件,或会改其属性、配置的对象)必须从只建一次的模板复制一份给该用例,不得为它从头重建(「独立标识」一条的情形除外),也不得改共享的那份;不能确认是否会被写的,按会被写处理。
- **被测构建**:被测行为本身就是某个加载或构建步骤时,用例必须执行该步骤;它的前置状态非空的,必须从模板复制,不得为准备前置状态重跑前面的构建。
- **独立标识**:复制品与模板共享内部标识(ID、版本号、创建时间);断言依赖两份资源各自独立构建、标识不同的用例,必须各自构建,不得用复制品。
- 被测代码在内部自行加载昂贵资源、外部无法传入已加载实例的,即为缺 seam:必须在被测代码侧补注入或进程内复用,复用的键必须覆盖决定资源内容的全部参数,否则参数不同的调用会拿到同一份资源;补注入的做法按 `/tdd` 的「缺 seam 是设计信号」。不得以在测试里替换项目自己的加载函数代替补 seam;这样做的,按缺 seam 报。补 seam 会改变 spec 已定义的行为时,必须先经用户确认并回写 spec,再写依赖它的测试。
- 设计前必须检索本仓库测试中已有的共享 setup 与复制模板;已有同类资源的共享或复制做法的,必须沿用,不沿用的必须在用例设计表写明理由。
- **执行顺序取自收集结果**:进程内共享的昂贵资源(进程级缓存、session 范围 fixture 的产物)会被某个用例清空或释放时,其余用例对它是复用还是重新加载取决于执行顺序。用例设计表中的用例会这样清掉资源的,必须在该行列出它清掉的每份资源(按清空或释放调用的实现逐项列出);用到的资源会被别的用例清掉的(检索全部测试里清空或释放该资源的调用得出),必须在该行写明是哪些用例。两种情形都必须按测试框架实际收集出的顺序(如 pytest 的 `--collect-only`;收集只导入测试代码并列出用例,不执行任何用例)定出清掉资源的用例与用到资源的用例的先后,据此回答下方「判据」一条的加载或构建次数;已写成的用例,顺序只得取自收集结果,由框架源码、文档、注释、文件名或标记约定推出的顺序一律不算——测试框架可按 fixture 参数等重排用例,推出的顺序与实际可以不同。尚未写成、收集不到的用例,必须在用例设计表写明设计所依据的位置,写成后、运行之前必须收集一次核对;不符的,必须按设计审查的「增量」条改表重审。
- **判据**:对用例设计表里每份昂贵资源,说得出它在一个测试进程里加载或构建几次、由哪个共享 setup 提供;说不出,或次数随用例数增长,即为发现。

## 记录归属

- 维度名、时点名、「用例设计表」与「发现」写进记录时，必须按 [产物固定名称](../repo-scaffold/artifact-names/review-tests.md) 书写。

- 必须完整读取 [Ticket 产物与文档同步清单](../to-tickets/ticket-artifacts.md)，按有票、无票或旧票接续入口确定测试审查路径并写入本轮各维度报告，注明日期、实现版本与范围；有关联票时必须注明票身份。两个时点必须写进同一份测试审查记录，各成一节；设计审查的实现版本必须写实现开始时所依据的 commit。
- 本 skill 的文档同步核对只限三项：用例设计表、测试文件头、测试审查记录。测试结论的后续维护及覆盖缺口、假通过、重复用例、资源复用发现在这三项里产生的同步义务，必须按 [文档同步与记录维护](../implement/document-sync.md) 处理，其中开头“定位同步材料前”那一条所定的核对范围由本条的三项代替；不得将补测通过等同于相关状态已同步。其余文档（需求覆盖清单、施工记录、spec、features 等）里与测试有关的陈述不在本 skill 核对之内，由 `/implement` 第 7 步与 `/features-catalog` 的文档收口负责，不得据以报发现；交接的运行日志不在此列，按「实现后复核」的「运行证据」条核对。
