# Review 测试——写测试前审设计,写成后复核

使用本文件的文档同步规则时，必须完整读取 [文档同步与记录维护](../implement/document-sync.md)。

## 审查时点与产出

测试审查必须分两个时点执行:先做设计审查,再做实现后复核。

### 设计审查

- **时点**:必须在写或改第一个测试之前执行。单独激活且测试已写成的,按「单独激活与产出」节办。
- **对象**:用例设计表——每个计划新写或改动的测试一行,必须写明:覆盖的 spec 条目;seam;把执行带进目标分支的输入;断言对象及期望值来源;fixture 的形态来源;所用的昂贵资源(定义见 `/tdd`「测试资源复用」节)、其提供方式(不沿用既有共享做法的写明理由)与在一个测试进程里的加载或构建次数;穿过整个应用而断言规则的用例,还要写明 `/tdd`「用例落在哪一层」节「判据」一条要说出的那处接线。缺任一项的行即为未设计完成,补齐后才可审。
- **内容**:必须做维度 1、维度 2、维度 4 的全部检查,以及维度 3 中凭设计即可判定的三种形态(定义见 `/tdd`「反模式」节「假通过」一条)——恒真断言(计划的数据量能否撑满阈值)、同义反复(期望值来源)、守旧路径(断言对象是否活路径)。
- **增量**:`/tdd` 循环中新增、删除或改变某个用例的设计时,必须先改用例设计表并按本节审过改动的行,再写或改该测试。测试必须仍按 `/tdd` 一次一纵切地写;用例设计表只列计划、不写测试代码,不属 `/tdd` 所说的横切。

### 实现后复核

- **时点**:必须在测试写成、且有一次运行了全部被复核测试并全部通过的运行之后执行。
- **请求数**:当前工具支持一次请求发出多个调用时,结果互不依赖的检查必须放进同一次请求,只有后一项取决于前一项的结果才分开。工具的单次输出有上限(如 Claude Code 的 Bash 约 3 万字符,超出的落盘,读回要多一次请求),预计超过上限的读取必须拆成多个调用,不得拼进一条命令。测试审查记录(路径见「记录归属」节)里的陈述所依赖的事实,必须查完再写记录。不得为减少请求跳过本节要求的检查,也不得放弃尚未查实的线索。
- **内容**,三项缺一不可:
  1. 逐用例核对写成的测试与用例设计表一致(seam、驱动输入、断言对象、期望值来源、fixture、资源取法),并按维度 1 核对测试文件头的缺口注明;不一致时改测试或改用例设计表,改表的必须按设计审查重审该行。
  2. 维度 3 的全部检查,其中变异检验按该维度「变异检验按能力声明」一条判定做不做。
  3. 维度 4 的运行时核对:资源的加载或构建有可观测输出(日志、计时、计数)时,必须从一次运行了全部被复核测试的运行里数出每份昂贵资源的实际加载或构建次数,与用例设计表对照;受交接执行时,取数来源见「运行证据」条。该次运行只跑了部分用例的,没跑到的用例清空资源引起的重新加载在计数里看不到,必须按 `/tdd`「测试资源复用」节「执行顺序取自收集结果」一条核对,不得以该次计数代替。
- **不改被复核的内容**(受交接执行时适用):不得改动代码、测试与测试读取的数据,复核要求的修改必须记为发现交回;变异检验的临时改动除外,按[变异检验](./mutation-testing.md)还原。
- **运行证据**(受交接执行时适用):不得自行重跑交接日志所记的运行,也不得自行跑全量。首轮复核的运行结果必须取自交接的复核前运行日志,增量复核时下方「增量复核」条所列对象的运行结果取自交接的定向验证日志;日志缺 [full-verification-gate.md](../implement/full-verification-gate.md) 对日志要求的任一项,或所记版本与交接的 commit 范围对不上的,必须记为发现交回,不得自行重跑补证。复核需要实测的(如回答维度 3「它在什么情况下会红」),只得运行本次复核对象中的测试:首轮复核为本次改动新写或改动的测试,增量复核为下方「增量复核」条列出的对象。
- **增量复核**:交接给出修复的 commit 范围时,上述三项内容必须只对以下对象执行:该范围内改动的测试;依赖该范围内改动的测试辅助代码(共享 setup、fixture、helper)的测试,按导入关系检索得出;用例设计表中该范围内改动的行。检索命令与结果必须写进测试审查记录;范围之外的各维度结论沿用上一轮,记录里注明沿用的是哪一轮。读测试审查记录时,必须按节标题定位,只读用例设计表(含其增量)与上一轮的结论、发现及其处置,不得读其余各节:其余各节是更早版本上的结论,增量复核沿用而不重判;已用的发现编号用检索取得。增量复核时第 3 项改从交接的定向验证日志里数,不用复核前运行日志。「记录归属」要求的文档同步核对,变化的事实只从该范围内的改动及其定向验证结果确定,核对的文件只限「记录归属」所列的三项,其中测试审查记录只限上述读取的内容。
- **交回**(受交接执行时适用):复核结束时最终交回的内容只得包含本轮结论(有无发现)、测试审查记录的路径,以及本轮每条发现的编号与一句话标题;发现的正文、各维度结论、证据与复核过程只写进记录,不得写进交回——交回会常驻主 agent 的上下文,写进去就是记录的第二份副本。

### 单独激活与产出

单独激活且测试已写成时,必须先从写成的测试逆向填出用例设计表,再依次做设计审查与实现后复核的全部检查。

**每个时点的产出都必须按维度分列,本时点审查的每个维度都要留结论**,不得只报有发现的维度:只报命中时,「这个维度没查」与「查过判无发现」在产出上无从分辨,而前者恰是要防的。可枚举的检查(用例清单、fixture 清单、资源清单、形态清单)先全量列表再逐项判,通读着找必漏。

**每个时点的发现必须集中列在该时点一节下的「发现」小节**:逐条编号,同一份测试审查记录里不得有两条发现用同一个编号;本时点没有发现的,该小节写明无发现。

## 发现的范围

维度 4 与维度 2「用例落层」一条的发现按其所指 `/tdd` 各节的判据报;其余发现必须属于下列三类之一,不属于的不得报、不得处置——每一轮只处理会改变结论的问题,不在审查里发散:

- **缺陷**:被测行为与 spec 不符,或测试假通过、掩盖了这样的不符。
- **会漏掉的回归**:spec 规定的行为,或实现中保障某条 spec 行为的细节(删改它时本应有测试变红),没有被驱动;只在默认取值或想象的数据形态下测过、断言没有对照 spec 原文的,都算。
- **不实的记录与证据**:用例设计表、测试文件头、测试审查记录与证据,其陈述与事实不符,或证据撑不起它写出的结论。必须先把陈述改到与证据一致;仅当该结论是前两类所需时,改为加强证据。

**只报真问题**:「缺陷」与「会漏掉的回归」的每条发现,必须写明失败情景:具体的用户操作、数据形态或对被测代码的一处改动,它造成的错误结果,以及现有或用例设计表计划的测试为什么不会因此变红。「不实的记录与证据」的每条发现,必须写明哪条陈述与哪项事实不符,以及哪个结论因此不成立或缺了依据。写不出的不得报,不影响任何结论的记账(格式、编号、措辞)与不指向缺陷的观察都在此列;情景要靠公开路径不可达的状态才成立的,同样不得报。

**不做过度防范**:问题出现的前提要求改动下列任一项的,不得报——项目已锁定版本的依赖、测试框架或测试客户端自身的行为、运行环境(操作系统、解释器、硬件)。被测代码的改动带来的问题不属于本条,按前三类判。

## 维度 1:覆盖是否完整

必须对照 spec 的「失败模式与边界」节逐条核销。设计审查时,漏的必须补进用例设计表并按设计审查审过;实现后复核时,漏的按「发现的范围」的「会漏掉的回归」报。
**测不到的**:必须按 `/tdd`「覆盖来源」节「测不到的」一条核对测试文件头的缺口注明。

**声称覆盖与驱动输入**:必须按 `/tdd`「覆盖来源」节「声称覆盖的边界必须真被驱动」一条逐个用例核对。

**fixture 不得与 spec 同源**:读外部数据的用例,必须按 `/tdd`「覆盖来源」节「读外部数据的用例」一条与「fixture 形态的判据」一条核对每份 fixture 的形态来源。

## 维度 2:case 设计是否合理

**基础检查**:必须按 `/tdd`「什么是好测试」节「基础要求」一条逐个用例核对三条。

**会掩盖缺陷的写法**:必须按 `/tdd`「反模式」节「实现耦合」一条中的旁路验证,与「Seam——测试站在哪」节「可达状态规则」一条核对;命中的,必须按「发现的范围」的「缺陷」或「会漏掉的回归」报。

**用例落层**:计划新写或改动的用例,必须按 `/tdd`「用例落在哪一层」节核对落层,不符该节任一条的即为发现。

## 维度 3:有没有假通过

必须按 `/tdd`「反模式」节「假通过」一条,对每个测试作答「它在什么情况下会红」,并对照该条的形态清单逐项判。

**变异检验按能力声明**:必须先按全局指令「项目能力声明」节读项目能力 `mutation-testing`。启用的,必须完整读取 [变异检验](./mutation-testing.md) 并执行;未启用的,不做变异检验,按全局指令写明跳过,上一条的作答必须对照被测代码与期望值来源逐个给出。

**`/tdd` 那份形态清单按单元测试写成。** 同一个判据("它在什么情况下会红")同样适用于界面/浏览器断言、关卡(CI 门禁、告警)与命令行验收,而那些地方常常不被当作"需要设计的断言"。本次改动若引入了这几类验证,按 [review-code/false-greens.md](../review-code/false-greens.md) 的形态清单一并审(清单只在那一处维护,此处不复述)。

## 维度 4:资源是否复用

设计审查时,必须按 `/tdd`「测试资源复用」节核对用例设计表里的每份昂贵资源,不符该节任一条的即为发现;「执行顺序取自收集结果」一条除外——用例此时尚未写成、收集不到。实现后复核的运行时核对(含该条)按「实现后复核」节「内容」第 3 项执行。

## 记录归属

- 维度名、时点名、「用例设计表」与「发现」写进记录时，必须按 [产物固定名称](../repo-scaffold/artifact-names/review-tests.md) 书写。

- 必须完整读取 [Ticket 产物与文档同步清单](../to-tickets/ticket-artifacts.md)，按有票、无票或旧票接续入口确定测试审查路径，本轮各维度报告的抬头按该文件「身份与路径」节写。两个时点必须写进同一份测试审查记录，各成一节；设计审查的实现版本必须写实现开始时所依据的 commit。
- 本 skill 的文档同步核对只限三项：用例设计表、测试文件头、测试审查记录。测试结论的后续维护及覆盖缺口、假通过、资源复用发现在这三项里产生的同步义务，必须按 [文档同步与记录维护](../implement/document-sync.md) 处理，其中开头“定位同步材料前”那一条所定的核对范围由本条的三项代替；不得将补测通过等同于相关状态已同步。其余文档（需求覆盖清单、施工记录、spec、features 等）里与测试有关的陈述不在本 skill 核对之内，不得据以报发现；交接的运行日志不在此列，按「实现后复核」的「运行证据」条核对。
