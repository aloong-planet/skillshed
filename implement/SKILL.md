> Fork 自 mattpocock/skills(2026-07 快照)。修改:扩为第 4-7 步编排器(分支纪律、验证网关、双 review 门、Spec 终检、拆解归档)。

实施 spec 或 tickets 描述的工作。编码全程遵循 AGENTS.md 的**窄而完整**原则(正文只在 AGENTS.md,此处不复制)。开始前读 CONTEXT.md 与相关 ADR。

仅收到既有交付的验收反馈且没有新增实现要求时，必须直接执行“验收反馈回写”，不得重新拉分支或重跑实现步骤；反馈包含缺陷或新范围时，必须先定位受影响要求并按现有需求变更与验证流程处理。

## 验收时点与阶段门禁

每次阶段核销前，必须为本轮每个验收项记录执行时点，并按以下顺序判定；不得用“产品验收、技术前提、流程验收”的分类代替时点判定：

1. 当前有效验证结果为失败，或所需实现缺失、部分实现的项，必须先修复并复验，不得改记为后置验收以越过门禁。
2. 尚未执行，且本流程明确安排在后续第 5–8 步、用户验收或合并事件中核对、执行时点尚未到达的流程项，必须保留为未验证，并在对应步骤或事件发生时核销。
3. 尚未执行、用户已明确确认在交付后验证且约定执行时点尚未到达的产品或技术项，必须记录确认依据、负责验证者、触发条件、验证方法及待补证据位置，保留为未验证。缺少任一记录时不得按此分支放行；不得以环境不可用或时间不足自行延期。
4. 不属于前述后置安排的项，必须在当前核销阶段取得符合保障机制的通过证据；失败、漏测或阻断未解决时不得进入下一阶段。

必须在交付说明中列出按第 2、3 项保留的后置验收及其安排，不得将允许继续流程写成验收通过；本节不豁免本 skill 的验证网关、交付凭据或 `/features-catalog` 的全 feature 最终收口判定。存在未验证项时不得将票标为最终验收完成。

## 第 4 步:实现

0. **准入检查(界面)**:待实施的改动若含用户可见的界面变化——**含改色、调间距这类视觉微调**——逐条列出界面点,确认每条都有**已确认的原型**覆盖。缺原型、或原型与当前需求不一致 → **停下先跑 `/prototype` 并等用户确认**,不在实现阶段边写边定界面。
   例外清单与跳过条件以 `/to-spec` 的原型门为准,此处不复述——**修 UI bug 虽然不走 to-spec 那条流程,例外口径照样照它**。这道闸是那种改动唯一的门,不可跳过。
   **本闸按改动逐次生效,不是阶段一次性**:实现期中途新到的需求(用户增量要求、review 引出的 UI 变化)同样先过此闸——**判据**:每次准备动 UI 代码前自问"这个界面点的原型改了吗 / 例外理由声明了吗",两者皆无就先回原型——**"这次很小"不是例外**,例外只有 `/to-spec` 列的那几类。
   过闸后、动任何界面代码前,必须先调 `/ui-design`(Skill 工具)载入界面硬性规范并全程遵循。
1. **分支**:从最新 master 拉 feature 分支(如 `feat/xxx`)——**先拉取远端再开分支,开完核对本分支相对 master 的提交列表为空**,否则会静默带上别人或上一轮未合并的改动;所有改动在分支上,不直接改 master。
2. **tasklist 持久化**(TaskCreate/TaskUpdate);多步任务给出带验证检查点的计划,循环到验证通过。**第 5、6 步必须各建独立 task,不得并入其他 task**。
3. **目标驱动**:先定可验证的成功标准与测试方法。按票实施时,必须先按 `/to-tickets` 的「The feature checklist」核对最新需求与清单的对应关系、定位本票承兑项,再进入编码;发现漏项或范围变化,按该节处置,不得只读取已有行。直接按 spec 实施时,必须采用该节的原子需求粒度制定成功标准,但不因此强制切票。
   按票实施时，必须完整读取 [Ticket 产物与文档同步清单](../to-tickets/ticket-artifacts.md)，定位本票清单及声明的审查路径；缺失时必须按该规范的旧票接续规则处理。实施与复审中必须执行下方“文档同步与记录维护”，不得等交付时才盘点同步对象。
4. **`/tdd` 纵切循环**(红先于绿、一次一纵切、覆盖清单来自 spec 失败模式节)。无测试价值的(纯 UI/样式/一行配置)说明理由后跳过 TDD。
5. **验证网关**:每个纵切完成即跑 typecheck + 该单测;整体完成前跑全量(lint → 单元/集成 → e2e/端到端;lint 与 e2e 按能力 `lint`、`e2e-suite` 判定,启用的照其 `enforced-by` 跑,未启用的按全局指令「项目能力声明」节写明跳过),**全绿才算这步完成**——不靠"我觉得过了",靠可跑的检查。**退出码必须显式挡住后续动作**(提交、开 PR)，不得仅记录失败而继续交付。
6. **清单核销**(仅按票实施时;直接按 spec 实施的由 Spec 核销终检承担):必须按 `/to-tickets` 的「The feature checklist」验证边界与证据规则逐条核对本票承兑项，并按“验收时点与阶段门禁”判定是否可进入第 5 步(`/review-code`)。清单里找不到本票、或本票承兑项为空,必须先回 `/to-tickets` 补映射;仅承担全 feature 核销的收口票允许空承兑,其核销由第 8 步承担;收口票若承兑了跨票组合行为,仍须逐条核对这些项。

## 第 5 步:`/review-code`(批判式代码自审)

必须调用 `/review-code` 并按其“记录归属”落盘本次分层结论与发现。

## 第 6 步:`/review-tests`(审测试本身)

必须调用 `/review-tests` 并按其“记录归属”落盘本次各维度结论与发现。

⚠️ **内联验证不能抵扣第 5/6 步**:实现期的变异检验、真实数据核验只触及 `/review-tests` 的第三个维度(假通过排查);`/review-code` 的分层扫查与 spec 逐条核销没有替代物。

## Spec 核销终检(第 7 步归档前,只读代码)

必须按第 4 步确定的原子需求粒度对照最新 spec 核销,结论引 spec 原文;不得用整段需求的部分实现替代逐项结论。验证尚未执行的项必须按“验收时点与阶段门禁”处理，不得仅因合法后置验证未执行而判为实现缺失，也不得据此推断实现已满足要求：
- **缺失/部分实现**的需求 → 回第 4 步补实现(补完重过第 5/6 步的相应部分)。第 5/6 步会改代码,**本票在清单里承兑的条目要重核一遍兑现是否仍成立**;清单里归后续票的条目不在此判缺失。
- **未记录的范围扩张**(spec 没要求却改了的)→ 与「窄而完整」的逐行可追溯要求互证,确属需要的补进 spec,不需要的回退;
- **与 spec 描述不符的实现** → 与用户确认:改代码,或确认偏离并更新 spec。

本终检**只读代码、可改 spec**(spec 是持久产物,实现期的合法演化必须回写)。所有发现处理完毕后才进第 7 步归档。

## 第 7 步:拆解归档(回同步)

第 4-6 步产生的东西各归其位:

- **新拍的决策**(尤其实现期踩坑改向的)→ ADR(按 domain-modeling/ADR-FORMAT;顺带检查有无「提议」态 ADR 该升级或推翻);
- **新术语/新消解的歧义** → CONTEXT.md;
- **踩坑因果链** → `docs/` 复盘文档;**判据**:说得出根因、说得出"现有检查为什么没拦住"、且已落一道防御——三者齐备才值得单开一篇,缺任一记在施工记录里即可;
- **/ui-design 要求报告的改动面外字符图标清单** → 归档前逐项确认已落归宿;
- **spec 是结论,施工记录是过程**:
  - **spec** 在 `docs/specs/<slug>.md`,**不删**。归档时按终检结论把实现期的合法演化回写进去(新增的边界条目、口径修订、Out of Scope 变化),使它描述的是**最终实现**而非最初设想;各节的处理按 to-spec「模板与持久化的配合」办。
  - **施工记录**必须按下方“文档同步与记录维护”处理现行记录与原始证据。同 feature 还有未完成 ticket 时，必须先把已确认的实现偏离回写 spec，再交给后续票实施。

## 文档同步与记录维护

维护文档或回写状态时，必须完整读取并遵循 [文档同步与记录维护](document-sync.md)；不得以本节指针代替规则正文。

## 交付

**开 PR 之前先验凭据**,缺任一不得开 PR:

1. 必须按两类审查 skill 的“记录归属”核对本次审查记录，读取内容确认版本、范围、发现及处置，不得只检查文件存在；按票交付必须据此核销票内对应流程验收。第 8 步跑过的，`final-regression.md` 同为凭据，判据以 `/features-catalog` 的落盘条款为准。
2. 本次若改变**用户可见行为**,已调 `/features-catalog` 走完第 8 步(功能目录就地更新 + 本次范围的交叉回归),其产出与代码进**同一个 PR**。判据是两问——本次让 `docs/features/` 里**哪句话变成了谎**、又**缺了哪句话**;两问皆答「无」方可判为不改变可见行为而跳过,该判定须写进交付说明,不得默认跳过。**收口票不适用两问跳过**——两问答的是本票改动的后果,而收口票的职责恰是找出各票拼起来才出现的不一致,答案在收口跑完之前不存在。收口票一律走完第 8 步,**含 `/features-catalog` 的全 feature 收口**,同为开 PR 的前置条件。

第 2 条**不得延后到后续 PR**:功能目录描述的是 master 上的产品,代码先合、文档后补会在两次合并之间留下目录说谎的窗口,而该窗口内没有任何检查会发现它。**编排范围止于第 7 步不构成豁免**——第 8 步不由本 skill 编排,但它是开 PR 的前置条件。

按票交付时，必须先执行 [文档同步与记录维护](document-sync.md) 的“核销前的范围复核”，再按 [Ticket 产物与文档同步清单](../to-tickets/ticket-artifacts.md) 的“文档同步清单结构与状态”重判各项状态；存在待处理项时不得交付。必须更新票内文档同步验收项，并按“验收时点与阶段门禁”处理后置验收；无用户可见行为变化而跳过第 8 步时，仍必须执行此项检查。

遵循 `/github-ops`(commit/push/PR 全程无 AI 署名):push 分支 → 开 PR 后**停下等用户确认——开 PR 不构成合并授权,确认前不执行合并**。用户确认后默认 squash 合并保持 master 线性、合并后删远程分支;合并方式有特殊需要用户会说明。

## 验收反馈回写

- 收到用户反馈时，必须先定位已交付的票或 spec、版本与验收范围；只能确认部分范围时必须只记录该部分，无法定位时必须澄清，不得猜测票号或扩大验收结论。
- 用户确认通过后，必须在同轮按“文档同步与记录维护”处理该事件触发的同步项，记录用户确认的时间、范围和可复查消息定位或原文摘录，并更新实际存在的 ticket、共享 checklist 与关联现行状态；失败反馈必须记录实际结果并重开受影响项。回写尚有阻断时必须区分“用户已确认”与“流程回写未完成”，不得宣称本票已全部收口。
- 必须将用户验收与合并授权分开判断；仅收到“测试通过”或“已验收”不得执行合并。获得合并授权并完成合并后，必须按“文档同步与记录维护”处理合并事件触发的同步项。
