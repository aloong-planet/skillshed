> Fork 自 mattpocock/skills(2026-07 快照)。修改:扩为第 4-7 步编排器(分支纪律、验证网关、双 review 门、Spec 终检、拆解归档)。

实施 spec 或 tickets 描述的工作。编码全程遵循 CLAUDE.md 的**窄而完整**原则(正文只在 CLAUDE.md,此处不复制)。开始前读 CONTEXT.md 与相关 ADR。

## 第 4 步:实现

0. **准入检查(界面)**:待实施的改动若含用户可见的界面变化——**含改色、调间距这类视觉微调**——逐条列出界面点,确认每条都有**已确认的原型**覆盖。缺原型、或原型与当前需求不一致 → **停下先跑 `/prototype` 并等用户确认**,不在实现阶段边写边定界面。
   例外与 `/to-spec` 原型门同口径(纯文案、纯数据口径、无可见变化的重构),但**例外必须显式声明理由后才可跳过**——心里豁免等于违规;新增状态形态(空态/提示态/降级态)不算纯文案。修 UI bug 不走 to-spec,这道闸就是唯一的门,不可跳过。
   **本闸按改动逐次生效,不是阶段一次性**(2026-08-01 定案):实现期中途新到的需求(用户增量要求、review 引出的 UI 变化)同样先过此闸——**判据**:每次准备动 UI 代码前自问"这个界面点的原型改了吗 / 例外理由声明了吗",两者皆无就先回原型——**"这次很小"不是例外,例外只有那三类且必须写出来**。
   过闸后、动任何界面代码前,必须先调 `/ui-design`(Skill 工具)载入界面硬性规范并全程遵循。
1. **分支**:从最新 master 拉 feature 分支(如 `feat/xxx`),所有改动在分支上,不直接改 master。
2. **tasklist 持久化**(TaskCreate/TaskUpdate);多步任务给出带验证检查点的计划,循环到验证通过。**第 5、6 步必须各建独立 task,不得并入其他 task**。
3. **目标驱动**:先定可验证的成功标准与测试方法。
4. **`/tdd` 纵切循环**(红先于绿、一次一纵切、覆盖清单来自 spec 失败模式节)。无测试价值的(纯 UI/样式/一行配置)说明理由后跳过 TDD。
5. **验证网关**:每个纵切完成即跑 typecheck + 该单测;整体完成前跑全量(lint → 单元/集成 → e2e/端到端),**全绿才算这步完成**——不靠"我觉得过了",靠可跑的检查。
6. **清单核销**(仅按票实施时;直接按 spec 实施的没有清单,需求核销由 Spec 核销终检承担):取 `docs/.workings/<slug>/checklist.md` 里本票承兑的每一条,逐条回答「它声明的 gate / test / evidence 兑现在哪」——gate 指出哪道门禁拦得住、test 报出用例名、evidence 给出可复查产物。答不出即为未完成,回本步补,**不得带着它进第 5 步**:需求还没落地就审代码质量,审的是一份还要重写的东西。清单里找不到本票、或本票承兑项为空,说明切票时漏了,先回 `/to-tickets` 补清单再往下走;**收口票除外**——它按设计不承兑条目,空承兑不是漏切,其需求核销整个由第 8 步的全 feature 收口承担。

## 第 5 步:`/review-code`(批判式代码自审;重构项整理成清单经用户确认)

产物落盘:分层结论与发现写入 `docs/.workings/<slug>/review-code.md`(与 tickets 同级的施工记录,保留)。

## 第 6 步:`/review-tests`(审测试本身)

产物落盘:三维度结论与发现写入 `docs/.workings/<slug>/review-tests.md`(与 tickets 同级的施工记录,保留)。

⚠️ **内联验证不能抵扣第 5/6 步**:实现期的变异检验、真实数据核验只触及 review-tests 的维度 3;四层法与 spec 逐条核销没有替代物。

## Spec 核销终检(第 7 步归档前,只读代码)

对照 spec 逐条核销,结论引 spec 原文:
- **缺失/部分实现**的需求 → 回第 4 步补实现(补完重过第 5/6 步的相应部分)。第 5/6 步会改代码,**本票在清单里承兑的条目要重核一遍兑现是否仍成立**;清单里归后续票的条目不在此判缺失。
- **未记录的范围扩张**(spec 没要求却改了的)→ 与「窄而完整」的逐行可追溯要求互证,确属需要的补进 spec,不需要的回退;
- **与 spec 描述不符的实现** → 与用户确认:改代码,或确认偏离并更新 spec。

本终检**只读代码、可改 spec**(spec 是持久产物,实现期的合法演化必须回写)。所有发现处理完毕后才进第 7 步归档。

## 第 7 步:拆解归档(回同步)

第 4-6 步产生的东西各归其位:

- **新拍的决策**(尤其实现期踩坑改向的)→ ADR(按 domain-modeling/ADR-FORMAT;顺带检查有无「提议」态 ADR 该升级或推翻);
- **新术语/新消解的歧义** → CONTEXT.md;
- **值得留的踩坑因果链** → `docs/` 复盘文档;
- **/ui-design 要求报告的改动面外字符图标清单** → 归档前逐项确认已落归宿;
- **spec 是结论,施工记录是过程**(2026-08-01 定,2026-08-11 改保留策略):
  - **spec** 在 `docs/specs/<slug>.md`,**不删**。归档时按终检结论把实现期的合法演化回写进去(新增的边界条目、口径修订、Out of Scope 变化),使它描述的是**最终实现**而非最初设想;够 ADR 门槛的决策落 ADR 后 spec 改为引用编号,腐烂的实现细节删掉(见 to-spec「模板与持久化的配合」)。
  - **施工记录** 在 `docs/.workings/<slug>/`(tickets、checklist.md、review-code.md、review-tests.md),**合并后保留、不删**,留作可追溯。
    但它**不得被任何 skill 当作可靠依据**:它记的是「当时是怎么干的」,不是「现在什么是对的」——需求以 spec 为准、当前行为以 features 为准、决策以 ADR 为准、术语以 CONTEXT.md 为准。
    读它只为回答「这件事当时为什么这么做」,不得据以推断现状;与结论类文档冲突时,一律以结论类为准,且不必回头修改施工记录——它就该保持当时的样子。
    同 feature 还有未完成 ticket 时,先把已定偏离回写进 spec——后续 ticket 依赖它的准确性。

## 交付

**开 PR 之前先验凭据**,缺任一不得开 PR:

1. `docs/.workings/<slug>/review-code.md` 与 `review-tests.md` 存在且含本票的发现或豁免记录;
2. 本次若改变**用户可见行为**,已调 `/features-catalog` 走完第 8 步(功能目录就地更新 + 本次范围的交叉回归),其产出与代码进**同一个 PR**。判据是两问——本次让 `docs/features/` 里**哪句话变成了谎**、又**缺了哪句话**;两问皆答「无」方可判为不改变可见行为而跳过,该判定须写进交付说明,不得默认跳过。**收口票不适用两问跳过**——两问答的是本票改动的后果,而收口票的职责恰是找出各票拼起来才出现的不一致,答案在收口跑完之前不存在。收口票一律走完第 8 步,**含 `/features-catalog` 的全 feature 收口**,同为开 PR 的前置条件。

第 2 条**不得延后到后续 PR**:功能目录描述的是 master 上的产品,代码先合、文档后补会在两次合并之间留下目录说谎的窗口,而该窗口内没有任何检查会发现它。**编排范围止于第 7 步不构成豁免**——第 8 步不由本 skill 编排,但它是开 PR 的前置条件。

遵循 `/github-ops`(commit/push/PR 全程无 AI 署名):push 分支 → 开 PR 后**停下等用户确认——开 PR 不构成合并授权,确认前不执行合并**。用户确认后默认 squash 合并保持 master 线性、合并后删远程分支;合并方式有特殊需要用户会说明。
