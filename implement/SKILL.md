> Fork 自 mattpocock/skills(2026-07 快照)。修改:扩为第 4-7 步编排器(分支纪律、用例设计审查、验证网关、双 review 门、Spec 终检、拆解归档),另设小改动路径。

实施 spec 或 tickets 描述的工作;判为小改动的改动按「小改动路径」节实施,收口票按「收口票路径」节实施。编码全程遵循 AGENTS.md 的**窄而完整**原则(正文只在 AGENTS.md,此处不复制)。开始前按全局指令「读项目词汇表 `CONTEXT.md`」查 CONTEXT.md(先读目录,用到的术语再取单条),并读相关 ADR。

本 skill 各步写或改的测试,凡是全量验证网关的测试命令会运行的,都不得读取惰性文件:网关判定改动范围时把惰性文件判为不影响测试命令,以此为前提(惰性文件、测试命令与跳过条件见 [full-verification-gate.md](full-verification-gate.md)「按改动范围跳过测试命令」条)。要校验惰性文件的内容(如 README 与站点页面一致),必须做成每次全量都照跑的检查命令,不得做成这样的测试。

仅收到既有交付的验收反馈且没有新增实现要求时，必须直接执行“验收反馈回写”(按该节完整读取 [delivery-and-feedback.md](delivery-and-feedback.md))，不得重新拉分支或重跑实现步骤；反馈包含缺陷或新范围时，必须先定位受影响要求并按现有需求变更与验证流程处理。

## 小改动路径

按全局指令判为小改动的改动,必须依次执行本节各项;下文各节与第 4 步各项,只执行本节指向的部分。

1. 必须执行第 4 步第 0 项(准入检查)与第 1 项(分支)。
2. 写代码前必须在回复里写下本次的成功标准:修 bug 的写明要消除的错误行为及其复现方式,改行为的写明改动后的行为。
3. 必须为成功标准里的每条行为写或改测试,按 `/tdd` 执行;按第 4 步第 5 项判为无测试价值的,说明理由后不写测试。
4. 必须按第 4 步第 6 项跑定向验证。
5. 必须执行「第 5 步」节。
6. 必须答两问:本次改动让仓库里陈述现状的文档(`docs/` 下的 spec、features、ADR,`CONTEXT.md`,各级 README,项目 `AGENTS.md`)中哪句话变成了谎、又缺了哪句话。作答前必须检索本次改动涉及的名称(被改的函数与模块、配置键、文件路径、界面文案)在这些文档中的全部出现处,不得凭印象作答。变成谎或缺的句子当场改写;改 `docs/features/` 的按 `/features-catalog` 的「更新流程」节,不跑其「文档一致性收口」节。两问的结论与所用的检索命令必须写进交付说明。
7. 必须执行「交付」节。

## 收口票路径

票写明自己是收口票时(定义与判据见 `/features-catalog`「全 feature 收口」节),必须依次执行本节各项;下文各节与第 4 步各项,只执行本节指向的部分。

0. **开工读取**:认定本票是收口票后,当前工具支持一次请求发出多个调用时,必须用一次请求读完票(尚未读的)与本节后面各项点名的 skill 与引用文档,各项指向的节里点名的也算;再用一次请求读完这些文件点名的 skill 与引用文档,以及票点名的 spec、`checklist.md`、`final-regression.md` 与本票的文档同步清单;读到的文件又点名了别的,依此再用一次请求读完,直到没有新的。每份文件仍是一次单独的工具调用。只在某种情形下才要读的(如第 2 项「需要可执行改动的」所走的步骤),等情形出现再读。
1. 票 Blocked by 的每张票都必须已合并进默认分支;有未合并的,必须停下报告,不得开工。随后必须执行第 4 步第 1 项(分支)。
2. 必须调 `/features-catalog`,执行其「文档一致性收口」与「全 feature 收口」两节,并把票点名的决定与边界写进 spec,其中用户可见的部分同时写进 features。写进仓库的每条产品事实都必须有证据留在施工记录里,证据的形态见 [claim-check.md](claim-check.md)「核对的执行」第 3 项。需要可执行改动([change-scope.mjs](change-scope.mjs) 会判为 `changed` 的改动)的,必须按第 4 步第 0 项起走到第 7 步的顺序写它,其中第 4 步第 1 项不重做,不得先写后补;走完必须按 `/features-catalog`「全 feature 收口」的「判定收口」条重核受影响项。写进仓库的改动必须提交为 commit。
3. 必须先拉取远端,取 `git merge-base HEAD origin/<默认分支>` 得到的分叉点,再按下列各支判定,所用命令、完整输出与退出码必须写进陈述核对记录(路径见 [Ticket 产物与文档同步清单](../to-tickets/ticket-artifacts.md)):
   - 相对分叉点 `git diff` 为空的:不得开 PR,跳过下面两项,把收口结论报告给用户。
   - 相对分叉点运行 [change-scope.mjs](change-scope.mjs),退出码为 0 的:即没有可执行改动,不得执行第 5、6 步与全量验证网关的复核前运行。
   - 退出码为 1 的:即有可执行改动。`/review-code` 与 `/review-tests` 的记录写明的范围已包含被判为 `changed` 的每个文件的,继续执行下面两项;未包含的,必须撤出这些文件的改动,按第 2 项重做,再重新执行本项。
   - 上述命令出错或退出码为其他值的:必须排除错误后重新执行本项,排除不了的必须报告用户。
4. 必须按 [claim-check.md](claim-check.md) 逐句核对写进仓库的事实陈述,并处置发现。
5. 必须执行「交付」节。

## 验收时点与阶段门禁

每次阶段核销前，必须为本轮每个验收项记录执行时点，并按以下顺序判定；不得用“产品验收、技术前提、流程验收”的分类代替时点判定：

1. 当前有效验证结果为失败，或所需实现缺失、部分实现的项，必须先修复并复验，不得改记为后置验收以越过门禁。
2. 尚未执行，且本流程明确安排在后续第 5–8 步、用户验收或合并事件中核对、执行时点尚未到达的流程项，必须保留为未验证，并在对应步骤或事件发生时核销。
3. 尚未执行、用户已明确确认在交付后验证且约定执行时点尚未到达的产品或技术项，必须记录确认依据、负责验证者、触发条件、验证方法及待补证据位置，保留为未验证。缺少任一记录时不得按此分支放行；不得以环境不可用或时间不足自行延期。
4. 不属于前述后置安排的项，必须在当前核销阶段取得符合保障机制的通过证据；失败、漏测或阻断未解决时不得进入下一阶段。

必须在交付说明中列出按第 2、3 项保留的后置验收及其安排（“后置验收”写进交付说明时按 [产物固定名称](../repo-scaffold/artifact-names/implement.md) 书写），不得将允许继续流程写成验收通过；本节不豁免本 skill 的定向验证与全量验证网关、交付凭据或 `/features-catalog` 的全 feature 最终收口判定。存在未验证项时不得将票标为最终验收完成。

## 第 4 步:实现

0. **准入检查(界面)**:待实施的改动若含用户可见的界面变化——**含改色、调间距这类视觉微调**——逐条列出界面点,确认每条都有**已确认的原型**覆盖。缺原型、或原型与当前需求不一致 → **停下先跑 `/prototype` 并等用户确认**,不在实现阶段边写边定界面。
   例外清单与跳过条件以 `/to-spec` 的原型门为准,此处不复述——**修 UI bug 虽然不走 to-spec 那条流程,例外口径照样照它**。这道闸是那种改动唯一的门,不可跳过。
   **本闸按改动逐次生效,不是阶段一次性**:实现期中途新到的需求(用户增量要求、review 引出的 UI 变化)同样先过此闸——**判据**:每次准备动 UI 代码前自问"这个界面点的原型改了吗 / 例外理由声明了吗",两者皆无就先回原型——**"这次很小"不是例外**,例外只有 `/to-spec` 列的那几类。
   **读原型只读要实现的界面点**:要实现什么必须以 spec 为准(按票实施时以票引用的 spec 条目为准),原型只用来定这些界面点长什么样。读原型时必须只读本项列出的界面点所在的元素——其标记、样式规则与渲染它的代码;定位这些元素必须用检索(按界面点的文案、类名、数据属性),不得为定位而通读整页;原型改动的 diff 同样只看这些元素所在的几处,不得通读整份。原型里写给评审者的说明——问题、裁决、演示基建(见 `/prototype` 的 UI.md「演示基建(harness)条款」)清单,不论写在页头注释里还是另存在页面旁的文件里——不属于界面,不得读。**判据**:读进上下文的每一段原型内容,都指得出它属于哪个界面点。读进上下文的内容此后每次调用都会再读一遍,与界面点无关的部分读得越早,重复的代价越大。
   过闸后、动任何界面代码前,必须先调 `/ui-design`(Skill 工具)载入界面硬性规范并全程遵循。
1. **分支**:从最新默认分支拉 feature 分支(如 `feat/xxx`)——**先拉取远端再开分支,开完核对本分支相对默认分支的提交列表为空**,否则会静默带上别人或上一轮未合并的改动;所有改动在分支上,不直接改默认分支。
2. **tasklist 持久化**(TaskCreate/TaskUpdate);多步任务给出带验证检查点的计划,循环到验证通过。**用例设计审查与第 5、6 步必须各建独立 task,不得并入其他 task**。
3. **目标驱动**:先定可验证的成功标准与测试方法。按票实施时,必须先按 `/to-tickets` 的「The feature checklist」核对最新需求与清单的对应关系、定位本票承兑项,再进入编码;发现漏项或范围变化,按该节处置,不得只读取已有行。直接按 spec 实施时,必须采用该节的原子需求粒度制定成功标准,但不因此强制切票。
   按票实施时，必须完整读取 [Ticket 产物与文档同步清单](../to-tickets/ticket-artifacts.md)，定位本票清单及声明的审查路径；缺失时必须按该规范的旧票接续规则处理。实施与复审中必须执行下方“文档同步与记录维护”，不得等交付时才盘点同步对象。
4. **用例设计审查**:写或改第一个测试前,必须调用 `/review-tests` 执行「设计审查」并按其“记录归属”落盘;按下一项判为无测试价值而跳过 TDD 的,本项随之跳过。
5. **`/tdd` 纵切循环**(一次一纵切、覆盖清单来自 spec 失败模式节;哪些测试必须先红按 `/tdd` 的「循环规则」节)。无测试价值的(纯 UI/样式/一行配置)说明理由后跳过 TDD。
6. **定向验证**:每个纵切完成后必须跑 typecheck 与该纵切的单测;整体完成后必须跑 lint(按 [full-verification-gate.md](full-verification-gate.md) 的能力判定)与本次改动涉及的测试:本次新写或改动的测试文件、按导入关系检索出的导入被改模块的测试文件(导入目标不是常量的调用,如动态导入,必须逐个列出并判断它是否导入了被改模块),以及按文件名检索出的读取被改配置或数据文件的测试文件。清单必须由检索得出,不得凭印象挑选;检索结果为空时,必须把检索命令与空输出记入施工记录。**全绿才算这步完成**——不靠"我觉得过了",靠可跑的检查;**退出码必须显式挡住进入第 5 步**,不得仅记录失败而继续。全量验证网关的复核前运行排在第 5 步之后、全量排在第 7 步之后(见 [full-verification-gate.md](full-verification-gate.md)):审查修复会改代码与测试,审查前跑的在修复后必须重跑,排在审查之后只需跑一次。
7. **清单核销**(仅按票实施时;直接按 spec 实施的由 Spec 核销终检承担):必须按 `/to-tickets` 的「The feature checklist」验证边界与证据规则逐条核对本票承兑项，并按“验收时点与阶段门禁”判定是否可进入第 5 步(`/review-code`)。清单里找不到本票、或本票承兑项为空,必须先回 `/to-tickets` 补映射;仅承担全 feature 核销的收口票允许空承兑,其核销由第 8 步承担;收口票若承兑了跨票组合行为,仍须逐条核对这些项。

## 第 5 步:`/review-code`(批判式代码自审)

必须调用 `/review-code` 并按其“记录归属”落盘本次分层结论与发现。

## 全量验证网关(第 5 步之后、第 6 步之前)

第 5 步完成(含其修复)后,必须完整读取 [full-verification-gate.md](full-verification-gate.md),按其跑复核前运行、写日志,并按其判定哪些测试命令可以跳过。

## 第 6 步:`/review-tests` 实现后复核(审写成的测试)

全量验证网关的复核前运行通过后,必须完整读取 [post-implementation-check.md](post-implementation-check.md),按其判定首轮是否复核、把实现后复核交给独立子 agent,并按其处置交回的发现、交出前自查、跑修复后的定向验证、判定是否增量复核。

## Spec 核销终检(第 7 步归档前,只读代码)

必须按第 4 步确定的原子需求粒度对照最新 spec 核销,结论引 spec 原文;不得用整段需求的部分实现替代逐项结论。验证尚未执行的项必须按“验收时点与阶段门禁”处理，不得仅因合法后置验证未执行而判为实现缺失，也不得据此推断实现已满足要求：
- **缺失/部分实现**的需求 → 回第 4 步补实现(补完重过第 5 步、全量验证网关与第 6 步的相应部分)。第 5/6 步会改代码,**本票在清单里承兑的条目要重核一遍兑现是否仍成立**;清单里归后续票的条目不在此判缺失。
- **未记录的范围扩张**(spec 没要求却改了的)→ 与「窄而完整」的逐行可追溯要求互证,确属需要的补进 spec,不需要的回退;
- **与 spec 描述不符的实现** → 与用户确认:改代码,或确认偏离并更新 spec。

本终检**只读代码、可改 spec**(spec 是持久产物,实现期的合法演化必须回写)。所有发现处理完毕后才进第 7 步归档。

## 第 7 步:拆解归档(回同步)

第 4-6 步产生的东西各归其位:

- **新拍的决策**(尤其实现期踩坑改向的)→ ADR(按 domain-modeling/ADR-FORMAT;顺带检查有无「提议」态 ADR 该升级或推翻);
- **新术语/新消解的歧义** → CONTEXT.md;
- **踩坑因果链** → `docs/` 复盘文档;**判据**:说得出根因、说得出"现有检查为什么没拦住"、且已落一道防御——三者齐备才值得单开一篇,缺任一记在施工记录里即可;
- **/ui-design 要求报告的改动面外字符图标清单** → 归档前逐项确认已落归宿;
- **spec 是结论,施工记录是过程**:
  - **spec** 在 `docs/specs/<slug>.md`,**不删**。归档时按终检结论把实现期的合法演化回写进去(新增的边界条目、口径修订、Out of Scope 变化),使它描述的是**最终实现**而非最初设想;各节的处理按 to-spec「模板与持久化的配合」办。
  - **施工记录**必须按下方“文档同步与记录维护”处理现行记录与原始证据。同 feature 还有未完成 ticket 时，必须先把已确认的实现偏离回写 spec，再交给后续票实施。

## 文档同步与记录维护

维护文档或回写状态时，必须完整读取并遵循 [文档同步与记录维护](document-sync.md)；不得以本节指针代替规则正文。

## 交付

第 7 步完成后,必须完整读取 [full-verification-gate.md](full-verification-gate.md),按其跑全量、写日志,并按其判定哪些测试命令可以跳过、全量后又有改动时能否沿用上次全量结果。全量全绿后、开 PR 或以其他方式交付之前,必须完整读取 [delivery-and-feedback.md](delivery-and-feedback.md),按其「交付」节验凭据并交付。

## 验收反馈回写

收到用户对已交付工作的验收反馈时,必须完整读取 [delivery-and-feedback.md](delivery-and-feedback.md),按其「验收反馈回写」节处理。
