实施 spec 或 tickets 描述的工作;判为小改动的改动按「小改动路径」节实施,收口票按「收口票路径」节实施,其余的依次执行「实现」「独立审查」「写下只有主 agent 知道的」「交付」四节,全程按「交付说明」节记下这次交付。开始前按全局指令「读项目词汇表 `CONTEXT.md`」查 CONTEXT.md,并读相关 ADR。

本 skill 写或改的测试,凡是测试命令会运行的,都不得读取惰性文件:判定可执行内容变没变时把惰性文件判为不影响测试命令,以此为前提(惰性文件与测试命令的界定见 [full-verification-gate.md](full-verification-gate.md)「测试命令与惰性文件」条)。要校验惰性文件的内容(如 README 与站点页面一致),必须做成每次都照跑的检查命令,不得做成这样的测试。

收到用户对已交付工作的反馈时,必须完整读取 [delivery-and-feedback.md](delivery-and-feedback.md),按其「验收反馈」节处理。

## 小改动路径

按全局指令判为小改动的改动,必须依次执行本节各项;下文各节与「实现」节各项,只执行本节指向的部分。

1. 必须执行「实现」节第 0 项(准入检查)与第 1 项(分支)。
2. 写代码前必须在回复里写下本次的成功标准:修 bug 的写明要消除的错误行为及其复现方式,改行为的写明改动后的行为。
3. 必须为成功标准里的每条行为写或改测试,按 `/tdd` 执行,其「用例落在哪一层」「不写重复的用例」与「测试资源复用」三节「判据」一条要说出的内容必须写进交付说明,不适用的写明不适用;按「实现」节第 4 项判为无测试价值的,在交付说明里写明理由后不写测试。
4. 必须按 [full-verification-gate.md](full-verification-gate.md)「审查前运行」条跑审查前运行。
5. 必须调用 `/review-code` 审本会话的这次改动,修掉它的每条发现中判为当场修的,并把每条发现及其处置写进交付说明,处置只取「交付说明」节「内容」条的三种;有修复的,修复后必须按 full-verification-gate.md「修复后运行」条跑修复后运行。
6. 必须答两问:本次改动让仓库里陈述现状的文档(`docs/` 下的 spec、ADR,`CONTEXT.md`,各级 README,项目 `AGENTS.md`)中哪句话变成了谎、又缺了哪句话。作答前必须检索本次改动涉及的名称(被改的函数与模块、配置键、文件路径、界面文案)在这些文档中的全部出现处,不得凭印象作答。变成谎或缺的句子当场改写。两问的结论与所用的检索命令及其输出必须写进交付说明。
7. 必须执行「交付」节。

## 收口票路径

票写明自己是收口票时(定义与判据见 `/features-catalog`「全 feature 收口」节),必须依次执行本节各项;下文各节与「实现」节各项,只执行本节指向的部分。

0. **开工读取**:认定本票是收口票后,当前工具支持一次请求发出多个调用时,必须用一次请求读完票(尚未读的)与本节后面各项点名的 skill 与引用文档,各项指向的节里点名的也算;再用一次请求读完这些文件点名的 skill 与引用文档,以及票点名的 spec 与 feature 级的 `checklist.md`;读到的文件又点名了别的,依此再用一次请求读完,直到没有新的。每份文件仍是一次单独的工具调用。只在某种情形下才要读的(如第 2 项「需要可执行改动的」所走的各节),等情形出现再读。
1. 票 Blocked by 的每张票都必须已合并进默认分支;有未合并的,必须停下报告,不得开工。随后必须执行「实现」节第 1 项(分支)。
2. 必须调 `/features-catalog`,执行其「文档一致性收口」与「全 feature 收口」两节,把全 feature 收口的结论写进交付说明,并把票点名的决定与边界写进 spec。写进仓库的每条产品事实都必须有证据留在陈述核对记录里,证据的形态见 [claim-check.md](claim-check.md)「核对的执行」第 3 项。需要可执行改动([change-scope.mjs](change-scope.mjs) 会判为 `changed` 的改动)的,必须从「实现」节第 0 项起依次走到「独立审查」节写它,其中「实现」节第 1 项不重做,不得先写后补;走完必须按 `/features-catalog`「全 feature 收口」的「判定收口」条重核受影响项。写进仓库的改动必须提交为 commit。
3. 必须先拉取远端,取 `git merge-base HEAD origin/<默认分支>` 得到的分叉点,再按下列各支判定,所用命令、完整输出与退出码必须写进陈述核对记录(路径见 claim-check.md「核对的执行」第 7 项):
   - 相对分叉点 `git diff` 为空的:不得开 PR,跳过下面两项,把收口结论报告给用户。
   - 相对分叉点运行 [change-scope.mjs](change-scope.mjs),退出码为 0 的:即没有可执行改动,不得送独立审查,交付说明写明这次跳过及其依据。
   - 退出码为 1 的:即有可执行改动。本会话已按第 2 项为可执行改动交出过独立审查的,继续执行下面两项;没有交出过的,必须撤出这些改动,按第 2 项重写,再重新执行本项。
   - 上述命令出错或退出码为其他值的:必须排除错误后重新执行本项,排除不了的必须报告用户。
4. 必须按 [claim-check.md](claim-check.md) 逐句核对写进仓库的事实陈述,并处置发现。
5. 必须执行「交付」节。

## 实现

0. **准入检查(界面)**:待实施的改动含用户可见的界面变化的,必须先按 `/prototype`「原型门」节判定;有界面点属门内情形而未过门的,**停下先跑 `/prototype`**,不在实现阶段边写边定界面。修 UI bug 这类不经 spec 的改动同样必须做这项判定。
   **本闸按改动逐次生效,不是阶段一次性**:实现期中途新到的需求(用户增量要求、审查引出的 UI 变化)同样先过此闸——**判据**:每次准备动 UI 代码前,按「原型门」节的判定条判这个界面点;属门内情形、又指不出它在哪个经用户确认的原型里可见的,先回原型。
   **读原型只读要实现的界面点**:要实现什么必须以 spec 为准(按票实施时以票引用的 spec 条目为准),原型只用来定这些界面点长什么样。读原型时必须只读本项列出的界面点所在的元素——其标记、样式规则与渲染它的代码;定位这些元素必须用检索(按界面点的文案、类名、数据属性),不得为定位而通读整页;原型改动的 diff 同样只看这些元素所在的几处,不得通读整份。原型里写给评审者的说明——问题、裁决、演示基建(见 `/prototype` 的 UI.md「演示基建(harness)条款」)清单,不论写在页头注释里还是另存在页面旁的文件里——不属于界面,不得读。**判据**:读进上下文的每一段原型内容,都指得出它属于哪个界面点。读进上下文的内容此后每次调用都会再读一遍,与界面点无关的部分读得越早,重复的代价越大。
   过闸后、动任何界面代码前,必须先调 `/ui-design`(Skill 工具)载入界面硬性规范并全程遵循。
1. **分支**:从最新默认分支拉 feature 分支(如 `feat/xxx`)——**先拉取远端再开分支,开完核对本分支相对默认分支的提交列表为空**,否则会静默带上别人或上一轮未合并的改动;所有改动在分支上,不直接改默认分支。本次是对一个尚未合并的 PR 所交付工作的缺陷或追加范围的,在该 PR 的分支上继续,不另拉分支。
2. **tasklist 持久化**(TaskCreate/TaskUpdate);多步任务给出带验证检查点的计划,循环到验证通过。**独立审查与交付必须各建独立 task,不得并入其他 task**。
3. **目标驱动**:先定可验证的成功标准与测试方法。按票实施、且票所属 feature 切成了两张及以上票的,必须先按 `/to-tickets` 的「The feature checklist」核对最新 spec 与清单里哪张票承兑什么的对应关系、定位本票承兑的覆盖单位,再进入编码;发现漏项或范围变化,必须停下按该节处置,不得只读取已有行。直接按 spec 实施时,必须采用该节的原子需求粒度制定成功标准,但不因此强制切票。
4. **`/tdd` 纵切循环**:必须调用 `/tdd` 执行;每个纵切完成后必须跑类型检查与该纵切的单测。无测试价值的(纯 UI/样式/一行配置)在交付说明里写明理由后跳过 TDD。
5. **审查前运行**:实现完成后,必须完整读取 [full-verification-gate.md](full-verification-gate.md),按其「审查前运行」条跑审查前运行。**全绿才算本节完成**——不靠"我觉得过了",靠可跑的检查;失败的处置按该文件「失败即停」条。

## 独立审查

审查前运行通过后,必须完整读取 [post-implementation-check.md](post-implementation-check.md),按其判定是否送审、把改动交给独立审查、核对交回、处置发现并跑修复后运行。

## 写下只有主 agent 知道的

发现处置完毕、有修复的其修复后运行通过之后,交出文档核对或交付之前,必须把只有主 agent 知道的写进持久文档:

- **spec**:本次改动定下或改变的行为,写进 `docs/specs/<slug>.md`(**不删**),使它描述的是**最终实现**而非最初设想(新增的边界条目、口径修订、Out of Scope 变化);各节的处理按 to-spec「模板与持久化的配合」办;留给用户决定的发现所涉的行为,按 [post-implementation-check.md](post-implementation-check.md)「留给用户决定」条不写。
- **新拍的决策**(尤其实现期踩坑改向的)→ ADR(按 domain-modeling/ADR-FORMAT;顺带检查有无「提议」态 ADR 该升级或推翻);
- **新术语/新消解的歧义** → CONTEXT.md;
- **踩坑因果链** → `docs/` 复盘文档;**判据**:说得出根因、说得出"现有检查为什么没拦住"、且已落一道防御——三者齐备才单开一篇,缺任一的不开;
- **/ui-design 要求报告的改动面外字符图标清单** → 交出前逐项确认已落归宿。

## 交付

必须完整读取 [delivery-and-feedback.md](delivery-and-feedback.md),按其「交付」节交出文档核对、跑本地的完整运行、交出交付、核对交回,并按其处理合并。

## 交付说明

一次交付只得有一份记录:它的交付说明。

- **位置与时点**:写在仓库主检出的 `docs/.workings/<slug>/delivery-<分支名>.md`(分支名里的 `/` 换成 `-`;`<slug>` 取本次改动已有的施工记录目录的那个——它的票、需求对齐记录或 feature checklist 所在的目录;没有这样的目录的,取本次改动实现的 spec 的 slug,实现了几篇的取承载其主要行为的那篇,没有 spec 的取分支名去掉类型前缀的部分)。最迟在独立审查交回时建立,没有独立审查的在第一项要写进它的内容出现时建立;此后每项内容一出现就写进去,不得攒到交付时一并写。
- **内容**:改了什么、为什么;审查的每条发现及其处置,处置取三种之一——已修复;留给用户决定;不修,附理由;本地跑过的每条命令及其结果(写法见 [full-verification-gate.md](full-verification-gate.md)「不写日志」条);按票交付的,票里保障写为 Evidence 的每条验收项的证据(截图、命令及其输出、测量值);没有验证的;等用户决定的;[delivery-and-feedback.md](delivery-and-feedback.md)「交付」节要求的界面截图;留给别人做的。交付说明里依据一条命令下的陈述(一次没有结果的检索、一个修复前失败的测试),必须给出该命令及其返回的内容。
- **去处**:经 PR 交付的,它就是 PR 的描述;不经 PR 的,它就是给用户的报告。按票交付、且 tracker 能凭 PR 的合并关闭票的,必须写明让合并关闭该票的那一行(如 GitHub 的 `Closes #<编号>`)。
- **不另写记录**:交付说明之外,不得为这次交付写代码审查记录、测试审查记录、用例设计表、文档同步清单、回归报告、运行日志、命令输出的副本或验证状态表,也不得为记下实施、交付或合并的进展而改写票或 feature checklist;收口票的陈述核对记录([claim-check.md](claim-check.md))除外。
- **既有记录**:项目里已有的这类记录原样保留,不迁移、不删除,接续它们的票也不往里写。按旧规则切出、带勾选框与流程验收项的票,照其产品验收与技术前提实施,不勾选,不写它点名的记录。
- **失败与缺失不改记**:运行失败、所需实现缺失或只实现了一部分的验收项,必须修到通过,不得改记为后置验收或未验证以越过它。
- **后置验收**:只有用户明确同意在交付后验证的项,才可列为后置验收("后置验收"写进交付说明时按 [产物固定名称](../repo-scaffold/artifact-names/implement.md) 书写),并写明用户同意的依据(可复查的消息定位或原文摘录)、由谁验证、何时验证(触发条件)与怎样验证;缺任一项的不得这样列,也不得因环境不可用或时间不足自行列为后置验收。列为后置验收的不得写成验收通过。
