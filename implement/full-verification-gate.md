# 全量验证网关

本文适用于 `/implement` 全量验证网关的两次运行——第 5 步之后、第 6 步之前的复核前运行,与第 7 步之后、交付之前的全量——以及每次运行里哪些测试命令可以跳过、全量通过后又有改动时能否沿用上次结果的判定;实现后复核的复核者按本文核对交接的复核前运行日志。入口:[SKILL.md](SKILL.md)「全量验证网关」节与「交付」节。

- 第 5 步完成(含其修复)后,必须跑复核前运行;第 7 步完成后、交付之前,必须跑全量。两者都依次跑 lint → 单元/集成 → e2e/端到端(lint 与 e2e 按能力 `lint`、`e2e-suite` 判定,启用的照其 `enforced-by` 跑,未启用的按全局指令「项目能力声明」节写明跳过),所跑的命令只在 e2e 上不同:全量运行全套用例,全套交给 PR 的 CI 时(见下一条)除外;复核前运行的 e2e 命令、以及全套交给 PR 的 CI 时全量的 e2e 命令,按本文「按改动范围跳过测试命令」条不能跳过的,只运行按 [SKILL.md](SKILL.md) 第 4 步第 6 项的检索规则对本次改动的最新状态重新得出的清单里的 e2e 用例文件,清单里没有 e2e 用例文件的不跑 e2e。复核前运行为第 6 步提供被复核测试的运行结果,只能排在第 6 步之前;全套 e2e 不是复核所需、又最耗时,排在第 6 步及其修复之后(全量里,或交给 PR 的 CI),才不会因复核修复而重跑。两者的测试命令能否跳过都按本文「按改动范围跳过测试命令」条判定;按该条跳过的命令之外,其余命令**全绿才进入下一步**(复核前运行之后是第 6 步,全量之后是交付);**退出码必须显式挡住后续动作**(进入第 6 步、提交、开 PR),不得仅记录失败而继续交付。
- **全套 e2e 交给 PR 的 CI**:由 PR 触发的 CI 工作流里出现了能力 `e2e-suite` 的 `enforced-by` 命令的,全量不得在本地运行全套 e2e,全套由 PR 上的 CI 运行承担;「出现」按本文「按改动范围跳过测试命令」条第 1 步对「在 CI 工作流中出现过」的判据判定,判定所读的工作流文件与命中的那一行必须写进全量的日志。不满足的,全量在本地运行全套 e2e。交给 CI 的,交付前必须取得 PR 上 CI 的结论,处置见 [delivery-and-feedback.md](delivery-and-feedback.md)「交付」节。
- **等待运行结束**:复核前运行与全量的执行与等待,必须按全局指令「等待后台工作」进行。
- 复核前运行与全量每次都必须把结果写成日志,日志必须写明:所测代码的版本——`git rev-parse HEAD` 的输出,以及 `git status --porcelain --untracked-files=all` 列出的每个文件的 `git hash-object` 输出(下称版本清单;已删除的文件写明删除);每条命令,取版本的命令连同其路径参数(如排除某目录的 pathspec)也算在内;不经管道直接取得的退出码;每条命令的完整输出。版本清单只得排除本次运行写出的文件,运行前已在工作区的文件即便位于日志所在目录也必须列出:被排除的既有文件若被这次运行读取,日志就证明不了它是哪个版本。复核前运行的日志是第 6 步的运行证据(复核者怎样核对它见 `/review-tests`「实现后复核」的「运行证据」条);缺任一项,日志就证明不了它对应哪份代码、是否真的全绿。
- 全量通过后又改了代码、配置或测试读取的数据文件的,交付前必须重跑全量;仅当同时满足下列两项时可沿用上次全量结果,两项的命令、完整输出与退出码必须记入施工记录:① 以上次全量为基线——它须满足本文「按改动范围跳过测试命令」条第 1 步对基线的两项要求,不满足的不得沿用——按该条第 2 步运行 [change-scope.mjs](change-scope.mjs),退出码为 0;② 改动后的代码上 lint 与 typecheck 都通过——lint 按能力 `lint` 判定,未启用的按全局指令「项目能力声明」节写明跳过;typecheck 即 [SKILL.md](SKILL.md) 第 4 步第 6 项所跑的那条。退出码为 0 说明改动只涉及惰性文件与只改了注释和格式的 JS/TS、Python 文件,可执行内容未变,上次全量的测试结果对改动后的代码仍然成立;脚本不区分注释是否被工具读取,lint 与 typecheck 读取的注释由 ② 核对。
- **按改动范围跳过测试命令**:复核前运行与全量里只有测试命令可以跳过——运行测试用例或被测程序的命令(单元/集成测试、e2e/端到端、冒烟测试);其余命令每次运行都必须照跑,包括 lint、类型检查、扫描仓库文件的检查与读取惰性文件(`docs/` 下的文件与所有 `.md` 文件)的命令,拿不准一条命令属于哪类的按照跑处理。项目把这些命令串成一条命令的(如依次调用各项的项目脚本),按其中的每条命令分别归类;要跳过其中的测试命令,必须拆开分别运行。测试命令运行的测试按 [SKILL.md](SKILL.md) 文首的禁止视为不读取惰性文件,无须逐个核查;已知其中有测试读取惰性文件的,运行它的命令不算测试命令,必须照跑。判定用本 skill 目录内的 [change-scope.mjs](change-scope.mjs)(它把工作区与基线提交逐文件比对,惰性文件判为 `inert`,去掉注释后语法树不变的 JS/TS 与 Python 文件判为 `same`,其余一律判为 `changed`,细则与它看不到的情形以其头部注释为准;下文命令里的 `<skill-dir>` 换成本 skill 实际所在的目录)。复核前运行,本次改动相对默认分支改动了测试文件的,不得跳过任何命令——第 6 步要从它的日志里取测试的运行结果。其余情形下能否跳过,必须按下列步骤判定,判定所用的每条命令、其完整输出与不经管道取得的退出码都必须写进该次运行的日志:
  1. **定基线**:必须取本分支上最近一次同时满足下列两项的复核前运行或全量,以其日志里 `git rev-parse HEAD` 的输出作为基线:版本清单里没有惰性文件以外的文件(否则它测的不是该提交本身);按本条跳过的命令之外,其余命令全部通过。这时可跳过的是在该次运行中完整运行过或按本条跳过的测试命令;复核前运行、或全套交给 PR 的 CI 的全量里只运行了部分用例、或因清单为空而没有运行的 e2e 命令,不算完整运行过。本分支还没有这样一次运行的,必须先拉取远端,取 `git merge-base HEAD origin/<默认分支>` 得到的分叉点作为基线,且必须先确认该提交上至少有一次默认分支的 CI 运行、全部运行的结论都是成功;这时可跳过的只限在该提交的 CI 工作流中出现过的测试命令——某个运行步骤里有一行命令以它结尾、且它前面是行首或空白(如 `xvfb-run -a pnpm e2e` 算出现了 `pnpm e2e`,`pnpm test:site` 不算出现了 `pnpm test`)。两种基线都取不到的,不得跳过任何命令。
  2. **判定改动**:必须直接在工作区运行 `node <skill-dir>/change-scope.mjs --base <基线>`,不必先暂存未跟踪的文件。
  3. **按退出码处置**:退出码 0,跳过第 1 步定下的可跳过的命令;退出码为其他值的,全部照跑。
