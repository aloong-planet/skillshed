# 文档同步与记录维护

本规范的步骤名写进记录时，必须按 [产物固定名称](../repo-scaffold/artifact-names/implement.document-sync.md) 书写。

- 定位同步材料前，必须根据任务输入和项目文档约定，列出本轮检查的具体文件、目录范围及排除项的理由；范围必须包含任务提供的文件、约定的文档与施工记录目录、根目录中的现行说明，以及发现的关联引用目标。必须在确定的范围内显式包含隐藏项和被忽略文件进行枚举与内容检索，不得使用工具默认过滤后的结果证明材料齐全；遇到新的关联引用必须补查，不得扩展到无关目录或以关联引用代替访问授权。
- 已知路径必须直接检查，不得以目录搜索无命中判断其不存在。创建或重建文档前，必须直接核对目标路径：存在时完整读取，并按下方记录维护规则就地更新；仅在确认不存在时才能新建。访问失败、读取失败、枚举失败或结果截断时，必须记录未核实范围并补查；无法补查时必须报告阻断，不得宣称范围完整、文件不存在或覆盖未读的既有文件。
- **变化到陈述的对应**：必须从任务输入、实际改动及执行结果确定变化的事实，在上述范围内核对关联文档的现行陈述并完整读取受影响内容；任务输入中的现行说明及已完成事项受影响时同样必须检查。不得仅靠已有清单、改动文件或固定关键词限定检查范围。核对所需的阅读粒度不得直接变成待办行数；清单粒度必须按 [Ticket 产物与文档同步清单](../to-tickets/ticket-artifacts.md) 执行。
- **核销前的范围复核**：交付、验收回写或文档收口前，必须从本轮任务、实际改动、执行结果与现行来源核对相关文档的现行状态是否与实际结果一致（合并后的回写除外：它以交付前的这次复核为准，见下文“合并事件按记录位置记录”），再与已有同步项对照；遗漏事项必须补入，已完成但依据失效的事项必须重开，失效说明必须按下方现行结论维护规则就地更新。必须在本轮已有清单或交叉回归报告中简记核对范围与发现的差异，不得另建一份同步台账或只检查原有行。
- 核对依据时，必须区分已取得证据与尚待补充证据的位置：已有证据必须读取并核对定位、内容、适用范围及版本是否支持结论；待补位置必须核对目标章节或字段的实际职责能否承载约定的验证结果，相关文档结构或职责改变时必须同步其引用，不能因事件尚未触发而略过。待补条件满足后必须改记实际证据，不得以文件存在、链接可打开或状态已更新代替核对。必须区分现行摘要与原始证据（命令输出、测试日志、用户消息或某次审查的原始报告）；当前结论、未解决缺陷或明确审计要求仍依赖的原始证据必须保留并引用，不得改写其事实；来源不能稳定访问时必须保存必要原文或输出及来源定位。其余历史材料不强制新增副本或台账，不得据此批量删除既有材料。
- **一个事实只写一处**：记录之间，同一事实（命令输出与退出码、测试结果、某次审查的结论与依据）只得在一处写明——原始证据写在日志或原始报告里，审查结论写在该审查的记录里；其余记录必须引用它的位置（文件与节、测试或用例编号、发现编号），可附一句结论（通过、失败、未验证），不得抄录其中的数字、清单、输出或论证。**判据**：删掉其中一处，该事实能否从剩下那处完整查到？能 → 被删的那处是复述，必须改为指针。
- 必须将现行结论与依据就地更新，注明核对日期、范围与适用版本；同一范围的旧状态摘要必须替换，不得只追加新结论而保留冲突陈述。不得为每次回写另建历史台账或强制追加历史章节；未受本轮影响的其它票、覆盖单位及适用路径的有效记录必须保留。
- 必须分别以 spec、features、ADR、CONTEXT 定义需求、当前产品行为、决策和术语，不得用施工记录替代这些权威文档；证据与权威描述不符时必须核查差异，不得只因文档层级而否定实际观测。
- 按票工作时，实际改动、审查发现或状态事件新增同步事项，必须补入本票清单，并按 [Ticket 产物与文档同步清单](../to-tickets/ticket-artifacts.md) 维护字段与状态；不得以切票时的清单限制后续范围。
- 必须按事实与授权范围更新关联现行状态；单条要求或单票完成不得推导为父级或整个 feature 完成。外部 tracker 写入缺少授权、证据无法取得或同步失败时，必须记录具体阻断并保留待处理状态，不得将记录阻断当作核销。
- **合并事件按记录位置记录**：真假只取决于某个 PR 是否合并的结论与同步事项——由该 PR 合并的结论、以该合并为触发条件的同步事项——按写在哪里分两种：
  - 写在仓库跟踪的文件里的，必须在该 PR 内写成合并后的结论，以 PR 编号指代该合并；不得在合并后为补记合并提交、合并树核对或这类状态另开 PR。PR 的内容只在合并后进入默认分支，写在其中的合并结论不会早于合并出现在默认分支上；合并提交与合并后的树在合并前无法取得，在仓库内补记它们只能再走一次合并。
  - 写在施工记录里的（施工记录不进仓库，见全局指令「施工记录存储」节），合并前不得写成已合并，合并后必须就地改为合并后的结论，写明合并提交，做了树的核对的连同其结果；同步事项的状态按 [Ticket 产物与文档同步清单](../to-tickets/ticket-artifacts.md) 的“文档同步清单结构与状态”标注。

  合并后必须取得合并提交；合并前默认分支未前进的，还必须核对合并后的树是否等于 PR 头，不等即查明差异并报告用户。tracker 在仓库外的，合并后必须回写 tracker（勾选验收项、发评论），评论必须写明合并提交，做了树的核对的连同其结果。这次回写失败时，必须按上一条（外部 tracker 写入失败须记录阻断）记录阻断：tracker 上未勾选的验收项即其待处理状态，阻断写进给用户的报告，不得为记录阻断而改动仓库。tracker 是仓库跟踪的文件或不存在时，合并后不得为回写改动仓库（由该合并决定的状态已按本条在 PR 内写成），合并提交，做了树的核对的连同其结果，必须写进给用户的报告。不经 PR 的合并（如仓库没有远端时由用户授权在本地合并分支）按本条执行时，必须以被合并的分支代替 PR、以分支名指代该合并。
