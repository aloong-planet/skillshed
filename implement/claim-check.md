# 陈述核对

本文适用于 `/implement`「收口票路径」第 4 项:把收口票写进仓库的事实陈述交给独立子 agent,逐句对照证据核对,再处置它交回的发现。入口:[SKILL.md](SKILL.md)「收口票路径」节。

本文的固定名称写进记录时,必须按 [本文的小表](../repo-scaffold/artifact-names/implement.claim-check.md) 书写,「发现」按 [review-tests 的小表](../repo-scaffold/artifact-names/review-tests.md) 书写。

## 交接

1. 工作区有未提交的仓库改动时不得交接:核对对象由 commit 范围确定,未提交的陈述不在其中。
2. 必须交给一个不继承本次对话的独立子 agent 执行:由它自己完整读取本文,执行本文「核对者的执行」节。
3. 交给它的只有:全局指令文件、本文路径、票、仓库工作区路径、陈述核对记录的路径、相对「收口票路径」第 3 项那个分叉点的 commit 范围、证据所在目录。交接中不得写入对陈述真伪的判断或取证时的推理。
4. 执行期间的禁止事项、结束信号、工具无法派生子 agent 时的办法与交回后的读取,必须按 [post-implementation-check.md](post-implementation-check.md)「本步必须交给」一段执行,其中「测试审查记录」读作陈述核对记录,「代码、测试与测试读取的数据文件」读作仓库文件与证据,「本次复核」读作本次核对,「不实的记录与证据」读作一条发现。

## 核对者的执行

1. 必须完整读取 [false-greens.md](../review-code/false-greens.md)。
2. **行集**:必须从 commit 范围的 diff 机械派生,列出范围内新增或改写的每一句陈述产品事实的话,即行为、边界、数值、阈值、测试保障或「没有测试」的说法,不论它写在 spec、features、ADR、词汇表、README、界面字典还是代码与测试的注释里。不得抽查。施工记录不进仓库,不在行集内。行集为空的,必须写明所用命令及其输出,跳到第 7 项。
3. **逐行判定**:行集的每一行都必须写明「陈述及位置」「证据位置」「核对结论」三栏,核对结论只取「成立」「不成立」「证据不足」。必须实际读取证据原文(日志行、截图、用例断言、代码),核对它的条件、版本与平台撑不撑得起这句话;票或其他文档的说法不算证据。
4. **否定陈述**:「不能」「够不到」「不会」「没有」这类陈述,必须先列出进入该状态的全部途径(如指针、键盘、程序入口、其他页面或窗口状态),再逐种指出证据;只有部分途径有证据的,判「证据不足」。
5. **读数**:读数撑不起结论的,按 false-greens.md 的形态判「证据不足」。陈述某状态如何结束或变化的,读数必须从该状态开始读,否则同样判「证据不足」。
6. **发现**:判「不成立」或「证据不足」的每一行记为一条发现,写明缺什么证据。不得改动仓库文件与证据,不得为补证新写测量:补证由主 agent 做,否则核对者就成了自己证据的取证人。
7. **记录**:必须写进陈述核对记录,注明日期、commit 范围与范围内的行集表;发现集中列在「发现」小节,逐条编号,同一份记录里不得有两条发现用同一个编号;没有发现的,该小节写明无发现。
8. **交回**:最终交回只得包含本轮结论(有无发现)、陈述核对记录的路径,以及每条发现的编号与一句话标题;其余内容只写进记录。

## 处置

1. 必须逐条处置发现:把陈述改到与证据一致,或补证。处置会改变产品行为或需要新决策的,必须报告用户,不得自行裁决。处置结论写进陈述核对记录。
2. 修复新增或改写了陈述、或为某行补了证据的,必须把这些行再交独立子 agent 增量核对:交接按本文「交接」节,行集只取修复的 commit 范围与补证的那些行。修复只删除陈述的,不再核对。
3. 修复改动了可执行内容的,必须回到「收口票路径」第 3 项。
4. 修复改变了 spec 或影响已有证据适用性的,必须按 `/features-catalog`「全 feature 收口」的「判定收口」条重核受影响项。
