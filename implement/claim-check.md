# 陈述核对

本文适用于 `/implement`「收口票路径」第 4 项:把收口票写进仓库的事实陈述逐句对照证据核对,再处置发现。入口:[SKILL.md](SKILL.md)「收口票路径」节。

本文的固定名称写进记录时,必须按 [本文的小表](../repo-scaffold/artifact-names/implement.claim-check.md) 书写,「发现」按 [review-tests 的小表](../repo-scaffold/artifact-names/review-tests.md) 书写。

## 核对的执行

工作区有未提交的仓库改动时不得开始核对:下面第 2 项的行集取自 commit 范围,未提交的陈述不在其中。

1. 必须完整读取 [false-greens.md](../review-code/false-greens.md)。
2. **行集**:必须从相对「收口票路径」第 3 项那个分叉点的 commit 范围的 diff 机械派生,列出范围内新增或改写的每一句陈述产品事实的话,即行为、边界、数值、阈值、测试保障或「没有测试」的说法,不论它写在 spec、features、ADR、词汇表、README、界面字典还是代码与测试的注释里。不得抽查。施工记录不进仓库,不在行集内。行集为空的,必须写明所用命令及其输出,跳到第 7 项。
3. **逐行判定**:行集的每一行都必须写明「陈述及位置」「证据位置」「核对结论」三栏,核对结论只取「成立」「不成立」「证据不足」。必须实际读取证据原文(命令与输出、日志行、截图、用例断言、代码),核对它的条件、版本与平台撑不撑得起这句话;票或其他文档的说法不算证据。
4. **否定陈述**:「不能」「够不到」「不会」「没有」这类陈述,必须先列出进入该状态的全部途径(如指针、键盘、程序入口、其他页面或窗口状态),再逐种指出证据;只有部分途径有证据的,判「证据不足」。
5. **读数**:读数撑不起结论的,按 false-greens.md 的形态判「证据不足」。陈述某状态如何结束或变化的,读数必须从该状态开始读,否则同样判「证据不足」。
6. **发现**:判「不成立」或「证据不足」的每一行记为一条发现,写明缺什么证据。必须判完行集的每一行并写进记录,才可开始处置:边判边改的,记录里就看不出这句话原来错在哪,发现及其处置无从复查。
7. **记录**:必须写进陈述核对记录,注明日期、commit 范围与范围内的行集表;发现集中列在「发现」小节,逐条编号,同一份记录里不得有两条发现用同一个编号;没有发现的,该小节写明无发现。

## 处置

1. 必须逐条处置发现:把陈述改到与证据一致,或补证后重判该行。处置会改变产品行为或需要新决策的,必须报告用户,不得自行裁决。处置结论写进陈述核对记录。
2. 修复新增或改写了陈述的,必须先提交修复,再只对这些行执行「核对的执行」第 2 至 7 项,行集只取修复的 commit 范围。只补证而不改陈述的,以及只删除陈述的,不再核对。
3. 修复需要可执行改动的,必须按「收口票路径」第 2 项写它,再重新执行该节第 3 项;已判定的行不因此重判。
4. 修复改变了 spec 或影响已有证据适用性的,必须按 `/features-catalog`「全 feature 收口」的「判定收口」条重核受影响项。
