# 交付与验收反馈

本文适用于 `/implement` 的两个时点:写下只有主 agent 知道的内容之后,交出文档核对、跑本地的完整运行、取证、交出交付、核对交回与合并(「交付」节);收到用户对已交付工作的反馈时(「验收反馈」节)。入口:[SKILL.md](SKILL.md)「交付」节与文首。

## 交付

### 文档核对与界面截图

1. 本次若改变**用户可见行为**,必须调 `/features-catalog`,按其「文档一致性收口」节交出文档核对并核对交回,其产出与代码进**同一个 PR**。判据是两问——对照本分支分叉点(`git merge-base HEAD origin/<默认分支>`)上的 `docs/specs/`,不对照本分支已改写的 spec,本次改动让其中陈述用户可见行为的条文**哪句话变成了谎**、又**缺了哪句话**;两问皆答「无」方可判为不改变可见行为而不交出,该判定须写进交付说明,不得默认不交出。按 [SKILL.md](SKILL.md)「收口票路径」节执行的,**不适用两问**,本项由该节第 2 项代替——两问答的是本票改动的后果,而收口票的职责恰是找出各票拼起来才出现的不一致,答案在收口跑完之前不存在。按「轻档路径」节执行的,本项由该节第 7 项代替,不交出文档核对。
2. 第 1 项**不得延后到后续 PR**:spec 描述的是默认分支上的产品,代码先合、文档后补会在两次合并之间留下 spec 说谎的窗口,而该窗口内没有任何检查会发现它。
3. 本次改动了界面、而其界面点按 `/prototype`「原型门」节判在门外的,交付说明里必须为它改动的每个界面点附一张运行中 app 的截图;app 无法运行、取不到截图的,必须逐处写明取不到及原因。

### 本地的完整运行

文档核对完成后、交出交付之前,必须按 [full-verification-gate.md](full-verification-gate.md)「每条测试命令完整运行一次」条,在本地运行 CI 不承担的测试命令与检查命令(不经 PR 交付的,即全部),并按该文件「不跑哪些」一节判定其中哪些不跑。

### 取证

跑完本地的完整运行之后、交出交付之前,必须在回复里列出这时还没有取得的每一项证据,以及取它们要运行的每条命令、要读的每个文件与要截的每张图。证据指截图、命令的输出与测量值:交付说明要附或要给出的,以及项目的指令文件(项目的 `AGENTS.md`)要求随交付取得的;项目的 `AGENTS.md` 不在上下文里的,列之前必须先读它。

- 一项证据都没有的,本节不适用。
- 命令、文件与图都列得出、且合计不足 3 个的,主 agent 必须自己取,下面各项不适用。
- 其余的(合计 3 个及以上,或其中有列不出的),必须按下面各项交给子 agent 取。

1. **交出前**:改动必须已全部提交,检出里 `git status --porcelain` 的输出为空;这时的 `git rev-parse HEAD` 即取证的 commit。
2. **交给谁**:当前工具能派子 agent 时,必须把取证交给一个不继承本次对话的子 agent(下称取证方)。当前工具能为子 agent 指定模型时,必须指定最新一代里比最小一档高一档的那一档:工具给的是档位别名的,取该档的别名;只能填具体型号的,取该档最新一代的型号,不得因为更便宜而取旧一代的型号;主会话所用已是最小一档的,取最小一档。当前工具不能派子 agent 的,主 agent 必须自己取,第 3 至 5 项不适用。
3. **交接写什么**:交给取证方的指示必须写明下列各项,缺任一项不得交出:
   1. 检出的绝对路径与取证的 commit 的完整 SHA。
   2. 要取的每一项证据及它要证明什么:界面截图的,写明界面点、截图时它要处于的状态与到达这个状态的操作步骤;票里保障写为 Evidence 的验收项的证据,照抄该项的 Evidence 原文;项目的指令文件要求的,照抄要求它的条文。
   3. 已列出的要运行的命令与要读的文件。
   4. 要取截图的,截图存放目录的绝对路径,取在交付说明所在的目录之下;不取截图的,写明「无」。
   5. 要求它每项证据都取自这个 commit 的代码运行出的结果,不改动检出里被跟踪的文件,不提交。
   6. 要求它的交回逐项写明:取到与否;取到的,截图的绝对路径,或所运行的命令、它的退出码与输出中证明该项的部分;取不到的,原因。
4. **取证进行期间**:不得改动检出,也不得提交。
5. **核对取证的交回**:收到交回后必须依次执行:
   1. 在检出里运行 `git rev-parse HEAD` 与 `git status --porcelain`。`HEAD` 不是取证的 commit,或被跟踪的文件有改动的,不得改动检出,必须停下报告用户;只列出未跟踪的文件的,必须删除其中不在截图存放目录之下的。
   2. 交回里缺第 3 项第 6 条所列内容的那几项证据,必须只就这几项再交出一次;仍缺的,主 agent 必须自己取。
   3. 交回的每张截图,主 agent 必须打开看过:它显示的是交接所写的界面点与状态的,才得附进交付说明;不是的,该项按上一条缺内容的办。
   4. 交回写明取不到的每一项证据,主 agent 必须自己取,不得只凭取证方的交回把它记为取不到。

### 交出交付

不经 PR 交付的(如仓库没有远端),不交出交付,本节与「核对交回」不适用:交付说明即给用户的报告,合并按「合并」节。

1. **交出前**:改动必须已全部提交,检出里 `git status --porcelain` 的输出为空;交付说明必须已写全 [SKILL.md](SKILL.md)「交付说明」节「内容」条所列的各项。这时的 `git rev-parse HEAD` 即交出的 commit。这个 commit 以分叉点(`git merge-base HEAD origin/<默认分支>`)为基线按 [full-verification-gate.md](full-verification-gate.md)「可执行内容变没变」条判定、退出码为 0 的,必须再判「合并」节「不经批准的合并」一条的第 2、5 项与仓库有没有由 PR 触发的 CI 工作流;都成立的,交付说明必须写明:这次改动不含可执行内容,按项目的能力声明 `docs-auto-merge`,CI 通过后即合并,不等批准。再次交出时不再都成立的,必须删去这句话。退出码不是 0 的,不判这几项,也不读该能力。
2. **交给谁**:当前工具能派子 agent 时,必须把交付交给一个不继承本次对话的子 agent(下称交付方),由它自己按当前工具的 skill 机制载入 `/github-ops` 并按其受委派交付的规则执行,不得在自己的会话里推送、开 PR 或等 CI。当前工具能为子 agent 指定模型时,必须指定最新一代里最小的一档:工具给的是档位别名的,取最小档的别名;只能填具体型号的,取最新一代的最小型号,不得因为更便宜而取旧一代的型号。当前工具不能派子 agent 的,主 agent 必须自己按 `/github-ops` 推送分支、以交付说明为描述开 PR 并等 PR 上的 CI。
3. **交接写什么**:交给交付方的指示必须写明下列各项,缺任一项不得交出:
   1. 检出的绝对路径与要推送的分支名。
   2. 交出的 commit 的完整 SHA。
   3. 交付说明文件的绝对路径,以及 PR 的标题。
   4. 本分支已有 PR 的(修复 CI 失败后再次交出时),该 PR 的地址;没有的,写明「无」。
   5. 等不等 CI:仓库里没有由 PR 触发的 CI 工作流的,写明「不等 CI」;有的,写明要传给 `watch-ci.sh` 的参数与环境变量,没有参数的写明「无」。
   6. 要求它按当前工具的 skill 机制载入 `/github-ops`,作为受委派交付的一方执行。
4. **等交回**:等它交回按全局指令「等待后台工作」进行;交付进行期间不得改动检出,也不得提交。

### 核对交回

收到交回后必须依次执行:

1. 交回缺 PR 的地址或 PR 头的 commit 的,或交接没有写明「不等 CI」而交回缺各 CI 运行的结论的,不得采信,必须按「交出交付」第 3 条再交出一次;仍缺的,必须自己按 `/github-ops` 查明所缺的各项。
2. PR 头的 commit 不是交出的 commit 的,不得报告交付完成,必须查明两者相差什么(`git log <交出的 commit>..<PR 头>` 与反向的同一条命令),报告用户。
3. CI 工作流承担的测试命令,其 job 在交回的 CI 运行里被跳过或没有出现的,必须按 [full-verification-gate.md](full-verification-gate.md)「每条测试命令完整运行一次」条判定这次要不要在 PR 头的 commit 上本地完整运行它,要的照跑。
4. 有 CI 运行的结论不是成功的,或第 3 项的本地运行失败的,这次交付没有完成:必须修复,修复按 full-verification-gate.md「修复后运行」条通过后提交,在交付说明里写明修复的 commit 范围并注明它没有经过独立审查,再按「交出交付」重新交出,等新的 CI。修复改变了文档所陈述的行为的,先按「文档核对与界面截图」第 1 项重新交出文档核对。
5. PR 头的 commit 就是交出的 commit、全部 CI 运行的结论都是成功(交接写明「不等 CI」的,没有这一项)、且第 3 项的本地运行全部通过的,才可报告交付完成,并把 PR 的地址与各 CI 运行的结论告诉用户。

### 合并

- 合并必须等用户批准,按 `/github-ops`「合并需要人明确授权」节执行;用户对交付的验收不构成合并授权。唯一的例外是下一条。
- **不经批准的合并**:按「核对交回」报告交付完成之后,必须依次判定下列各项,有一项不成立的不再判后面的各项,按上一条等用户批准;全部成立的,主 agent 必须自己合并,不问用户,即 `/github-ops`「合并需要人明确授权」节的例外:
  1. 先拉取远端,在检出的 `HEAD` 是 PR 头的 commit、`git status --porcelain` 无输出时,以 `git merge-base HEAD origin/<默认分支>` 得到的分叉点为基线,按 [full-verification-gate.md](full-verification-gate.md)「可执行内容变没变」条判定,退出码为 0。
  2. 项目能力 `docs-auto-merge` 已启用。
  3. 仓库有由 PR 触发的 CI 工作流,且 PR 头上全部 CI 运行的结论都是成功。
  4. PR 头的 commit 就是交出交付的 commit。
  5. 用户没有要求这次改动在合并之前先给他看。对话里对这次改动提的要求,与指令文件(项目的 `AGENTS.md`、用户的全局指令)里的长期要求,都算;长期要求点名文件或目录的,这个 PR 改动的文件里有一个是它点名的文件、或在它点名的目录之下,即为要求了。项目的 `AGENTS.md` 不在上下文里的,判这一项之前必须先读它。

  按本条合并之后,必须告诉用户 PR 的地址、它未经批准即已合并,以及下一条的合并提交。
- 合并之后不得再写任何东西:不写记录,不改票,不发评论。必须取得合并提交(如 `gh pr view <PR> --json mergeCommit`),把它告诉用户。

## 验收反馈

- 收到用户反馈时,必须先定位它说的是哪一次交付;无法定位时必须问清,不得猜测票号或交付。
- 用户确认验收通过的,不得为此写任何东西。
- 反馈里有缺陷或追加的范围的,它是一次新的交付:必须按 [SKILL.md](SKILL.md) 从头实施(含按其文首定档),有它自己的审查。在尚未合并的 PR 的分支上继续的,续写该 PR 的交付说明,把这次的内容另列一段;其余的另起一份交付说明。
