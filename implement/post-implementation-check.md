# 独立审查:交出、核对交回与处置发现

本文适用于 `/implement` 审查前运行通过之后、写下只有主 agent 知道的内容之前:判定是否送审,把改动交给独立执行审查的一方(下称审查方),核对它的交回,处置它交回的发现,自查修复并跑修复后运行,核心档的判定是否复审。审查方审什么、怎样交回,由它载入的 `/review-code` 与 `/review-tests` 规定,不在本文。入口:[SKILL.md](SKILL.md)「独立审查」节。

一次交付只得送审一次,唯一的例外是核心档改动按「复审」节的那一次复审,一次交付因此最多送审两次:最后一次审查交回之后的改动——处置发现的修复,或交付之前又加的别的改动——都不再送审,改动多大都一样;报告交付完成之后再改的,算一次新的交付,按本文送它自己的审查。

## 交出

1. **送审判定**:必须先拉取远端,以 `git merge-base HEAD origin/<默认分支>` 得到的分叉点为基线运行 [change-scope.mjs](change-scope.mjs)(用法见 [full-verification-gate.md](full-verification-gate.md)「可执行内容变没变」条)。退出码为 0 的,不得送审,必须在交付说明里写明这次跳过及其依据(所用命令、输出与退出码),本文其余各条不适用。退出码为 1 的,必须按下文送审,不得以实现期做过的变异检验或真实数据核验代替。判据取整个改动,不得只看测试文件:只改产品代码而不写或不改测试的改动,正是审查最要抓的情形。
2. **先提交**:交出前必须把本次改动全部提交为 commit,提交后检出里 `git status --porcelain` 的输出为空,才得交出;它列出的路径里有不属本次改动的,不得提交它们,也不得交出,必须停下报告用户——核对交回时,交出的 commit 之后的每处改动都按审查方所改处置,带着它们交出,它们会被恢复掉。这时 `git branch --show-current` 与 `git rev-parse HEAD` 给出的,即交出的分支与交出的 commit。
3. **交给谁**:当前工具能派子 agent 时,必须把审查交给一个不继承本次对话的子 agent 作为审查方,由它自己按当前工具的 skill 机制载入 `/review-code` 与 `/review-tests` 并执行——执行审查的是子 agent 本身,不属于让子 agent 代读 skill。不得为审查方指定模型。当前工具不能派子 agent 的,主 agent 必须自己载入这两个 skill,作为审查方按其中受交接执行独立审查的规则执行,并在交付说明里写明这次审查不是独立执行的。
4. **交接写什么**:交给审查方的指示必须写明下列各项,缺任一项不得交出:
   1. 检出的绝对路径。
   2. 审查范围起点的完整 SHA 与交出的 commit 的完整 SHA;范围起点是分叉点,按「复审」节复审时是第一次交出的 commit。
   3. 本次改动触碰的 spec 的 slug;一份都没触碰的,写明「无」。
   4. 按票的,票的标识与位置(本地票文件的绝对路径,或 tracker 上的票号);不按票的,写明「无」。
   5. 本次改动是不是核心档:是的,写明「核心档」;不是的(含不定档位的收口票),写明「不是核心档」。
   6. 要求它按当前工具的 skill 机制载入 `/review-code` 与 `/review-tests`,作为受交接的独立审查方执行审查。

   不得写入对代码或测试的判断、改动是怎样做出的,也不得写入作者计划的用例清单。
5. **等交回**:等它交回按全局指令「等待后台工作」进行。审查进行期间,主 agent 不得改动该检出里的代码、测试与测试读取的数据。审查以审查方的最终交回为完成;交回之前它写下或运行的任何东西都不是完成的信号。
6. **没有交回**:审查方没有交回就结束的(崩溃、中断、上下文耗尽),或交回里没有「检查过的验收条件数」与「审过的测试数」的,或交接写明「核心档」而交回里没有「核对过的代价条目数」的,必须按第 4 条以同样的指示再交出一次;仍是如此的,主 agent 必须自己按第 3 条「不能派子 agent」的做法执行审查,并在交付说明里写明这次审查不是独立执行的。

## 核对交回

收到交回后,必须先在检出里运行 `git branch --show-current` 与 `git rev-parse HEAD`,与第 2 条记下的分支与交出的 commit 对照:

- 分支不是交出的分支,或交出的 commit 不是 `HEAD` 的祖先(`git merge-base --is-ancestor <交出的 commit> HEAD` 的退出码非 0)的,不得改动检出,必须停下报告用户。
- `HEAD` 不是交出的 commit 的,即审查方提交了,必须先运行 `git reset --soft <交出的 commit>` 把它的提交撤回工作区。
- 再运行 `git status --porcelain` 与 `git diff --name-only <交出的 commit>`,列出自交出的 commit 以来改动的全部路径(含未跟踪的新文件);除主 agent 在等待期间自己改的之外,每个路径都必须恢复到交出的 commit 的状态(`git checkout <交出的 commit> -- <路径>`;该 commit 里没有的新文件删除)。撤回了提交或恢复了路径的,必须报告用户撤回与恢复了什么;交回的发现照常使用。

## 处置发现

- **记下每条发现**:动手处置任何一条之前,必须把交回的每条发现写进交付说明(见 [SKILL.md](SKILL.md)「交付说明」节),并为每条写明该节「内容」条的三种处置之一。
- **留给用户决定**:解决一条发现需要 spec 没有写明、而又会改变可观察行为的东西(还有谁能改这份数据、产品运行在哪里、两种说得通的行为要哪一种)的,留给用户决定。能不等这个决定继续做下去的,保留现有行为;不能的,实现主 agent 推荐的行为,并在交付说明里该条发现下标明它是暂定的;两者在用户决定之前都不得写进 spec。这样的发现不阻挡交付。
- **不同意的不丢**:主 agent 不同意的发现,不得删去,必须列为不修,把发现与主 agent 的理由并排写出。
- **陈述不实的先改陈述**:`/review-tests`「不实的证据」一类的发现,必须把那条陈述改到与事实一致;只有它所下的结论是消除一条「缺陷」或「会漏掉的回归」所必需的,才改为补足证据。
- **修复自己写**:修复必须由主 agent 自己写;交回里即便带了补丁、修复草稿或测试草稿,也不得照搬。
- **修复自查**:每处修复写完、运行任何命令之前,必须逐项查:
  1. 修复改动的产品代码,与它实现的 spec 条文逐句并排核对。
  2. 修复新写或改动的每个断言,按 `/tdd`「反模式」节「假通过」一条的形态逐个核对。
  3. 修复改动的每个函数,其中每个分支、每个退出路径(返回、抛出、超时)与每个被钳制的取值,都指得出驱动它的测试;指不出的,按 `/tdd`「覆盖来源」节「测不到的」一条注明为缺口。
  4. 修复改动的共享测试辅助代码(fixture、测试替身、helper):按 [full-verification-gate.md](full-verification-gate.md)「审查前运行」条的导入关系检索在全仓找出它的使用者,除去修复后运行将运行的测试文件,余下的(证据脚本、证据服务器等)逐个运行或核对。

  查出的问题必须修掉,修完对新的修复重做这四项;自查本身不写下来。
- **修复后运行**:有修复的,自查完成后必须按 full-verification-gate.md「修复后运行」条跑修复后运行,通过后把修复提交为 commit。

## 复审

只适用于按「交出」送过审的核心档改动:第一次审查的发现处置完毕、有修复的其修复后运行通过之后,必须以第一次交出的 commit 为基线运行 [change-scope.mjs](change-scope.mjs)(用法见 [full-verification-gate.md](full-verification-gate.md)「可执行内容变没变」条),取它判为 `changed` 的路径——只改了文档、注释或排版的文件不在其中。

- 其中有测试文件与测试读取的数据以外的路径(即此后的 commit 改动了产品代码)的,必须把这些 commit 复审一次:按「交出」第 2 至 6 条交出,第 4 条第 2 项的范围起点写第一次交出的 commit,交出的 commit 写这时的 `HEAD`;按「核对交回」核对交回,按「处置发现」处置复审的发现。
- 判为 `changed` 的路径全是测试文件与测试读取的数据的,或一个都没有的,不复审。

## 没有审过的范围

最后一次交出的 commit 之后凡改动了代码、测试或测试读取的数据的 commit(修复,或交付之前又加的别的改动),必须在交付说明里写明其范围,并注明它们没有经过独立审查。
