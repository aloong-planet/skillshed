本 skill 把**当前对话上下文** + 代码库理解合成为一份 spec(即 PRD)。**不采访用户**——只合成已知内容;对话里没有的东西合成不出来,所以必须与 `/grill-with-docs` 的需求对齐处在同一个上下文窗口。

## spec 是持久产物

必须将 spec 作为持久文档写入 `docs/specs/`，与 `docs/features/`、`docs/adr/` 同级维护，不得随 tickets 或施工记录的清理而丢弃。必须在 spec 中保留功能穷举过的边界和明确不做的范围，供后续开发判断需求覆盖；文档职责按下方分工表执行。

- **粒度**:一个功能模块一篇,**slug 与 `docs/features/` 一一对应**(features 有 `memory-view.md`,spec 就是 `docs/specs/memory-view.md`)。一次开发跨多个模块时产出/更新多篇。
- **生命周期**:同 features——**现行描述、就地改写**,不记变更史(变更史在 git),功能移除即删文件。既有功能的增量开发是**改写既有 spec**,不新开文件。
- **与 features 的分工**(定死,不要每次重判):

  | | docs/features/ | docs/specs/ |
  |---|---|---|
  | 读者 | 用户/产品视角 | 要改这块代码的人 |
  | 内容 | 当前可见行为的能力清单 | 需求全景:用户故事、**失败模式与边界穷举**、测试决策、明确不做 |
  | 细节 | 零实现细节 | 抽象层的实现决策(不写路径与代码片段) |

- **决策取舍归 ADR**:spec 只引用 ADR 编号,不复述取舍过程;spec 里的决策若够 ADR 门槛(判据见 domain-modeling),落 ADR 后 spec 改为引用。
- **不得引用会被清理的临时物**：spec 不得引用票号、分支名、施工记录路径等临时材料，避免持久文档的引用随临时材料清理而失效。要标时间用日期；标注出处时，可以引用持久化的 spec 主定义或 ADR。跨 spec 引用的标识与路径必须按 [requirement-identifiers.md](requirement-identifiers.md) 的“完整标识与模板占位符”执行。
- **尚未落地的事实写成 `Pending:` 注记**:形如 `> Pending: <条件>`,条件必须是能对着实现判真假的产品事实,不得写成"待某票/某人/某轮"——这样它到期与否只取决于文档与实现的现状,收口时逐条重判即可。
- **`Pending:` 一到期就处置,三选一,都不得留下"曾经没有"的痕迹**(spec 描述现状,历史在 git):条件消失且事实已平常 → 删注记;事实仍需被陈述 → 改写成普通现在时正文;条件转为"决定不做" → 移入 Out of Scope 或边界条目,带理由不带时间线。
- **一致性**:spec 与 features/ADR/CONTEXT 的交叉一致由第 8 步收尾统一回归(见 features-catalog skill)。

## 流程

### 准备：读取规范

必须先完整读取 [requirement-identifiers.md](requirement-identifiers.md) 并按其定义组织需求和验收标识。

### 准备：核对记录约定

必须在“盘点已确认来源”和“发布前设计自审”各自执行时，将结果写入或复用 `docs/.workings/<slug>/checklist.md` 的“来源 → spec”部分，记录需求来源、spec 路径、本轮 spec 的 commit 参考及逐项结论；该文件不存在时必须按 `/to-tickets` 的 `<checklist-template>` 创建，不得预填 ticket 归属或通过证据。读取模板时必须完整读取对应 SKILL.md，但不得因此执行拆票流程或提前分配 tickets。必须仅用 commit 记录 spec 与实现的版本参考，不得要求内容指纹或用自然语言摘要充当版本；包含未提交修改时必须注明该事实，无可用 commit 时必须如实标明，不能伪造或为填字段擅自提交。commit 只是参考，必须结合当前内容和实际变更核对证据适用性。必须将该文件作为可复查的工作索引而非需求权威；再次使用时必须按当前阶段的核对职责对照现行来源重核；spec 的引用边界必须遵守“spec 是持久产物”中的临时物限制。

### 合成与发布

1. **探代码库**(若还没探):spec 通篇使用项目词汇表(CONTEXT.md)的语言;**尊重所触及区域的 ADR**——对话内容与某 ADR 冲突时指出冲突,不默写进去。
2. **盘点已确认来源**：必须盘点当前上下文中已达成共识的来源，并对照既有 spec、CONTEXT 和相关 ADR。必须逐项记录来源锚点及支持原文，区分“本轮确认且有效”“已被后续决定取代”“背景”“明确不做”；必须核对后续修订，不得仅从最新一句或旧清单推断完整范围。不得把实现现状等同于用户要求。存在缺失上下文、歧义、冲突或未确认的新范围时，必须指出具体缺口并回到需求对齐；不得自行补成已确认需求，也不得重复询问已有明确共识的项目。
3. **勾画测试 seam**(seam 的定义见 `/tdd`):优先复用既有 seam;取最高层,测试基建撑不住最高层时才下探;越少越好(理想为 1)。seam 不明或需新建时问用户确认,否则自己定。结果写进 Testing Decisions。
4. **界面决策的原型门**:spec 若含**用户可见的界面变化**,先确认对应原型已存在、已更新到该 spec 描述的形态、且经用户确认;不满足就先跑 `/prototype`,不用散文描述界面替代。
   - 判定方式:把 spec 涉及的界面点逐条列出(新增/改动的页面、分栏、控件、状态、**配色与间距**),每条指出它在哪个原型里可见;列不出来的就是缺原型。
   - 例外(**必须显式声明理由**后才可跳过,心里豁免等于违规):纯文案、纯数据口径调整、无可见变化的重构。**新增状态形态(空态/提示态/降级态)不算纯文案。**
   - spec 里写**结论**(布局方向、交互规则、边界行为、色值),不写原型文件路径——原型会被合并重构,路径会腐烂。
5. **写 spec**(模板见下)：必须按共享规范的“核对范围与旧格式接续”确定本轮有效需求，为范围内条目建立唯一主定义和验收定位。必须检查所有章节中的规范性内容，包括 User Stories、失败模式、Implementation Decisions、Testing Decisions 和 Further Notes，以发现适用约束及受影响的回归条件；是否纳入本轮承兑与是否补齐标识，必须按上述范围条文判断。背景、设计解释、测试方法和 Out of Scope 必须明确归类，不得把绑定要求藏入未核对的备注。
6. **发布前设计自审**(发布门禁——审设计本身,独立于实现后的 /review-code):
   - **来源与 spec 双向核对**：必须先从“盘点已确认来源”步骤的每项有效来源检查对应 spec 覆盖单位，再从共享规范规定的本轮核对范围内每项规范性 spec 内容反查已确认来源；必须逐项核对前提、分支、例外、否定限制和适用范围是否保留。发现遗漏必须补齐；发现未授权扩张或冲突必须回到对齐；任一缺口未解决，不得把 spec 标为可供拆票或实施。不得以编号齐全替代本步骤其余设计审查项。
   - 必须检查决策之间的矛盾与未消解依赖，并在发布前解决发现的问题；
   - 必须按“界面决策的原型门”的界面点清单逐项复核原型覆盖与用户确认，不得用整体印象代替；
   - 必须按用户真实操作序列核对“失败模式与边界”，不得按准备修改的代码限定场景；涉及状态/effect 时必须列全各状态的进入和退出路径，并从场景推导依赖数组与边界，不得以改动最少为依据删去场景；
   - 逻辑漏洞、考虑欠缺处,补全后再发布。
7. **发布**:写入 `docs/specs/<slug>.md`(slug 与生命周期见上方「spec 是持久产物」节)。首次建立时一并铺 `docs/specs/README.md`(索引 + 不变量,格式仿 features/ADR 的 README)。
   - 用真 tracker 时:spec 仍落 `docs/specs/`(它是持久产物),tracker 上放的是切出来的 **tickets**(`/to-tickets`);tracker 与标签约定读 `docs/agents/issue-tracker.md`,没有就先跑 `/repo-scaffold`。

## Spec 模板

必须从已确认需求填写模板占位内容；章节是否生成、标识及粒度必须按 [需求标识与覆盖单位](requirement-identifiers.md) 的“唯一主定义”和“覆盖单位”执行。模板与本文件写进项目产物的内容（固定名称、占位符里的填写指引与叙述句），必须按 [产物固定名称](../repo-scaffold/artifact-names.md) 书写。

```md
# {功能名,与 docs/features/<同 slug>.md 同名}

> 关联: [features](../features/<slug>.md) · {ADR-XXXX,如有}

## Problem Statement
{用户视角的问题}

## Solution
{用户视角的解法}

## User Stories

### <spec-slug>::US-001 <故事标题>

<已确认的用户角色、目标与收益>

- <spec-slug>::US-001/AC-01：<保留前提、动作及可观察结果的独立验收条件>
- <spec-slug>::US-001/AC-02：<另一项独立验收条件>

## Functional Requirements

### <spec-slug>::REQ-001 <标题>（直接验收）

<单一、明确且可核验的功能条件>

## Quality Requirements

### <spec-slug>::QR-001 <质量要求标题>

适用范围：<已确认的范围>

- <spec-slug>::QR-001/AC-01：<已确认的适用条件、测量口径与合格标准>

## Constraints

### <spec-slug>::CON-001 <约束标题>（直接验收）

适用范围：<已确认的范围>；<可直接验证的约束条件>

## 失败模式与边界
{按用户真实操作序列穷举:边界值、错误/失败路径、并发与 race、中断与恢复、
空/异常输入、与既有功能交互的回归点。每条写明预期行为。
**另加一维:引入内容带来的能力**——见下方说明。
必须把本节纳入全 spec 覆盖核对；已经在其它条目定义的条件必须引用其标识，不得另建同义验收项。}

## Implementation Decisions
{要建/改的模块、接口、架构决策、schema 变更、API 契约、具体交互。
**不写文件路径与代码片段**(很快过时)。
唯一例外:prototype 产出的、比散文更精确的决策性片段(状态机/reducer/schema/类型形状),
裁剪到只剩决策部分,注明来自 prototype。}

## Testing Decisions
{什么算好测试(只测外部行为,不测实现细节);测哪些模块(=“勾画测试 seam”步骤确认的 seams);
代码库里的既有先例(prior art)。}

## Out of Scope
{明确不做的}

## Further Notes
{其余备注}
```

### 失败模式的第二维:引入内容带来的能力

按操作序列穷举只覆盖**你亲手写的交互面**。但把外部内容(用户文档、配置、agent 生成物、
第三方数据)渲染或加载进 app 时,**渲染器/框架/平台会凭空造出你没写过的交互面**——
它们同样是真实的用户可点、可触发的东西,却不在任何操作序列里。

所以除"数据出问题怎么办"外,再问一遍:**这些内容能对宿主做什么?**

- **链接**:点击会不会导航整窗/开新窗口?站内、站外、危险协议各自的归宿?
- **图片/媒体**:相对路径怎么解析?能不能引用本机任意路径?加载失败什么样?
- **脚本/样式/iframe/webview**:能不能注入?被剥除后留下什么可见残骸?
- **表单/可交互元素**:提交去哪?
- **拖放/粘贴**:拖进来的文件被谁接管?
- **超大/畸形内容**:渲染是否卡死、是否撑破布局?

**判据**:逐个渲染/加载点问——"这里除了我写的元素,渲染器/框架还会生成什么用户能触发的东西?"
凡是**代码里没有对应的一行、但用户能点/能拖/能触发**的,都要有一条边界。

**同一内容有两个独立边界,不可互相顶替**:消毒(内容安全,防注入)与行为归宿(点了会怎样)。
消毒库的职责恰恰是**保留良性元素**——过了消毒不代表行为已定义。

### 模板与持久化的配合

各节的腐烂速度不同,回归时按此处理——

- **Problem/Solution/User Stories/Functional Requirements/Quality Requirements/Constraints/失败模式与边界/Out of Scope**:长期主体,就地改写保持与实现一致;
- **Implementation Decisions**:只留抽象层决策;已腐烂的实现细节(具体类型名/模块划分)删除而非保留;
- **Testing Decisions**:seam 选择长期有效;具体用例清单不进 spec(在测试文件里)。
