description: 把已达成共识的需求合成为持久 spec。需求讨论完成、准备拆票或实施时使用；需求仍待澄清时使用 grill-with-docs。
---

本 skill 把**当前对话上下文** + 代码库理解合成为一份 spec(即 PRD)。**不采访用户**——只合成已知内容;对话里没有的东西合成不出来,所以必须与 `/grill-with-docs` 的需求对齐处在同一个上下文窗口。

## 流程

### 准备：读取规范

必须先完整读取 [requirement-identifiers.md](requirement-identifiers.md) 与 [spec-writing.md](spec-writing.md),按前者组织需求和验收标识,按后者写 spec。

### 准备：核对记录约定

必须在“盘点已确认来源”和“发布前设计自审”各自执行时，将结果写入或复用 `docs/.workings/<slug>/checklist.md` 的“来源 → spec”部分，记录需求来源、spec 路径、本轮 spec 的 commit 参考及逐项结论；该文件不存在时必须按 `/to-tickets` 的 [feature-checklist.md](../to-tickets/feature-checklist.md) 中的 `<checklist-template>` 创建，只建文件头与“来源 → spec”部分，不得预填 ticket 归属。读取模板时必须完整读取该文件，但不得因此执行拆票流程或提前分配 tickets。必须仅用 commit 记录 spec 与实现的版本参考，不得要求内容指纹或用自然语言摘要充当版本；包含未提交修改时必须注明该事实，无可用 commit 时必须如实标明，不能伪造或为填字段擅自提交。commit 只是参考，必须结合当前内容和实际变更核对证据适用性。必须将该文件作为可复查的工作索引而非需求权威；再次使用时必须按当前阶段的核对职责对照现行来源重核；spec 的引用边界必须遵守 spec-writing.md「不得写,以及不得留下的内容」节 4.8。

### 合成与发布

1. **探代码库**(若还没探):spec 通篇使用项目词汇表(CONTEXT.md)的语言;**尊重所触及区域的 ADR**——对话内容与某 ADR 冲突时指出冲突,不默写进去。
2. **盘点已确认来源**：必须盘点当前上下文中已达成共识的来源，并对照既有 spec、CONTEXT 和相关 ADR。必须逐项记录来源锚点及支持原文，区分“本轮确认且有效”“已被后续决定取代”“背景”“明确不做”，这四种处置写进清单时必须按 [产物固定名称](../repo-scaffold/artifact-names/to-spec.md) 书写；必须核对后续修订，不得仅从最新一句或旧清单推断完整范围。不得把实现现状等同于用户要求。存在缺失上下文、歧义、冲突或未确认的新范围时，必须指出具体缺口并回到需求对齐；不得自行补成已确认需求，也不得重复询问已有明确共识的项目。`docs/.workings/<slug>/alignment.md` 存在时必须完整读取，逐条与对话核对后计入来源；与对话不符或在对话里找不到依据的条目，按上一句的缺口处理。
3. **界面决策的原型门**:spec 若含**用户可见的界面变化**,必须按 `/prototype`「原型门」节过门,界面点取 spec 涉及的界面点;未过门的先跑 `/prototype`,不用散文描述界面替代。
4. **写 spec**(模板与各节写法见 spec-writing.md「模板与逐节写法」节)：必须按共享规范的“核对范围与旧格式接续”确定本轮有效需求，为范围内条目建立唯一主定义和验收定位。必须检查所有章节中的规范性内容，包括 User Stories、失败模式、Implementation Decisions 和 Further Notes，以发现适用约束及受影响的回归条件；是否纳入本轮承兑与是否补齐标识，必须按上述范围条文判断。背景和 Out of Scope 必须明确归类，不得把绑定要求藏入未核对的备注。
5. **发布前设计自审**(发布门禁,审设计本身):
   - **来源与 spec 双向核对**：必须先从“盘点已确认来源”步骤的每项有效来源检查对应 spec 覆盖单位，再从共享规范规定的本轮核对范围内每项规范性 spec 内容反查已确认来源；必须逐项核对前提、分支、例外、否定限制和适用范围是否保留。发现遗漏必须补齐；发现未授权扩张或冲突必须回到对齐；任一缺口未解决，不得把 spec 标为可供拆票或实施。不得以编号齐全替代本步骤其余设计审查项。
   - 必须检查决策之间的矛盾与未消解依赖，并在发布前解决发现的问题；
   - 必须按“界面决策的原型门”的界面点清单，对判在门内的每一项复核原型覆盖与用户确认，不得用整体印象代替；
   - 必须按 spec-writing.md「失败模式与边界的写入条件」节逐条核对“失败模式与边界”本轮新增的条目，并核对属该节所列各类的情形都已写成条目；
   - 逻辑漏洞、考虑欠缺处,补全后再发布。
6. **发布**:按 spec-writing.md「spec 放在哪、一篇写多大范围」「大小上限」「功能拆分」「索引 README」各节写入 `docs/specs/` 并改索引。
