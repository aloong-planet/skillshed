本 skill 把**当前对话上下文** + 代码库理解合成为一份 spec(即 PRD)。**不采访用户**——只合成已知内容;对话里没有的东西合成不出来,所以必须与 `/grill-with-docs` 的需求对齐处在同一个上下文窗口。
tracker 与标签约定读 `docs/agents/issue-tracker.md`(没有就先跑 `/repo-scaffold`)。

## spec 是持久产物(2026-08-01 定案)

spec **不是**用完即丢的施工文档——tickets 才是。spec 归 `docs/specs/`,与 `docs/features/`、`docs/adr/` 同级长期维护:它是全套文档里**唯一**记录「这个功能穷举过哪些边界、哪些明确不做」的地方(ADR 记决策取舍、features 记当前行为,都不覆盖这一层)。丢掉它,下一个改这块代码的人(或模型)无从判断自己是否想全了。

- **粒度**:一个功能模块一篇,**slug 与 `docs/features/` 一一对应**(features 有 `memory-view.md`,spec 就是 `docs/specs/memory-view.md`)。一次开发跨多个模块时产出/更新多篇。
- **生命周期**:同 features——**现行描述、就地改写**,不记变更史(变更史在 git),功能移除即删文件。既有功能的增量开发是**改写既有 spec**,不新开文件。
- **与 features 的分工**(定死,不要每次重判):

  | | docs/features/ | docs/specs/ |
  |---|---|---|
  | 读者 | 用户/产品视角 | 要改这块代码的人 |
  | 内容 | 当前可见行为的能力清单 | 需求全景:用户故事、**失败模式与边界穷举**、测试决策、明确不做 |
  | 细节 | 零实现细节 | 抽象层的实现决策(不写路径与代码片段) |

- **决策取舍归 ADR**:spec 只引用 ADR 编号,不复述取舍过程;spec 里的决策若够 ADR 三门槛,落 ADR 后 spec 改为引用。
- **一致性**:spec 与 features/ADR/CONTEXT 的交叉一致由第 8 步收尾统一回归(见 features-catalog skill)。

## 流程

1. **探代码库**(若还没探):spec 通篇使用项目词汇表(CONTEXT.md)的语言;**尊重所触及区域的 ADR**——对话内容与某 ADR 冲突时指出冲突,不默写进去。
2. **勾画测试 seam**:优先复用既有 seam;取最高层,测试基建撑不住最高层时才下探;越少越好(理想为 1)。seam 不明或需新建时问用户确认,否则自己定。结果写进 Testing Decisions。
3. **界面决策的原型门**:spec 若含**用户可见的界面变化**,先确认对应原型已存在、已更新到该 spec 描述的形态、且经用户确认;不满足就先跑 `/prototype`,不用散文描述界面替代。
   - 判定方式:把 spec 涉及的界面点逐条列出(新增/改动的页面、分栏、控件、状态、**配色与间距**),每条指出它在哪个原型里可见;列不出来的就是缺原型。
   - 视觉微调同样入门(改色、调间距)——它们是真实的设计决策,散文描述不出效果,只有并排看才判得了。
   - 例外(说明理由后跳过):纯文案、纯数据口径调整、无可见变化的重构。
   - spec 里写**结论**(布局方向、交互规则、边界行为、色值),不写原型文件路径——原型会被合并重构,路径会腐烂。
4. **写 spec**(模板见下)。
5. **发布前设计自审**(发布门禁——审设计本身,独立于实现后的 /review-code):
   - 决策之间有无矛盾/依赖未消解;
   - 涉及界面的需求是否**逐点**都有已确认的原型覆盖(对着界面点清单核,不是"大概有");
   - 「失败模式与边界」节是否按**用户真实操作序列**穷举(不按"我要改的代码"穷举);涉及状态/effect 时,"该状态能从哪些路径进入/退出"是否列全;依赖数组、边界由**场景**推导,不由"最小"推导;
   - 逻辑漏洞、考虑欠缺处,补全后再发布。
6. **发布**:写入 `docs/specs/<slug>.md`(slug 与生命周期见上方「spec 是持久产物」节)。首次建立时一并铺 `docs/specs/README.md`(索引 + 不变量,格式仿 features/ADR 的 README)。
   - 用真 tracker 时:spec 仍落 `docs/specs/`(它是持久产物),tracker 上放的是切出来的 **tickets**(`/to-tickets`)。

## Spec 模板

```md
# {功能名}(与 docs/features/<同 slug>.md 同名)

> 关联: [features](../features/<slug>.md) · ADR-XXXX(如有)

## Problem Statement
{用户视角的问题}

## Solution
{用户视角的解法}

## User Stories
{长编号列表:"As an <actor>, I want <feature>, so that <benefit>"。极尽详尽,覆盖功能所有侧面。}

## 失败模式与边界
{按用户真实操作序列穷举:边界值、错误/失败路径、并发与 race、中断与恢复、
空/异常输入、与既有功能交互的回归点。每条写明预期行为。
**另加一维:引入内容带来的能力**——见下方说明。
此节是下游按条核销的共同依据——/tdd 的覆盖清单、/review-tests 的覆盖维度、/to-tickets 的功能验收清单都从它逐条派生。}

## Implementation Decisions
{要建/改的模块、接口、架构决策、schema 变更、API 契约、具体交互。
**不写文件路径与代码片段**(很快过时)。
唯一例外:prototype 产出的、比散文更精确的决策性片段(状态机/reducer/schema/类型形状),
裁剪到只剩决策部分,注明来自 prototype。}

## Testing Decisions
{什么算好测试(只测外部行为,不测实现细节);测哪些模块(=第 2 步确认的 seams);
代码库里的既有先例(prior art)。}

## Out of Scope
{明确不做的}

## Further Notes
{其余备注}
```

### 失败模式的第二维:引入内容带来的能力(2026-08-02 定案)

按操作序列穷举只覆盖**你亲手写的交互面**。但把外部内容(用户文档、配置、agent 生成物、
第三方数据)渲染或加载进 app 时,**渲染器/框架/平台会凭空造出你没写过的交互面**——
它们同样是真实的用户可点、可触发的东西,却不在任何操作序列里。

所以除"数据出问题怎么办"外,再问一遍:**这些内容能对宿主做什么?**

- **链接**:点击会不会导航整窗/开新窗口?站内、站外、危险协议各自的归宿?
- **图片/媒体**:相对路径怎么解析?能不能引用本机任意路径?加载失败什么样?
- **脚本/样式/iframe/webview**:能不能注入?被剥除后留下什么可见残骸?
- **表单/可交互元素**:提交去哪?
- **拖放/粘贴**:拖进来的文件被谁接管?
- **超大/畸形内容**:渲染是否卡死、是否撑破布局?

**判据**:逐个渲染/加载点问——"这里除了我写的元素,渲染器/框架还会生成什么用户能触发的东西?"
凡是**代码里没有对应的一行、但用户能点/能拖/能触发**的,都要有一条边界。

**同一内容有两个独立边界,不可互相顶替**:消毒(内容安全,防注入)与行为归宿(点了会怎样)。
消毒库的职责恰恰是**保留良性元素**——过了消毒不代表行为已定义。

### 模板与持久化的配合

各节的腐烂速度不同,回归时按此处理——

- **Problem/Solution/User Stories/失败模式与边界/Out of Scope**:长期主体,就地改写保持与实现一致;
- **Implementation Decisions**:只留抽象层决策;够 ADR 门槛的落 ADR 后改为引用编号;已腐烂的实现细节(具体类型名/模块划分)删除而非保留;
- **Testing Decisions**:seam 选择长期有效;具体用例清单不进 spec(在测试文件里)。
