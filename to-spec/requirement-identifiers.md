# 需求标识与覆盖单位

## 唯一主定义

必须按下表选择需求的唯一主定义；同一义务不得同时复制为 REQ、US、QR 或 CON。必须通过引用表达共享关系，不得为了填满类别创建无内容章节。

| 前缀 | 必须采用的选用判据 |
|---|---|
| US | 必须用于以用户角色、目标和收益表达的功能需求 |
| REQ | 必须用于直接陈述、无需改写成用户故事的功能行为或规则；不得作为包住所有其它类别的额外父层 |
| QR | 必须用于质量属性及其可判定目标；必须写明适用条件、评价口径和合格标准，不得擅自补数值 |
| CON | 必须用于已确定的解法限制或边界约束；必须写明限制对象及适用范围 |
| AC | 必须用于具体化一个 REQ、US、QR 或 CON 的独立验收条件，不得当作 ticket 或实现步骤 |

## 覆盖单位

必须把可独立失败的行为、分支或限制分别写成验收条件，保留共享前提、例外和否定限制。必须为 US 写明 AC；其它需求若正文已经是单一、明确可核验的条件，可直接以该需求 ID 作为覆盖单位，标明“直接验收”；否则必须细化 AC。含 AC 的需求必须核对父项正文是否全部落实到 AC，不得用子项列表掩盖父项未细化的义务。

## 局部编号

必须以 `<类型>-<序号>` 构成需求的局部编号，例如 `US-001`；必须以 `<父需求局部编号>/AC-<序号>` 构成验收条件的局部编号，例如 `US-001/AC-01`。必须在一篇 spec 内保持需求局部编号唯一、在同一父需求内保持 AC 序号唯一；不得从章节顺序或 ticket 编号推导需求身份。主定义及引用的完整标识必须按下条“完整标识与模板占位符”生成，不得将这里的局部编号示例当成可直接使用的完整标识。

## 完整标识与模板占位符

必须以 `<spec-slug>::<局部编号>` 作为需求及验收条件的完整标识，`<spec-slug>` 必须取该项主定义所属 spec 的文件名主体；例如 `docs/specs/history.md` 中的验收条件写作 `history::US-001/AC-01`。必须在 spec 的主定义与内部引用、清单、ticket 及验收证据索引中使用完整标识，不得因只涉及一份 spec 而省略前缀。通用模板必须使用 `<spec-slug>` 占位；生成实际文件时必须替换为对应值，不得把 `history` 固定套用到其它 spec，也不得保留未替换的占位符。在 spec 外引用或引用另一份 spec 时，必须提供对应命名空间的 spec 相对路径引用：本地 Markdown 文件必须以引用文件所在目录为基准生成链接；tracker 票必须以所属仓库根目录为基准记录 spec 路径，并结合已配置 tracker 的仓库上下文解析，不得将该路径冒充已验证可点击的网页链接。清单必须在文件头、ticket 必须在“需求来源”区集中列出各命名空间对应的引用，映射行使用完整标识；另一篇 spec 中的引用必须在引用处链接其主定义文档；不得使用本机绝对路径。本篇 spec 内部引用不要求重复自链接。不得在覆盖表或 ticket 中为同一覆盖单位另造 R 编号或票内产品 AC 编号。

引用示例（说明上述条文，不增加另一套规则）：

| 场景 | 写法 |
|---|---|
| history spec 的主定义、内部引用，或只引用该 spec 的清单 | `history::US-001/AC-01` |
| 同一 ticket 同时承兑历史管理和 Provider 配置 | `history::US-001/AC-01` 与 `provider::US-001/AC-01`，分别链接各自 spec |
| Provider spec 引用安全 spec 中的日志限制 | `security::CON-001`，链接其主定义，不复制成 Provider 的新需求 |

这些跨功能例子不代表每个项目必须拆成这些 spec，也不增加命名空间管理脚本。

## 稳定身份与变更授权

实质改变已确认的产品需求、验收条件或票范围时，必须先取得用户确认并记录依据，再更新权威来源；修正错字或落实已有明确决定不得重复申请确认。修改需求时，若义务身份未变，必须保留 ID 并记录本轮来源 commit 参考；新增独立义务必须分配新 ID。删除、拆分或合并需求时，必须在工作核对记录中保留旧→新或批准移除的对应关系并更新受影响引用；不得复用已撤销 ID。必须结合现行文档与版本历史确认编号是否用过，不得只取现存最大值后声称从未复用。需求历史仍归版本历史与工作记录，不得把历史流水塞进现行 spec。

## 共享适用范围

必须为共享需求明确适用的功能或场景；其主定义与引用必须遵守前文的唯一主定义条文。必须按内容区分质量属性、功能行为和解法限制，不得仅因“安全”“全局”或“跨功能”等字眼决定前缀；复合义务的拆分必须遵守前文的覆盖单位条文。

## 技术前提与流程验收

必须区分产品验收条件与实现/验证前提。技术前提必须在 ticket 中标为“技术前提”并引用所支撑的覆盖单位；工作流要求必须标为“流程验收”并引用规定该步骤的流程。不得为了给准备工作凑产品 ID 而向 spec 增加虚构需求；技术工作若改变产品行为或已确认约束，必须先对齐并更新 spec。

## 核对范围与旧格式接续

必须完整读取当前 spec 后确定本轮核对范围：首次建设 feature 或全 feature 收口时，必须覆盖该 feature 的全部有效覆盖单位；增量开发时，必须覆盖新增或修改的义务、适用的共享约束及受本轮改动影响的既有回归条件。其余章节或条目必须记录“不受本轮影响”及依据，不得将其等同于产品永久不做的范围，也不得仅因完整读取而为无关旧功能增设实施票。必须在拆票前为本轮范围内的条目补齐身份和验收定位；已有稳定 ID 若与本约定不同，必须记录迁移映射并更新本轮引用，不得默默改号或长期并行维护两套编号。
