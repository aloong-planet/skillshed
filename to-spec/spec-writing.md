# spec 写作要求

本文适用于写与改 `docs/specs/` 下的一切文件。

## 1. spec 放在哪、一篇写多大范围

- spec 必须作为持久文档写入 `docs/specs/<slug>.md`,与 `docs/adr/` 同级维护,不得随票或施工记录的清理而丢弃。项目用真 tracker 的,spec 同样只写进 `docs/specs/`,不放进 tracker。
- spec 是现行描述:必须就地改写,变更史不写进 spec(形态见 4.1)。功能移除时,必须删掉它的 spec 文件,并按第 9 节删去索引里那一行。
- 每篇 spec 写一个功能,文件名去掉扩展名即该功能的 slug;一次开发涉及几个功能的,产出或更新几篇。
- **独立功能**:一组需求同时满足下面三条,就是一个独立功能:
  - 写得出它自己的 Problem Statement:它为用户解决的问题,不是另一组需求所解决问题的一部分;
  - 它有自己的需求标识(US、REQ、QR 或 CON),这些需求的验收条件与失败模式条目都在这一组之内;
  - 两边都能单独成立:没有它,其余的每条规则仍完整可执行;没有其余部分,它的每条规则也完整可执行。两边互相引用只得是一句指向,不得有哪条规则要靠另一边才成立。
- 新建 spec 时,要写的内容里每个独立功能必须各成一篇。既有功能的增量开发,必须改写既有 spec,不新开文件;增量本身是独立功能的,必须新开一篇。拿不准算不算独立功能的,必须停下问用户。
- 已有 spec 里本来就是独立功能的部分,不得因上一条拆分,只按第 8 节拆。
- 改动定下或改变的行为所属的功能还没有 spec 的,不论这次改动是哪个风险档位,必须为它新建一篇,只写本次定下或改变的行为;该功能其余既有的行为,不因此补写。

## 2. 写什么,写多细

- **必须写**:
  - 产品的行为,含它不做什么;
  - 外部系统及其数据的事实;
  - 算法与计算口径;
  - 持久化格式,以及读到别的版本写下的数据时怎么处理;
  - 架构约束,写成对设定它的 ADR 或项目不变量的引用。

  持久化格式与架构约束不得只留在代码里:重建的产品必须读得了现有用户已有的数据。
- **决策归 ADR**:spec 里的决策够 ADR 门槛的(判据见 domain-modeling),必须落成 ADR,spec 只写它的编号,不复述取舍过程。
- **写多细**(只管产品行为的细节):设想两个实现在某处细节上取法不同,用户能否看出差别(界面、数字、文件内容、能不能用)。
  - 看得出的,必须写到两个实现取法一致:边界上取哪一边(「恰好等于上限的照常读」)、阈值的精确值与单位、外部数据的字段名与形态清单、持久化字段、计算口径。
  - 看不出的,由实现自由选择,不得写。
  - 持久化格式与架构约束,不论用户看不看得出,都按「必须写」写。
- **判据**(拿不准一句话该不该写时用):设想只凭 `docs/specs/`、ADR 与 `CONTEXT.md` 从头重建这个产品。删掉这句话后重建的人会做错或做漏的,必须留;不会的,不得写。
- **尚未落地的事实**:必须写成 `> Pending: <条件>` 注记。条件必须是能对着实现判真假的产品事实,不得写成「待某票、某人、某轮」。条件到期时必须当即处置,三选一,都不得留下「曾经没有」的痕迹:
  - 条件消失、事实已平常的,删去注记;
  - 事实仍需陈述的,改写成普通现在时的正文;
  - 条件转为「决定不做」的,移入 Out of Scope 或边界条目,带理由,不带时间线。

## 3. 模板与逐节写法

- 新增、改动或搬动带标识的条目(US、REQ、QR、CON 及其 AC),或写入对需求标识的引用之前,必须完整读取 [requirement-identifiers.md](requirement-identifiers.md)。节是否生成、标识与粒度,按它的「唯一主定义」与「覆盖单位」定。
- 新建 spec 必须从下面的模板起步,各节写什么按模板后的表。模板与本文件写进项目产物的内容(固定名称、占位符、叙述句),必须按 [产物固定名称](../repo-scaffold/artifact-names/to-spec.spec-writing.md) 与 [需求标识的固定名称](../repo-scaffold/artifact-names/to-spec.requirement-identifiers.md) 书写。

```md
# {功能名}

> 关联: {ADR-XXXX,如有}

## Problem Statement
{用户视角的问题}

## Solution
{用户视角的解法}

## User Stories

### <spec-slug>::US-001 <故事标题>

<已确认的用户角色、目标与收益>

- <spec-slug>::US-001/AC-01：<保留前提、动作及可观察结果的独立验收条件>
- <spec-slug>::US-001/AC-02：<另一项独立验收条件>

## Functional Requirements

### <spec-slug>::REQ-001 <标题>（直接验收）

<单一、明确且可核验的功能条件>

## Quality Requirements

### <spec-slug>::QR-001 <质量要求标题>

适用范围：<已确认的范围>

- <spec-slug>::QR-001/AC-01：<已确认的适用条件、测量口径与合格标准>

## Constraints

### <spec-slug>::CON-001 <约束标题>（直接验收）

适用范围：<已确认的范围>；<可直接验证的约束条件>

## 失败模式与边界
{失败模式与边界条目}

## Implementation Decisions
{实现决策}

## Out of Scope
{明确不做的事}

## Further Notes
{其余备注}
```

| 节 | 写什么 | 这一节特有的限制 |
|---|---|---|
| 标题与关联行 | 功能名;关联的 ADR 编号及其一句话名称 | — |
| Problem Statement | 用户视角的问题 | 只写功能上线后仍然为真的话 |
| Solution | 这个功能为用户做什么的概述 | 不带各节规则的条件、数值、分支与例外 |
| User Stories | 角色、目标、收益,以及验收条件 | — |
| Functional / Quality Requirements、Constraints | 每个义务一个主定义 | — |
| 失败模式与边界 | 按 3.1 的三类写条目,每条写明边界与预期行为;用到别处定义的规则,写其标识 | — |
| 界面相关的决策(不论放在哪一节) | 用户看得到的结果:位置、顺序、文案、状态、出现与消失的时机 | — |
| Implementation Decisions | 第 2 节「必须写」里的持久化格式、对外接口的契约、算法与计算口径、架构约束 | 不写代码,不论它是不是原型产出的:状态机写成状态转换表(状态、触发、下一个状态、用户看到什么),数据结构写成字段表(字段名、类型、含义、读到别的版本写下的数据时怎么办) |
| Out of Scope | 不做的事,及其理由 | 理由不得与正文矛盾 |
| Further Notes | 不属上面任何一节、而按第 2 节判据必须留的内容 | — |

### 3.1 失败模式与边界的写入条件

「失败模式与边界」节的新条目只为下列三类情形写:

- **必须定下的边界**:说得出产品在这个边界上两种不同而都说得通的做法的,取哪一种是一个决定,写一条。决定在已确认的来源里找不到的,写的人不得自行定,必须停下问用户。
- **高代价的失败**:说得出正常使用中走到它的一条操作路径,且处理错的代价是下列四种之一——丢数据、没人会察觉的错误数字、安全漏洞、主流程走不通。
- **引入内容带来的能力**:渲染或加载外部内容的每一处,用户在那里能触发的每样东西各一条,见 3.2。

属这几类的情形,不得只取准备修改的代码涉及的那些,也不得以改动最少为依据删去。涉及状态/effect 的,必须先列全各状态的进入与退出路径,再从这些路径推出上述条目。已有的条目不得因不属上述三类而删,只有两种情形删条目:经用户确认的迁移,以及按第 6 节删去其中属第 4 节的内容。

### 3.2 失败模式的第二维:引入内容带来的能力

把外部内容(用户文档、配置、agent 生成物、第三方数据)渲染或加载进 app 的,除「数据出问题怎么办」外,必须再问一遍:这些内容能对宿主做什么?渲染器、框架或平台会造出代码里没写过的交互面,它们同样是用户可点、可触发的东西,却不在任何从需求与操作推出的序列里。

- **链接**:点击会不会导航整窗、开新窗口?站内、站外、危险协议各自的归宿?
- **图片/媒体**:相对路径怎么解析?能不能引用本机任意路径?加载失败什么样?
- **脚本/样式/iframe/webview**:能不能注入?被剥除后留下什么可见残骸?
- **表单/可交互元素**:提交去哪?
- **拖放/粘贴**:拖进来的文件被谁接管?
- **超大/畸形内容**:渲染是否卡死、是否撑破布局?

**判据**:逐个渲染或加载点问——「这里除了我写的元素,渲染器或框架还会生成什么用户能触发的东西?」凡是代码里没有对应的一行、但用户能点、能拖、能触发的,都必须有一条边界。

**同一内容有两个独立边界,不得互相顶替**:消毒(内容安全,防注入)与行为归宿(点了会怎样)。消毒库的职责恰恰是保留良性元素——过了消毒不代表行为已定义。

## 4. 不得写,以及不得留下的内容

下列九类各给判据;4.1、4.4、4.6、4.7、4.9 另列典型形态。一句话合某一类的判据或形态的,先看该类的例外;不属例外的,按该类的「改放哪里」处理,4.9 按「处置」。

**4.1 规则的由来与历史**

- 判据:这句话说的是规则怎样、为什么、在什么时候变成现在这样,而不是规则本身;删掉它,规则照样完整可执行。
- 形态:
  - 规则、条目或标题上的日期与确认状态,含原型门的过门记录与豁免声明:「(某日)」「(原型已确认,某日)」「Prototype gate: passed(某日)」「(the prototype exemption, declared)」;
  - 为什么这样定、为什么不那样定,含旧做法错在哪:「故意」「为了避免……」「否则会……」「代价是……」;
  - 相对以前版本的变化:「照旧」「(不变)」「新增:之前……」,以及指和以前比的「改为」「不再」。
- 例外:
  - Problem Statement 陈述的问题,Out of Scope 条目不做的理由;
  - 理由里含有重建的人必须遵守的约束的:把约束改写成规则本身,删去理由。例:措辞必须在两种状态下都成立;列出试过不可行的做法,免得重建的人再试一遍;
  - 外部事实可靠程度限定里的日期,见 4.2。
- 改放哪里:够 ADR 门槛的进 ADR(第 2 节「决策归 ADR」);其余留在提交信息与交付说明里。

**4.2 测量值及其测法**

- 判据:这个数是产品规则定下的,还是从测量、抽样或个案得来的。
  - 规则定下的照写:上限、默认值、超时、质量要求的阈值。
  - 测得的不写,测量的过程也不写:抽样或枚举得到的条数与占比,耗时、内存等读数及其对比,某台机器或某批数据上的个案。
- 例外:外部事实可靠程度的一句限定,只写方法、日期或版本,如「全量枚举,2026-09-11」「实测」「未实测」「据其帮助文本,1.4.9 版」;每个外部事实只写一句。
- 改放哪里:交付说明;要长期保存的,另写成调研文档。

**4.3 当前代码的组织**

- 判据:这个名字或机制是否穿过产品边界,即用户、外部系统或持久化数据看不看得到它。
  - 看得到的不属本类,按第 2 节写成契约本身,不写实现它的类型名:持久化的文件名、键名与字段名,对外接口,用户会设置的命令行参数与环境变量,外部数据的字段名与类型,操作系统与运行时的行为。
  - 看不到的不得写:只在代码内部用的类型、函数、变量、模块、文件路径、行号、CSS 类名、代码片段,以及跑在哪个线程或进程、怎么缓存、用哪种数据结构、样式怎么实现这类机制。只给测试用的,归 4.5。
- 改放哪里:代码与代码注释。

**4.4 写给维护者的提醒**

- 判据:祈使的对象是改代码的人,说的是代码,不是产品行为。
- 形态:
  - 「不要动」「务必」「照上面……去实现」;
  - 暂定标记:🔬「暂定」「待确认」「不是结论」;
  - TODO、FIXME。
- 例外:无。尚未落地的产品事实,按第 2 节「尚未落地的事实」写。
- 改放哪里:代码注释或票。

**4.5 测试的设计**

验收条件只写应当观察到什么,不写怎么测。

- 判据:这句话说的是怎么验证——测试 seam、fixture、测试用的启动参数与环境变量、由哪一层测、由哪个测试守住。
- 例外:产品对测试入口本身的行为(如打包版遇到测试参数就退出),属产品行为,照写。
- 改放哪里:测试文件及其注释。

**4.6 同一份 spec 里的第二次陈述**

- 判据:同一份 spec 里已有一处陈述了这条规则或它的一部分。
- 形态:
  - 在失败模式、界面决策、实现决策、Out of Scope 或另一条需求里,再写一遍别处已定义的规则:哪怕只写半句,哪怕后面跟着「(见 X)」;
  - 「与 X 结构相同」这类类比式的重述;
  - 引用旁边概括被引用条目内容的括注:「(因为 R1 只放行已列出的会话)」;
  - 同一个数值写在两处。
- 例外:Solution 的概述,不带条件、数值与例外。
- 改放哪里:只写被引用条目的标识。已有规则在另一种情形下的例外或补充,按第 5 节写。

**4.7 复述别的文档**

- 判据:这句话的内容在 `CONTEXT.md`、ADR、项目 `AGENTS.md` 或另一份 spec 里已经写着,本 spec 在其上没有增量。
- 形态:
  - 抄写 `CONTEXT.md` 词条的定义;
  - 抄写 ADR 的决定、背景或数据;
  - 转述项目 `AGENTS.md` 的不变量;
  - 抄写另一份 spec 的规则或口径。
- 例外:本 spec 在被引用内容之上的增量(来源没写的规则),照写。
- 改放哪里:写词条名、ADR 编号,或另一份 spec 的完整标识及链接,写法按 requirement-identifiers.md「完整标识与模板占位符」;引用处不加转述。

**4.8 会被清理的临时物**

- 判据:引用的东西会不会被清理或改写:票号、PR 号、分支名、施工记录路径、提交哈希。
- 改放哪里:要指出出处的,改为引用持久文档(spec 的主定义或 ADR);没有可引用的持久文档的,删去。

**4.9 已失效的内容**

- 判据:这句话陈述的东西现在不成立、既没实现也没定下要做,或把别的产物当作权威。
- 形态:
  - 删除线;
  - 已放弃的需求或整节;
  - 「可选的优化」这类既没实现、也没定下要做的内容;
  - 与现行行为矛盾的陈述;
  - 「照原型」这类以别的产物为准的说法。
- 处置:删去;需要说明「不做」的,写进 Out of Scope。

## 5. 每条规则只写一处

- 往 spec 里加一句陈述规则的话之前,必须按这条规则的标识和关键词检索整份 spec:
  - 已有陈述的,改在那一处,不另写一句;
  - 别处要用到它的,写它的标识,不再陈述一遍(形态见 4.6)。
- 要加的是已有规则在另一种情形下的例外或补充的,它是一条新规则:写在它适用的那一处,作为它自己的主定义,并写出原规则的标识。
- **判据**:本次新增的每一句,说得出它是哪条规则的主定义,或它引用的是哪条主定义。两样都说不出的,不得写。

## 6. 改写既有 spec 时

- 改写既有 spec 的某一节时,必须在同一次改动里删去该节里属第 4 节的内容。
- 不得只为删这类内容去改本次没有改写的节;其中已不为真的陈述,照常改正或删去。既有 spec 里的 Testing Decisions 节同样如此。
- 已超过第 7 节上限的 spec,不受上一条限制:为抵消本次的增长,可以删去本次没有改写的节里属第 4 节的内容。
- 按第 8 节拆分的那次改动,不适用本节:要清理的,放在拆分之前或之后的改动里做。

## 7. 大小上限

- 每份 spec 的大小,以本文件同目录的 [check-spec.mjs](check-spec.mjs) 报出的字符数为准:Unicode 码点数,含 Markdown 标记。
- 上限按项目的工作语言(`working-language`)定:超过 50,000 的英文 spec、超过 18,000 的中文 spec 即超限。工作语言不是这两种的,check-spec.mjs 报出它没有上限,写的人必须停下问用户上限。
- 改动 spec 的,以及提交别人对 spec 所作改动的,提交前必须在仓库根运行 check-spec.mjs,以分叉点(`git merge-base HEAD origin/<默认分支>`)为基准,按下面各条处置它报出的结果;它没能核对(退出码 2)的,不得当作通过,必须排除它报出的原因后重跑。
- **停下报告**:写明超出上限多少;有可以拆出去的独立功能的,附第 8 节的拆分方案,没有的写明没有。用户明确同意不拆的,才可以发布或让它变长,并必须在交付说明里写明用户同意的原话。
- 新建的 spec 不得超过上限。超过的,必须按第 8 节拆分后再发布;用户不同意拆、或找不出可以拆出去的独立功能的,必须停下报告。
- 已超过上限的 spec,一次改动不得让它变长:加了多少,同一次改动里就必须删去至少同样多。删去的只得是第 4 节所列的内容,或第 5 节判出的重复陈述。删不出这么多的,必须停下报告。

## 8. 功能拆分

- 必须拆分的情形:按第 7 节停下报告后、用户同意拆的;用户要求拆分的。
- 拆出去的只得是第 1 节定义的独立功能。
- 动手前必须把拆分方案交用户确认。方案写明:拆成几份,各自的 slug、范围与字符数;按完整标识检索全仓库得到的、要改的引用处数,连同所用的检索命令。
- 拆分只搬内容:同一次改动里不得改变任何规则的意思;除标识前缀与引用外,搬过去的句子逐字不变。
- 新 spec 的 slug 取 `<原 slug>-<子主题>`。
- 标识:
  - 搬走的需求保留局部编号,前缀改成新 spec 的 slug;
  - 旧标识到新标识的对应关系,按 requirement-identifiers.md「稳定身份与变更授权」记录;
  - git 跟踪的文件里引用搬走的标识的每一处(含 `AGENTS.md`),都必须在同一次改动里改成新标识;
  - 改的引用在 ADR 里的,即改了该条目的文字:同一次改动里必须按 domain-modeling 的 [ADR-FORMAT.md](../domain-modeling/ADR-FORMAT.md)「旧规则下写的条目」节把该条目纳入现行规则。
- 新 spec 有自己的 Problem Statement、Solution 与关联行;索引按第 9 节改。
- 项目里以功能 slug 命名或定位的其他东西(测试文件名、目录名),按项目规则查要不要跟着改;要改的,并入同一次改动。

## 9. 索引 README

- `docs/specs/README.md` 必须按下面的模板写,一份 spec 一行。
- 首次建立 `docs/specs/` 时一并建立。新建的 spec 必须加一行;改写使某一行「一句话」不再成立的,必须同步改写该行;功能移除时删去该行;拆分时为新 spec 加一行,并按拆分后的范围改写原 spec 那一行。

```md
# Specs

{必须按 spec-writing.md 第 1 节生成面向目录读者的说明与不变量;将规则展开成正文,不得将此占位指令或依赖本机 skill 路径的链接留在成品中。}

| Spec | 一句话 |
|---|---|
| [{功能名}]({slug}.md) | {这个功能做什么,一句话} |
```
