# 合并前后的机械核对

合并一个受本 skill 管辖的 PR 时使用本文件:按用户授权合并的、按 `docs-auto-merge` 例外合并的都一样。核对由本目录的 [merge-check.mjs](merge-check.mjs) 执行(需要 node;它跑 `spec-check` 或 `adr-check` 时还需要 python3 3.11 或更高版本),它只检查、不改 GitHub 上的任何东西。

## 1. 合并之前

- 合并之前必须在该仓库的检出里运行 `merge-check.mjs before --repo <owner/repo> --pr <N> --head <sha> --squash-body <文件>`。`--head` 必须是自己审过的那个 commit 的完整 SHA。紧挨着合并的那一次运行,`--squash-body` 必须是合并时用作提交正文的那个文件,合并必须用它;更早的运行可以传草稿。
- 项目 `AGENTS.md` 与用户的长期指示禁止出现在公开文字里的写法,每一种都必须以一个 `--forbid <正则>` 传入;两处都没有的,不传。
- 某个 job 只在项目 `AGENTS.md` 或用户的长期指示写明它的结果不作为证据时,才得传给 `--ignore-job`;另一个 job 的结果要等这样的 job(如 `needs` 它的 gate job)的,也得传。传了的,给用户的报告里必须引出那条规则的原文,并写明那个依赖。
- 每次运行都必须读它的退出码,按下列各支处置:
  - 退出码为 0 的:这次运行判为通过。
  - 退出码为 1、`FAIL` 的只有 `spec-check`、它报出的违规全是 spec 超出上限(输出里写 `over the cap` 的那几条)、且 PR 描述为其中每一份 spec 写明了用户明确同意它超限的原话的:这次运行判为通过。
  - 其余退出码为 1 的:改 PR 的分支、PR 的描述或 `--squash-body` 文件,或等 CI 结束,能消除的 `FAIL` 与 `BLOCKED`,消除后重跑本节;消除不了的报告用户。
  - 退出码为 2 或其他值的(进程被信号结束时没有退出码):不是对这个 PR 的结论,不得当作通过;必须排除它报出的原因后重跑,排除不了的报告用户。
- `spec-check` 下面列出的待判行,必须逐行判它是否属 `/to-spec` 的 [spec-writing.md](../to-spec/spec-writing.md)「不得写,以及不得留下的内容」节所列的内容。判为属的,是这次核对的一条发现,必须在合并前修掉:改之前完整读取 spec-writing.md,修完对新的 PR 头重跑本节;修完后仍按原来的合并方式(按授权或按例外)合并,不得只因这条发现改为等用户授权。
- `For review:` 下列出的每一项,以及 diff 的内容,合并之前必须由合并的 agent 逐项判断;判为要改的是一条发现,改掉后对新的 PR 头重跑本节,要用户决定的报告用户。
- 紧挨着合并的那一次运行判为通过、且按上两条判出的发现都已修完的,核对才判为可以合并。

## 2. 合并之后

- 合并之后必须运行 `merge-check.mjs after --repo <owner/repo> --pr <N> --head <sha>`,`--head` 与合并之前那次相同,`--forbid` 按第 1 节同一条规则传入。退出码为 2 或其他值的,必须排除它报出的原因后重跑,排除不了的把原因报告用户;它报出的每一条 `FAIL` 与 `ERROR` 都必须报告用户。

## 3. 查什么

- 两种模式各查哪几项、每项依赖哪几项、按什么判,以 `merge-check.mjs --list` 的输出为准;不得在本文件或别处另列一份检查清单。
