# CONTEXT.md 格式

## 结构

```md
# {上下文名}

{一两句:这个上下文是什么、为何存在。}

## Language(术语)

**订单(Order)**:
{一两句定义。定义它「是什么」,不是「做什么」。}
_Avoid_: 购买、交易

**发票(Invoice)**:
交付后向客户发出的付款请求。
_Avoid_: 账单、付款单

## Relationships(关系)——可选节

{概念间关系,一行一条(如"发现 = announce + register 组成双向发现")。仅当关系本身承载易混信息时才写。}

## Flagged ambiguities(已消解歧义)——可选节

{曾经混用、现已裁定的术语,写明旧含义作废及裁定出处。}
```

## 规则

- **有立场**:同一概念存在多个词时,选定最佳的一个,其余全部进 `_Avoid_`。
- **定义收紧**:至多一两句。
- **只收本项目特有概念**:通用编程概念(超时、错误类型、工具模式)不收,哪怕项目大量使用。收录前自问:这是本上下文独有的概念,还是通用编程概念?只有前者进。
- **零实现细节(硬规则)**:CONTEXT.md 是纯词汇表。"备注存 settings.json 的 deviceAliases 字段"这类不属于这里——存储位置/字段名/文件名会腐烂,概念不会。实现细节归 ADR 或代码。
- 术语自然成簇时可用子标题分组;单一内聚领域用平铺列表即可。

## 单/多上下文仓库

- **单上下文(绝大多数)**:根目录一个 `CONTEXT.md`。
- **多上下文**:根目录 `CONTEXT-MAP.md` 列出各上下文(名称、CONTEXT.md 路径、一句职责)与上下文间关系(谁发事件谁消费、共享哪些类型)。各上下文目录内放各自的 `CONTEXT.md` 与 `docs/adr/`(系统级决策放根 `docs/adr/`)。
- 推断规则:有 CONTEXT-MAP.md 按它找;只有根 CONTEXT.md 即单上下文;都没有则首个术语敲定时懒创建根 CONTEXT.md。多上下文时按当前话题推断归属,不明确就问。
