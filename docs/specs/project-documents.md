## Problem Statement

A project kept two documents per feature, a spec and a feature-catalogue page, and the page restated the spec. Every change that touched one had to touch the other and then check the two against each other.

A spec also carried content that nobody rebuilding the product would need: how a rule came about, how the current code is laid out, how the tests were designed, what a benchmark measured on one machine. The section on failure modes was filled by walking every user operation sequence, and each entry in it had to have a test case, so the number of cases followed the number of entries rather than the risk.

A project's ADRs were append-only. A change to a decision opened a new entry that superseded part of an older one, so the rule in force was spread across several entries, and the entries kept how each decision came about, verification logs, costs already paid and implementation detail. Nothing said what an entry may hold or how long it may be, and the rule keeping process conventions out of ADRs contradicted the places that record a project's own choice of practice in one. Sentences and characters were then counted by eye, and entries missing a kind of consequence passed both the writer's check and the closing check.

Every visible change to the interface, down to a colour or a gap, needed a prototype the user had confirmed, and the prototype had to be kept in step with the app afterwards.

The document check at the end of a change ran in the main session, at the point where that session's context is largest.

Nothing bounded a spec's size or said when one spec should be two, so whoever needed one rule of a feature read the whole of a long spec. The rules for writing a spec sat in the skill that synthesises one from the conversation, and the later steps that also write a spec did not read them, so what those steps wrote held content the rules exclude.

## Solution

A feature has one document, its spec, and the spec states the user-visible behaviour too. A spec holds what rebuilding the product from the specs, the ADRs and `CONTEXT.md` would need, and nothing else. An ADR states a decision in force the way a spec states behaviour: a table decides which decisions get one, it holds only what each of its sections allows within a length cap, and it is edited in place once the user confirms the change. A script checks an entry's form, its counts and the index, and sets the options and negative consequences a change touched beside their earlier text for the writer to compare. A boundary entry is written when the product's behaviour had to be decided there or when real use reaches the failure and getting it wrong is costly; test cases follow the acceptance criteria and that risk. A prototype is made when the interface question is open, and is not kept in step with the app once the app exists. The document check at the end of a change runs in a sub-agent on a smaller model. The rules for writing a spec are in one file that every step changing a spec reads first. A spec covers one feature, stays within a cap on its size that a script reports, and is split by feature with the user's agreement.

## Functional Requirements

### project-documents::REQ-001 One document per feature

- project-documents::REQ-001/AC-01: No skill creates, updates, reads as a source of truth or requires `docs/features/`. A feature's user-visible behaviour is stated in its spec.
- project-documents::REQ-001/AC-02: Whatever took a feature's slug from `docs/features/` takes it from `docs/specs/`: the working-record directory, the prototype module directory, the file an e2e case goes in.
- project-documents::REQ-001/AC-03: The index of `docs/specs/` is a table of each spec and what the feature does in one line, so the directory is also the overview of what the product does.
- project-documents::REQ-001/AC-04: In a project that still has `docs/features/`, the closing document check reports it as one finding and states the migration: add to the same-name spec whatever the page says and the spec does not, repoint the references to it, delete the directory. Until the owner has that done, no skill maintains the directory or checks anything against it.

### project-documents::REQ-002 What a spec holds

- project-documents::REQ-002/AC-01: A spec holds the product's behaviour, including what it does not do; facts about external systems and their data; algorithms and accounting rules; persisted formats and how data written by another version is read; and the architectural constraints, by reference to the ADR or invariant that sets them. A rebuilt product must read the data existing users already have, so the last two are never left to the code alone.
- project-documents::REQ-002/AC-02: A spec does not hold these kinds of content:
  - the history of a rule: a date or a confirmation note on a rule or a heading, a prototype gate's record or exemption among them, why the rule was decided or why another was not, and how it differs from an earlier version;
  - a measurement and how it was taken: a count or share found by sampling or enumeration, a reading such as a duration or memory size, a case seen on one machine or one batch of data;
  - how the current code is laid out: a name or a mechanism that neither the user, nor an external system, nor persisted data can see, such as an internal type, function, module, file path, line number, style class or code fragment, or the thread, cache or data structure a thing runs on;
  - a reminder to whoever maintains the code, such as a do-not-touch note, a provisional marker or a TODO;
  - the design of the tests: a test seam, a fixture, a launch argument or environment variable for tests, the layer that tests something, the test that guards it;
  - a second statement, in the same spec, of a rule it already states, in part or whole and with or without a pointer to the first, a summary of a cited entry beside the citation among them;
  - a restatement of another document: a glossary entry's definition, an ADR's decision, context or figures, an invariant of the project's `AGENTS.md`, another spec's rule;
  - a reference to something that is cleaned up or rewritten: a ticket, a pull request, a branch, a working-record path, a commit hash;
  - content no longer in force: struck-through text, an abandoned requirement or section, an optional optimisation neither built nor decided, a statement that contradicts the current behaviour, a pointer that makes another artifact the authority, such as "as the prototype shows".

  These are not of those kinds: the problem stated in the Problem Statement and the reason an Out of Scope entry is not done; a constraint that a reason carries, once rewritten as the rule itself; a limit, default, timeout or threshold the product sets; one statement per external fact of how reliable it is, naming only the method, a date or a version; a name that crosses the product's boundary, such as a persisted file name, key or field, an external interface, a command-line argument or environment variable the user sets, or an external data field; what the product does when it meets a test entry point; and what a spec adds to the document it cites. What of those kinds is still worth keeping goes elsewhere: a decision that meets the ADR bar to an ADR, how the code works to its comments, the design of a test to the test, a reminder to a code comment or a ticket, a measurement to the delivery note or a research document, and the rest of a rule's history to the commit message and the delivery note.
- project-documents::REQ-002/AC-03: The spec template has no section for testing decisions, and `/to-spec` has no step that settles test seams. The seam is chosen when the test is written.
- project-documents::REQ-002/AC-04: A fact about real data that comes to light while tests are designed is written into the spec as a statement about that data.
- project-documents::REQ-002/AC-05: When a change rewrites a section of an existing spec, content of the kinds in AC-02 found in that section is removed in the same change. A section the change does not rewrite is not edited just to remove such content, and a statement in it that is no longer true is corrected. A spec over the cap of REQ-013/AC-01 is an exception: to offset what a change adds, the change may remove such content from sections it does not rewrite. A change that splits a spec (REQ-013/AC-06) removes no such content; any cleanup is a change before or after it.
- project-documents::REQ-002/AC-07: A detail of the product's behaviour is written when two implementations that chose it differently could be told apart by the user, in the interface, in a figure, in a file's content or in whether something works: which side of a boundary is taken, a threshold's exact value and unit, the field names and forms of external data, persisted fields, an accounting rule. It is written so that the two would choose alike. A detail the user could not tell apart is left to the implementation and not written. Persisted formats and architectural constraints are written whether the user could see them or not (AC-01).
- project-documents::REQ-002/AC-08: Each section of a spec holds what the template gives it. The Problem Statement holds only what stays true once the feature ships. The Solution is an overview of what the feature does for the user, without the conditions, figures, branches or exceptions of its rules. A decision about the interface, in whatever section, states what the user sees: position, order, wording, state, and when a thing appears and goes. Implementation Decisions hold persisted formats, the contracts of external interfaces, algorithms and accounting rules, and architectural constraints, with no code in them, whether or not a prototype produced it: a state machine is a table of transitions (state, trigger, next state, what the user sees), and a data structure a table of fields (name, type, meaning, what happens with data another version wrote). The reason an Out of Scope entry gives does not contradict the rest of the spec.
- project-documents::REQ-002/AC-09: A rule is stated in one place in a spec. Before a sentence stating a rule is added, the spec is searched for that rule's identifier and key words: a rule already stated is changed where it is stated, and another place that needs it cites its identifier. An exception to a rule or an addition to it for another case is a rule of its own, written where it applies as its own primary definition, citing the identifier of the rule it qualifies. Each sentence a change adds is either the primary definition of a rule or a citation of one.

### project-documents::REQ-003 Boundary entries and test coverage

- project-documents::REQ-003/AC-01: A new entry under "Failure modes and boundaries" is written for a boundary where the product's behaviour had to be decided, or for a failure that real use reaches and whose mishandling is costly: lost data, a wrong figure nobody would notice, a security hole, a blocked main flow. The section is not filled by walking every user operation sequence.
- project-documents::REQ-003/AC-02: The question of what content brought into the app can do to the host (links, media, scripts, forms, drag and drop, oversized content) is asked at every point that renders or loads such content, and an entry is written for each thing a user can trigger there.
- project-documents::REQ-003/AC-03: For a change that involves state or effects, the ways into and out of each state are listed first, and the entries of AC-01 are derived from them.
- project-documents::REQ-003/AC-04: The cases a change must have are one for each acceptance criterion it delivers, and one for each boundary entry it adds or changes that is costly in the sense of AC-01. Any other entry needs no case. A case that cannot be driven is a stated gap. A core-tier change has more cases than these ([risk-tiers::REQ-005/AC-01](risk-tiers.md)).
- project-documents::REQ-003/AC-05: The test review checks coverage against the list of AC-04, not against the section entry by entry, except for the entries [risk-tiers::REQ-005/AC-01](risk-tiers.md) names for a core-tier change.
- project-documents::REQ-003/AC-06: Entries and cases that already exist stay, even where an entry is of none of the kinds of AC-01 and AC-02. Two things still remove entries: a migration of a spec's entries that the user confirmed, and REQ-002/AC-05 for content of REQ-002/AC-02's kinds. Nothing here asks for a case to be deleted.
- project-documents::REQ-003/AC-07: Where the behaviour at a boundary had to be decided and no confirmed source gives the decision, the writer does not decide it: it stops and asks the user.

### project-documents::REQ-004 The prototype gate

- project-documents::REQ-004/AC-01: A prototype confirmed by the user is required before an interface is specified or coded in two cases only: the change adds a surface the app does not have (a page, a pane, a drawer, a dialog or another overlay: a region with a layout of its own, not a control added to a surface the app has), or more than one arrangement of the interface is being weighed, which includes the user asking to see it first.
- project-documents::REQ-004/AC-02: Every other interface change is implemented directly and delivered with a screenshot of the running app for each interface point it changed. Where the app cannot be run to take one, the delivery says so and why.
- project-documents::REQ-004/AC-03: The app is the baseline of the interface. Existing prototypes stay in the repository as reference, and where a prototype and the app differ the app is right, with the one exception of boundary 7. No skill requires a prototype to be updated because the app changed, to be marked as out of date, or to be compared with the implementation.
- project-documents::REQ-004/AC-04: A prototype made for a surface the app already has starts from the app's current look.
- project-documents::REQ-004/AC-05: `/ui-design` applies to interface code and to a prototype when one is made, as before.

### project-documents::REQ-005 The closing document check runs in a sub-agent

Applies to the document check that ends a change, not to the full-feature closeout of a closeout ticket.

- project-documents::REQ-005/AC-01: Where the tool can send a sub-agent, the main agent hands the check to one that does not inherit the conversation and that loads the skill itself. Where it cannot, the main agent runs the check.
- project-documents::REQ-005/AC-02: Where the tool lets the sub-agent's model be chosen, it is the tier one below the main session's, of the latest generation: the tier's alias where the tool takes aliases, the latest model of that tier where it takes model names, never an older generation because it is cheaper. A main session already on the smallest tier uses that tier.
- project-documents::REQ-005/AC-03: Where the tool lets the sub-agent's reasoning effort be chosen, it is the level named `high`; where no level has that name, the first level above the tool's default.
- project-documents::REQ-005/AC-04: The main agent commits the change before it hands over. If the working tree then still holds changes that are not the change's, it does not hand over and tells the user. The handoff carries the checkout's absolute path, the fork point and that commit, the slugs of the specs the change touched, the directory of the change's working records, the ticket when there is one, the events of the change that no file records (a rule newly decided, the user's acceptance feedback, a change of work status), the commit range of the fix when the check is handed over again after one, and the instruction to load the skill and run the check. It carries no judgement of what is or is not consistent.
- project-documents::REQ-005/AC-05: The sub-agent may rewrite documents to make them true, a document being a Markdown file, in the checkout or in the change's working records, that no test reads. It does not change code, tests, data a test reads, interface dictionaries or package metadata, does not commit, and hands back a finding that needs any of these.
- project-documents::REQ-005/AC-06: The handback is the conclusion, the documents it changed, the number of statements it judged with the searches it ran to find them, and each finding it could not settle, stated in full. No report is written.
- project-documents::REQ-005/AC-07: On the handback the main agent first checks that the checkout is on the branch it handed over and that the commit of AC-04 is still in its history; if not, it changes nothing and tells the user. It undoes any commit the sub-agent made, keeping its changes in the working tree, then lists what changed in the working tree since the commit of AC-04. A changed path that is not a document is restored from that commit and reported to the user. The main agent then reads the findings in the handback, commits the document changes that remain, and only then acts on a finding. A handback without the number and the searches sends the check out once more; if that fails too, the main agent stops and tells the user.
- project-documents::REQ-005/AC-08: The main agent reads only the rules for handing over and for checking the handback. The rules of the check itself are in a file the sub-agent reads.
- project-documents::REQ-005/AC-09: Before the main agent commits the document changes a sub-agent left, it reads the sub-agent's changes to the documents in the checkout and judges each added, rewritten or deleted statement against what the change did and decided, reading the code or document the statement is about where that does not settle it. A statement left untrue is corrected, a deleted one that still holds is restored, and the user is told which. It judges only those statements and does not run the check again. This does not apply when the main agent ran the check itself.

### project-documents::REQ-007 Which decisions get an ADR (direct acceptance)

A decision gets an ADR when it is hard to reverse, baffling without context and the product of a real trade-off, and the table below sends it to an ADR; whatever the table sends elsewhere goes there instead.

| What is decided | Where it goes |
|---|---|
| A project's architectural decision, or the trade-off behind its product behaviour or an accounting rule | An ADR |
| A project's choice on a process question: which practice it adopts, and why | An ADR, stating this project's choice and not the practice's own rules |
| A process rule that holds across projects | The skill that governs that work |
| A constraint on whoever changes the code | An invariant in the project's `AGENTS.md`; the trade-off behind it, when it meets the thresholds, also gets an ADR as in the first row |
| Product behaviour or an accounting rule, as stated | The feature's spec, which cites the ADR of the choice behind it when that choice gets one |
| An incident | A postmortem |
| How the code carries out a decision | A comment in that code |

### project-documents::REQ-008 What an ADR holds

- project-documents::REQ-008/AC-01: An ADR has five sections, and each holds only this: Context, the problem and the forces on it; Options, one item per option, chosen, rejected or deferred, with why (marked as not recorded where no record gives it, never written after the fact), and for a deferred one the condition that reopens it; Decision, the rule in force in the active voice; Consequences, the positive, negative and neutral consequences that still hold; Sources, pointers to the evidence and the key figures the decision rests on, each with the premise it holds under.
- project-documents::REQ-008/AC-02: No section holds how the rule came about, a verification or rollout log, a record of the evidence closing, a one-off cost already paid, how the code carries out the decision, interface detail, how a measurement was taken, line numbers, a site-by-site list, a restatement of another ADR, a spec or a skill, or an option about how to record the decision.
- project-documents::REQ-008/AC-03: Context is at most three sentences, and each option and each consequence is its own item of at most two sentences. The entry without its title and status line is at most 1,800 characters in a project whose working language is `zh`, and at most 5,000 in a project with any other working language. Sentences and characters are counted as the check script of AC-05 counts them. An entry over the cap first loses what AC-02 excludes, under REQ-009/AC-06, and is split by decision if it is still over.
- project-documents::REQ-008/AC-04: Whoever writes or edits an ADR runs the check script of AC-05 at the repository root before committing, and commits only when it passes or, where AC-09 has the writer make its checks by hand, when those checks all hold. They also read each section against AC-01 and AC-02, and check that the declaration at the head of the project's `docs/adr/README.md` states these rules, which the script does not. The closing document check makes the same checks again for each ADR the change added or whose own statements it edited (REQ-010/AC-01), and for each ADR it deleted checks that its number was retired under REQ-009/AC-05.
- project-documents::REQ-008/AC-05: The check script fails on any violation it finds. For each entry it checks, a violation is a title whose number is not the file name's, a status line not in the template's form, the five sections missing, out of order, empty or with text outside them, an option or a consequence that is not its own list item, a count over the limits of AC-03, a consequence without its kind, or a kind among positive, negative and neutral that no consequence has. Whatever entries it checks, a violation is two entry files with one number, an index that breaks AC-07, a number that had an entry file in the repository's history and has none now but is not among the index's retired numbers, a retired number that has a file, and a citation of a retired number, written `ADR-NNNN` or as one of the file names it had, in any file of the repository that git does not ignore, untracked ones included, outside the list of retired numbers; a binary file is not searched. Its output names the forms it searched for, so a clean result says only that those are absent.
- project-documents::REQ-008/AC-06: The entries the script checks are those the change added and those whose text differs from the base in more than ADR numbers and entry file names (REQ-010/AC-01). An ADR number is `ADR-NNNN`, or a four-digit number with no letter or digit next to it that is the number of an entry now, at the base or in the history; an entry file name is a name such an entry has or had, so a dated file name of a research note or a postmortem is not one. The base is the branch's fork point from the default branch unless another commit is given, and the current side is the working tree, uncommitted and untracked files included. A full sweep checks every entry.
- project-documents::REQ-008/AC-07: The ADR index has one row for each entry file, linking to it. A row's Decision cell is the entry's title without its `ADR-NNNN: ` prefix, verbatim, and its status cell names the entry's state.
- project-documents::REQ-008/AC-08: Beside the violations, the script lists for review, without failing on them: the options and the negative consequences of every entry the change added, deleted or checked, at the base and now, with the deleted entries on the base side and the added ones on the current side, so that a merge or a split lines up; each status line that changed; and each line in the repository that cites one of those entries. The writer judges each difference: a rewrite that keeps the decision is listed under REQ-009/AC-02, and a change of decision is confirmed by the user before it is written. The writer also checks that each citing line still points at something the entry says, and corrects the citation where it does not.
- project-documents::REQ-008/AC-09: The script never passes what it could not check. Run outside a repository root, without `docs/adr/`, in a shallow clone, where there is no base to compare with (no `--base` is given and the repository has no `origin/HEAD` to find the fork point from, or the `--base` given is not a commit), where the working language cannot be read or has no column in the table of fixed names, or where `docs/adr/`, an entry or the index is there but cannot be read, it fails with an exit code of its own and says why; so does any error of the script itself. The writer removes the cause and runs it again; where the working language has no column, the writer makes the script's checks by hand, and the delivery note says that the script could not run, with its output.

### project-documents::REQ-009 How an ADR changes

- project-documents::REQ-009/AC-01: An entry states the decision in force. A change to an accepted decision edits that entry in place, and an approach given up becomes one of its rejected options, with why it was given up. The states are Proposed and Accepted; there is no superseded state, and the history of an entry is in git.
- project-documents::REQ-009/AC-02: A change to what an entry chose, rejected or accepted as a consequence is confirmed by the user before it is written. Deleting a superseded clause, and recording the approach it held as a rejected option of the entry that superseded it, under REQ-010/AC-01, keep the decision. A rewrite that keeps the decision, such as compressing an entry, merging entries or correcting a stale fact, is not confirmed in advance, and each one is listed in the delivery note for the review before the pull request merges, or reported to the user when the change has no delivery note.
- project-documents::REQ-009/AC-03: An accepted entry's status line carries the date the decision in force was confirmed, written YYYY-MM-DD, with nothing else in its parentheses. A change of decision updates it; a rewrite that keeps the decision leaves it.
- project-documents::REQ-009/AC-04: A new decision edits every existing entry in which it makes a sentence of the Decision section untrue or needs a sentence added there, and opens a new entry when there is none. An edit that takes an entry over the cap of REQ-008/AC-03 splits it by decision.
- project-documents::REQ-009/AC-05: An entry merged into another, or whose decision is withdrawn, has its file deleted. The same change points every citation of its number in the repository at the entry it went into, or removes the citation when the decision was withdrawn, and the ADR index keeps a line naming each retired number and where it went. A number is never used again.
- project-documents::REQ-009/AC-06: Before content of a kind REQ-008/AC-02 excludes leaves an entry, it is found in its current home, or added there first: interface behaviour in the spec, how the code carries out the decision in a comment in that code, a constraint in an `AGENTS.md` invariant. Content with no current home, such as how the rule came about, is deleted.

### project-documents::REQ-010 ADRs written under the earlier rules

- project-documents::REQ-010/AC-01: When a change edits an entry's own statements (its decision, its options, its consequences or a fact it states), the whole entry is brought under REQ-008 and REQ-009 in the same change: the entries its status line or notes mark as wholly superseding, extending or amending it, or as wholly superseded, extended or amended by it, are merged into it under REQ-009/AC-05; where a note marks only one clause of one entry superseded by another, the two stay separate entries: the superseded clause is deleted from the entry that holds it, together with the notes on either entry that mark it superseded, and a superseded approach the superseding entry's options do not list becomes one of them, with the reason it was superseded; what REQ-008/AC-02 excludes leaves it under REQ-009/AC-06; and its length comes within the cap. Pointing a citation at another number is not such an edit. An entry no change edits stays as it is.
- project-documents::REQ-010/AC-02: These rules apply in every project at once. The first change that writes or edits an ADR in a project rewrites the declaration at the head of its `docs/adr/README.md` to these rules.

### project-documents::REQ-011 One file holds the rules for writing a spec

- project-documents::REQ-011/AC-01: The rules for writing and changing a file under `docs/specs/` are in one reference file in `/to-spec`'s directory: those of REQ-002, REQ-003, REQ-012 and REQ-013, where a spec lives, the `Pending:` note, the spec template and the index template. `/to-spec`'s `SKILL.md` holds the flow of synthesising a spec from the conversation, and reads that file in full before it writes.
- project-documents::REQ-011/AC-02: Every step of a skill that writes or changes a file under `docs/specs/` requires, at that step, that the file be read in full before the change. The step does not restate the file's rules and does not send the reader to a section of `/to-spec`. A step that cites one of those rules without writing a spec names the file and its section.
- project-documents::REQ-011/AC-03: For measurements, the layout of the code, the design of the tests and references to things that are cleaned up, the file gives the criterion that decides whether a sentence is of that kind. For each other kind of REQ-002/AC-02 it lists three to five typical forms beside the criterion.
- project-documents::REQ-011/AC-04: The closing document check judges each sentence the change added to a spec against REQ-002/AC-02 and REQ-002/AC-09. Before a pull request that changes a spec merges, whoever merges it runs the script of REQ-014 and judges each line the script lists for review; a violation the script reports keeps the pull request from merging. A run that could not check is run again once its cause is removed, and a cause that cannot be removed is reported to the user.

### project-documents::REQ-012 What one spec covers

- project-documents::REQ-012/AC-01: A spec describes one feature, and its file name without the extension is the feature's slug. A change that touches several features writes or rewrites a spec for each.
- project-documents::REQ-012/AC-02: A set of requirements is an independent feature when all three hold: it has a Problem Statement of its own, a problem it solves for the user that is not part of the problem another set solves; it has requirement identifiers of its own, and their acceptance criteria and boundary entries all fall inside the set; and each side stands alone, so that without the set every other rule is still complete and can be carried out, and without the rest every rule of the set is too. A pointer from one side to the other is allowed; a rule that holds only together with the other side is not.
- project-documents::REQ-012/AC-03: A new spec gives each independent feature among what it is to hold a spec of its own. An increment to an existing feature rewrites that feature's spec; an increment that is itself an independent feature gets a new spec. Where it is unclear whether something is an independent feature, the writer stops and asks the user.
- project-documents::REQ-012/AC-04: A part of an existing spec that is an independent feature is not split off because of AC-03; it is split only under REQ-013/AC-06.
- project-documents::REQ-012/AC-05: When the feature whose behaviour a change decided or changed has no spec, a spec is created for it holding only what the change decided or changed; the feature's other existing behaviour is not written up for it. This holds at every risk tier.

### project-documents::REQ-013 A cap on a spec's size, and splitting

- project-documents::REQ-013/AC-01: A spec's size is the number of Unicode code points in its file, Markdown markup included, as the script of REQ-014 reports it. A spec is over the cap when its size is more than 50,000 in a project whose working language is English, or more than 18,000 where it is Chinese. In a project with another working language the script reports no cap, and the writer stops and asks the user for one.
- project-documents::REQ-013/AC-02: Whoever changes a spec, or commits a change another made to one, runs the script before committing, with the branch's fork point from the default branch as the base, and acts on what it reports as AC-03 to AC-05 say.
- project-documents::REQ-013/AC-03: A new spec is not published over the cap. It is split under AC-06 first; where the user does not agree to the split, or no independent feature can be split off, the writer stops and reports under AC-05.
- project-documents::REQ-013/AC-04: A change does not make a spec that is already over the cap longer: whatever it adds, it removes at least as much in the same change, and what it removes is content of REQ-002/AC-02's kinds or a second statement found under REQ-002/AC-09. Where it cannot remove that much, the writer stops and reports under AC-05.
- project-documents::REQ-013/AC-05: A report under AC-03 or AC-04 states how far over the cap the spec is or would be, and gives a split plan under AC-06 where an independent feature can be split off, or says there is none. Only the user's explicit agreement not to split lets the spec be published over the cap or grow, and the delivery note quotes the user's words.
- project-documents::REQ-013/AC-06: A spec is split when the user agrees to it after a report under AC-05, or asks for it. Only independent features (REQ-012/AC-02) are split off. The user confirms the plan before the split: how many specs, each one's slug, scope and size, and how many references to change a repository-wide search by full identifier found, with the search command.
- project-documents::REQ-013/AC-07: A split only moves content. In that change no rule changes its meaning, and the moved sentences stay word for word but for identifier prefixes and citations. A split-off spec's slug is `<original slug>-<sub-topic>`; it has its own Problem Statement, Solution and Related line, and gets a row in the index, and the original's row is rewritten to its new scope.
- project-documents::REQ-013/AC-08: A moved requirement keeps its local number under the new spec's prefix, and the mapping from old identifier to new is recorded as `/to-spec`'s rules on stable identity say. Every file git tracks in the repository that cites a moved identifier cites the new one after the same change. Repointing such a citation in an ADR is an edit of that entry's text, so the entry is brought under the ADR rules in that change as REQ-010/AC-01 says. Anything else the project names or locates by the feature's slug, such as a test file, is checked against the project's own rules and renamed in the same change where they require it.

### project-documents::REQ-014 The spec check script

- project-documents::REQ-014/AC-01: The script lives in `/to-spec`'s directory and runs from a project's repository root with `--base <commit>`. It reads `working-language` from `capabilities.toml` with a TOML parser, which needs python3 3.11 or later, and reports each spec's size, its cap and how much it grew or shrank since the base. A spec is a Markdown file directly under `docs/specs/` other than the index `README.md`, and it is new when its file is not at the base.
- project-documents::REQ-014/AC-02: A violation is a spec over the cap that is longer than at the base; a new spec over the cap; struck-through text; a path into the directory the skills keep working records in; and a full identifier `<slug>::<local number>`, cited in a file git tracks, whose spec `docs/specs/<slug>.md` has no primary definition of it, a heading or list item that opens with the identifier, or whose spec was at the base and is gone. A citation whose slug has a spec neither now nor at the base is not checked.
- project-documents::REQ-014/AC-03: Beside the violations, and without failing on them, the script lists for review the lines of specs that the change added and that hold a date, a percentage or a count of the form "N of M", a path with a line number or an identifier in camel or snake case in backticks, a code block, a provisional marker or TODO, a test seam or fixture, a number after a hash sign as a ticket number is written, or a mention of a prototype. The writer, and whoever merges under REQ-011/AC-04, judges each against REQ-002/AC-02.
- project-documents::REQ-014/AC-04: Exit code 0 is no violation, 1 a violation, and 2 a run that could not check: a usage error or a run outside the repository root, a `capabilities.toml` or python3 that cannot be used, a working language that is not declared or has no cap, a base that is not a commit, no spec found, a read or git command that failed, or an error the script does not expect. It never passes what it could not check.
- project-documents::REQ-014/AC-05: No CI runs the script; it runs at the writer (REQ-013/AC-02) and before the merge (REQ-011/AC-04).

### project-documents::REQ-015 Code and tests cite a spec by full identifier (direct acceptance)

A code comment or a test that cites a spec gives the full identifier of the entry it cites, never a section-local number or a line number, and does not restate what the entry says or the figures it gives.

### project-documents::REQ-006 This repository follows its own rules (direct acceptance)

The two specs this repository already has lose their testing-decisions sections and the content of REQ-002/AC-02's kinds, under REQ-002/AC-04 for any fact about real runs worth keeping. The repository's README describes the document check without a feature catalogue, and the specs index lists this spec.

## Failure modes and boundaries

1. **The tool cannot choose a sub-agent's model or effort.** The sub-agent runs on what the tool gives it; the check is still handed over (REQ-005/AC-02, AC-03).
2. **The sub-agent changed code.** Its change is restored from the commit made before the handover, so nothing the main agent wrote is lost with it, and the user is told (REQ-005/AC-04, AC-07).
3. **The check finds that the implementation, not a document, is wrong.** It is a finding handed back; the main agent fixes the code through the implementation steps and hands the check over again for what the fix touched (REQ-005/AC-05).
4. **An existing spec has a testing-decisions section and the change does not rewrite it.** It stays. `/tdd` no longer reads it for seams (REQ-002/AC-03, AC-05).
5. **A prototype exists for a surface and the change alters that surface without adding one.** The change is implemented directly; the prototype is neither updated nor marked (REQ-004/AC-02, AC-03).
6. **A change adds a new state to an existing surface (an empty state, a notice, a degraded form).** It adds no surface, so it needs no prototype unless more than one form is being weighed (REQ-004/AC-01).
7. **A change inside the gate is being implemented.** Until the change is delivered, its in-gate interface points are built to the prototype the user confirmed, and a difference from it is a defect of the implementation. Once it is delivered, the app is the baseline for them as for any other (REQ-004/AC-01, AC-03).
8. **The spec was rewritten before the code, as the flow asks.** Whether the change alters user-visible behaviour, and so whether the closing check runs, is judged against the specs at the branch's fork point, not against the specs the branch has already rewritten (REQ-001/AC-01).
9. **Something happened in the conversation and no file records it** (a rule newly decided, acceptance feedback). The sub-agent cannot see the conversation, so the handoff states the event; it states what happened, not what is or is not consistent (REQ-005/AC-04).
10. **Retiring an entry changes a citation inside another entry.** The citing entry is not rewritten for that; it comes under the new rules when a change edits its own statements (REQ-010/AC-01). The check script does not check it either, since it compares the entry with its ADR numbers and entry file names left out (REQ-008/AC-06).
11. **A project's ADR index still declares append-only.** The new rules apply there all the same, and the first change to an ADR in that project rewrites the declaration (REQ-010/AC-02).
12. **The closing check finds a touched ADR outside the rules, and the fix needs code changed**, such as a citation of a retired number in a source comment. The check rewrites what is document-only and hands back the rest as a finding (REQ-005/AC-05, REQ-008/AC-04, REQ-009/AC-05).
13. **The entries of one rule, merged, exceed the cap.** The result is split by decision rather than kept over the cap (REQ-008/AC-03, REQ-009/AC-04).
14. **Something an entry excludes is stated nowhere else**, such as an interface behaviour only an ADR describes. It is added to its home before it leaves the entry, so a rewrite loses nothing still true (REQ-009/AC-06).
15. **A rewrite meant to keep the decision changes it**, by dropping a rejected option or a negative consequence that still holds; removing content REQ-008/AC-02 excludes is not such a drop. That is a change of decision and is confirmed by the user before it is written; the delivery note's list of rewrites is where a reviewer catches one that was not (REQ-009/AC-02).
16. **A change leaves alone entries written under the earlier rules.** The check script does not check them against the template, so they stay as they are; their index rows are checked all the same, since the index is not an entry (REQ-008/AC-06, AC-07; REQ-010/AC-01). For the index it reads such an entry's title and status line with or without the template's spacing and list marker, and a status that opens with Proposed or Accepted names that state whatever follows. A cell it still cannot compare, such as the status of an entry whose status line is under another language's label, is named in its output rather than reported, so making the row pass never needs the entry edited.
17. **An entry is written but not yet committed, or not yet added to git.** The script reads the working tree, so it checks the entry before the commit it gates (REQ-008/AC-06).
18. **Entries are merged or split.** The options and negative consequences of all touched entries are listed together, deleted entries on the base side and added ones on the current side, so an option that moved to another entry is not taken for a dropped one (REQ-008/AC-08).
19. **A retired number is cited in a form other than `ADR-NNNN` or a former file name**, such as a bare number. The script does not find it; its output says which forms it searched, and the search of REQ-009/AC-05 still covers the rest (REQ-008/AC-05).
20. **The script cannot check**: a shallow clone, whose history cannot show which numbers were retired, or a working language with no column of fixed names. It fails instead of passing, and in the second case the writer makes its checks by hand (REQ-008/AC-09).

## Implementation Decisions

- The `features-catalog` skill keeps its name and keeps the closing document check; its selector describes the check only. Renaming it is left to the redesign of the flow.
- In that skill, the rules for handing over and for checking the handback open `SKILL.md`, and the three-stage regression moves to a reference file the sub-agent reads in full. The three ways a statement goes untrue stay the sub-agent's method for finding what to judge; it writes none of it down. The full-feature closeout stays where a closeout ticket's own session reads it.
- The wording for the model tier follows the rule already used for handing the CI wait to a sub-agent, and the wording for effort follows the rule `/research` already used for its gatherer, so the three rules read alike.
- The fixed names that existed only for catalogue pages leave the artifact-name tables; "In one line" is in the table of fixed names for `/to-spec`'s spec-writing file, which holds the specs index template. `scripts/check-artifact-names.mjs` checks that table against that file.
- The rules for ADRs stay in domain-modeling's `ADR-FORMAT.md`, the one place the other skills point to, which also says what the index declaration states. How sentences and characters are counted is defined once, in the header of the check script, and `ADR-FORMAT.md` points to it.
- The ADR check script lives in domain-modeling's directory and runs from a project's repository root, as github-ops' pin check does; exit 0 is a pass, 1 a violation, 2 a check it could not make. It reads the fixed names from `ADR-FORMAT.md`'s table of fixed names, `repo-scaffold/artifact-names/domain-modeling.ADR-FORMAT.md`, when it runs, finding each row by its English name, so it writes none of them itself. It reads `working-language` from `capabilities.toml` with the `tomllib` module built into Python 3.11 and later, since a skill directory carries no dependencies. It takes `--base <commit>` in place of the fork point, and `--all` for a full sweep, which has no base and lists nothing for review. The table of REQ-007 takes the place of its collection boundary; the capability registry's wording that a project's adoption of a practice is recorded in a document such as an ADR stands.
- `/prototype` keeps its rule that persistent documents hold conclusions rather than prototype paths, with a reason that no longer appeals to append-only documents. In ADR-FORMAT's artifact-name table the fixed name of the superseded state gives way to "Retired numbers" and "Withdrawn", and `scripts/check-artifact-names.mjs` checks the table against ADR-FORMAT.
- Every step that edits an ADR points to ADR-FORMAT: `/implement`'s light-path document check, the closeout's claim check, and the closing check's executor, whose rules in the features-catalog reference file also hold the second look of REQ-008/AC-04 and hand back as a finding any rewrite that would change a decision. The main agent lists the executor's ADR rewrites when it checks the handback.
- The owner's global instructions name the catalogue, the exhaustive section and the prototype rule in their outline of the flow. That file is outside this repository and is changed by the owner's session when this change merges.

## Out of Scope

- Handing a closeout ticket's full-feature closeout to a sub-agent.
- Migrating another project's `docs/features/` or the boundary entries of its specs, trimming its specs beyond REQ-002/AC-05 and REQ-013/AC-04, splitting them beyond REQ-013/AC-06, or rewriting its ADRs beyond REQ-010; a project's owner asks for that as a change of its own.
- A project's own ADRs and gate scripts about prototypes. A project that has decided its prototypes are the baseline keeps that decision until it reverses it.
- Renaming the `features-catalog` skill.
