# 第 1 步:调研 = ① 事实坐实 + ② 需求对齐

动手前两件事都要做。

**共识不得只留在对话里**——上下文一蒸发,下一轮谁也复现不出当时定了什么。术语按 ② 落进 CONTEXT.md,够 ADR 门槛的决策按 ② 落 ADR;没落进这两处的需求、边界与决策,每拍定一条,必须当场写进 `docs/.workings/<slug>/alignment.md`,一条一个列表项,写明拍定的内容与用户确认它的原话。`<slug>` 取本功能的 feature slug(与 `docs/features/` 对齐),尚未定的先与用户定下。这份记录的标题写为「需求对齐记录」,按 [产物固定名称](../repo-scaffold/artifact-names/grill-with-docs.md) 书写;它是施工记录,不代替 spec。**判据**:本轮拍定的每一条,说得出它此刻躺在哪个文件里。

## ① 事实调研(客观事实,自己查,不拿来问用户)

- 有参考实现或依赖库时,先读它的**真实代码与类型定义**坐实事实(可派 Explore agent 深挖 + 自己核对 .d.ts)。
- 依赖库必须按项目实际使用的版本调研(锁文件或已安装的版本);尚未引入的按准备引入的版本,决策涉及升级的另查目标版本,结论都标明版本。
- 产出带 **file:line 证据**的结论,明确区分「确认」(读代码/实测坐实)与「推断」(设计选择/猜测)。
- 要向用户提问前,必须先按 `/grilling` 文首的「事实与决策分流」判定该自己查还是该问(尚未载入 `/grilling` 的先载入);判为该问的,留到 ② 按 `/grilling` 提问。
- **别人写下的事实同样要坐实**:既有注释、文档、测试记录的是"当时有人这么认为",不是"现在仍如此";凡要作为本次决策前提的,当场用当前代码或实测复现一遍,复现不出的按未确认处理。

## ② 需求对齐(意图/决策归用户)

运行 `/grilling` 会话,同时按 `/domain-modeling` 维护领域模型。

设计问题在对话里拍不了板(证据不在桌面上)时,不得硬拍:原型能产出所缺证据的,先调 `/prototype` 拿到证据再拍;产不出的(如要靠上线或外部实测的选型),必须向用户写明缺哪项证据、要靠什么取得,由用户决定先定方向还是暂缓,先定方向且够 ADR 门槛的按 `/domain-modeling` 落「提议」态。
