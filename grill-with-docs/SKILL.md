# 第 1 步:调研 = ① 事实坐实 + ② 需求对齐

动手前两件事都要做。**未达成共识前不动手**——需求不明确宁可继续问。

**共识不得只留在对话里**——上下文一蒸发,下一轮谁也复现不出当时定了什么。各类共识的归宿见 §2(术语与决策)与 `/to-spec`(需求与边界);**判据**:本轮拍定的每一条,说得出它此刻躺在哪个文件里。

## ① 事实调研(客观事实,自己查,不拿来问用户)

- 有参考实现或依赖库时,先读它的**真实代码与类型定义**坐实事实(可派 Explore agent 深挖 + 自己核对 .d.ts)。
- 基于**最新版本**调研,不用旧版。
- 产出带 **file:line 证据**的结论,明确区分「确认」(读代码/实测坐实)与「推断」(设计选择/猜测)。
- 能从代码/环境查到的一律自己查;**只有决策才问用户**。
- **读外部数据定形态时,先全量枚举再下结论**:样本能证明"有",证不了"没有"——凡结论要写成"只有这几种形态"「不存在 X」,须换一种不依赖覆盖率的手段(扫全量目录并计数、穷举类型、走全历史),做不到就如实写"本次采样未见",不写"不存在"。这类否定结论错了没有下一步来纠正它。
- **别人写下的事实同样要坐实**:既有注释、文档、测试记录的是"当时有人这么认为",不是"现在仍如此";凡要作为本次决策前提的,当场用当前代码或实测复现一遍,复现不出的按未确认处理。

## ② 需求对齐(意图/决策归用户)

运行 `/grilling` 会话(独立决策并批、依赖决策分轮、每问附推荐答案、走决策树每个分支、共识前不动手),
同时按 `/domain-modeling` 维护领域模型:术语一敲定即写 CONTEXT.md;决策定形且过三门槛时,当场 offer ADR(格式见 domain-modeling/ADR-FORMAT.md,含三态规则——证据未闭环的落"提议"态)。

设计问题在对话里拍不了板(证据不在桌面上)时,**先 `/prototype` 拿证据再拍**,不硬拍:逻辑/状态模型 → 浏览器驾驶面板 + mermaid 图;界面长什么样 → 文字选型后单个 HTML。**原型代码是原型级的(不进产线),但产物保留**——验证出的决策落 ADR/spec,原型本身留在 `docs/prototypes/` 作模型的活文档(生命周期与防腐烂条款以 `/prototype` 为准)。
