# Review 代码(第 5 步)

重读本次全部改动,目标是找真 bug,不是走形式确认。审查对象是当前会话的改动本身(带实现上下文的自审;不做 diff 范围重建,PR 级独立审查走内置 /code-review)。

## 四层法(自底向上扫,层间有依赖)

1. **底层前提**〔事实层〕:有没有"从没质疑、默认它对但没验"的假设。这次改动依赖的事实还成立吗。
2. **可运行性**〔事实层〕:API/库的**真实行为** vs 我假设的行为,尤其没实测就写进方案的。race / 资源泄漏 / 状态错乱路径逐条走;涉及状态/effect 的,把"该状态能从哪些路径进入/退出"列全,逐条对照实现(对照 spec 失败模式节,但不局限于它)。
3. **安全正确性**〔逻辑层〕:建立在事实之上的逻辑——race/TOCTOU、"假安全"绕过口、错误路径也是攻击面;输入边界、路径穿越、注入、权限、敏感信息落盘/日志。
4. **一致性**〔表层〕:反查"**本次改动破坏了哪些原有不变量或路径**"(回归高发区,重构时尤其);与既有约定(错误处理风格、命名、协议语义、仓库成文规范文档)冲突处,要么服从,要么写明有意不一致的理由;对照下方**坏味道基线清单**,命中项进重构清单。

**迭代规则**:事实层(①②)有发现 → 修正后**重扫上层(③④)**——它们的结论建立在被推翻的前提上;逻辑层发现一般不用回验事实层(依赖单向)。不是平行四遍。
**实测规则**:不确定的事实层假设必须**实测坐实**,不靠读代码猜(终端时序、库的错误包装这类,读代码+推理都不可靠,要抓真实行为)。
输出按层分列:`【① 底层前提】发现/无` ……每层各自结论,一层一个视角,别摊薄。

## 坏味道基线清单(一致性层用;命中即记录,不当场改)

坏味道是信号不是判决:命中 = 需要一个"为什么这样是对的"的答案,答得出即豁免(记录理由)。
**范围规则**:只对**本次改动引入或实质触碰**的代码判定;改动之外既有代码的坏味道只记录(默认不做,除非用户点名),与「窄而完整」的"不顺手改进邻近代码"一致。
仓库成文规范与本清单冲突时,以成文规范为准。

- **名不达意**(Mysterious Name):标识符看不出用途
- **重复代码**(Duplicated Code):多处出现同一逻辑
- **依恋情结**(Feature Envy):过度访问其他对象的内部状态
- **数据泥团**(Data Clumps):总是结伴出现的参数/字段
- **基本类型偏执**(Primitive Obsession):原始类型硬扛领域概念
- **重复的条件级联**(Repeated Switches):相同条件分支散布多处
- **霰弹式修改**(Shotgun Surgery):一个逻辑改动被迫散改多处
- **发散式变化**(Divergent Change):一个文件因多个不相关原因被改
- **夸夸其谈通用性**(Speculative Generality):无人使用的抽象/参数
- **过长消息链**(Message Chains):深层导航依赖
- **中间人**(Middle Man):纯转发、无增值的委托
- **被拒绝的遗赠**(Refused Bequest):继承了却大多弃用

## 产出(三类,处理方式不同)

- **bug——当场修**:修掉并补成测试(先让新测试对着 bug 红一次,验证测试有效)。
- **重构——只整理,不执行**:把实现循环攒下的重构项、坏味道/约定冲突命中项、缺 seam 补注入项(被迫 cast 才能测的)汇成清单,每项写明:内容、理由(命中哪条/违反哪个约定)、影响面、建议处理(现在做/另开任务/不做)。**提交用户确认,按其决定处理**;确认执行的,安全网是已攒的测试。
- **分层结论报告**:四层各自的发现与结论。
