# Review 代码(第 5 步)

重读本次全部改动,目标是找真 bug,不是走形式确认。审查对象是当前会话的改动本身(带实现上下文的自审;不做 diff 范围重建,PR 级独立审查走内置 /code-review)。

## 四层法(自底向上扫,层间有依赖)

1. **底层前提**〔事实层〕:有没有"从没质疑、默认它对但没验"的假设。这次改动依赖的事实还成立吗。**注释、测试与文档是这类假设最常见的载体**——它们只能证明"当时有人这么决定",不能证明"现在仍然对";通过的测试尤其有欺骗性,绿只说明实现与**当时的理解**一致。判据是这条理由能否用当前事实复现,不能就是过期依据。
   **本层同样约束本次新写的注释**:凡陈述因果的注释("这样写是为了避免 X"、"改成 Y 是因为 Z"),其因果**须已坐实**;未坐实的只写做法与目的,不写归因。一条错误归因比没有注释更坏——后人会拿它当已验证的事实往下推,而它在字面上与坐实过的注释毫无区别,不会有任何东西提示它可疑。
2. **可运行性**〔事实层〕:API/库的**真实行为** vs 我假设的行为,尤其没实测就写进方案的。race / 资源泄漏 / 状态错乱路径逐条走;涉及状态/effect 的,把"该状态能从哪些路径进入/退出"列全,逐条对照实现(对照 spec 失败模式节,但不局限于它)。错误/降级路径逐条标注**故障逃逸面**:自伤(只影响该条目自身)/ 同层逃逸(清空或污染其他条目,含遮蔽判定这类跨条目计算)/ 上层逃逸(拖垮聚合或整次流程)——这个标注决定它在产出里的归类。
3. **安全正确性**〔逻辑层〕:建立在事实之上的逻辑——race/TOCTOU、"假安全"绕过口、错误路径也是攻击面;输入边界、路径穿越、注入、权限、敏感信息落盘/日志。
4. **一致性**〔表层〕:反查"**本次改动破坏了哪些原有不变量或路径**"(回归高发区,重构时尤其);与既有约定(错误处理风格、命名、协议语义、仓库成文规范文档)冲突处,要么服从,要么写明有意不一致的理由——但若该约定的依据是一条注释/测试所记录的理由,先按①核它是否仍成立,别直接服从;对照下方**坏味道基线清单**,命中项进重构清单。

**迭代规则**:事实层(①②)有发现 → 修正后**重扫上层(③④)**——它们的结论建立在被推翻的前提上;逻辑层发现一般不用回验事实层(依赖单向)。不是平行四遍。
**实测规则**:不确定的事实层假设必须**实测坐实**,不靠读代码猜(终端时序、库的错误包装这类,读代码+推理都不可靠,要抓真实行为)。两条配套:
- **优先横向对照**:同类物件在同一环境下跑同一条检查,差异直接指出问题所在——同机的同类 app、同批产物里正常的那个、同一接口的另一个实现。比纵向读代码快一个数量级,且不依赖对实现的理解是否正确。
- **实测本身也会假绿**:一次实测算数要同时满足——① 断言的对象是目标属性本身(不是"存在"这类恒真量);② 该断言在目标属性不成立时确实会红。形态清单与判据见 [false-greens.md](./false-greens.md)。
输出按层分列:`【① 底层前提】发现/无` ……每层各自结论,一层一个视角,别摊薄。

## 坏味道基线清单(一致性层用;命中即记录,不当场改)

坏味道是信号不是判决:命中 = 需要一个"为什么这样是对的"的答案,答得出即豁免(记录理由)。
**范围规则**:只对**本次改动引入或实质触碰**的代码判定;改动之外既有代码的坏味道只记录(默认不做,除非用户点名),与「窄而完整」的"不顺手改进邻近代码"一致。
仓库成文规范与本清单冲突时,以成文规范为准。

- **名不达意**(Mysterious Name):标识符看不出用途
- **重复代码**(Duplicated Code):多处出现同一逻辑
- **依恋情结**(Feature Envy):过度访问其他对象的内部状态
- **数据泥团**(Data Clumps):总是结伴出现的参数/字段
- **基本类型偏执**(Primitive Obsession):原始类型硬扛领域概念
- **重复的条件级联**(Repeated Switches):相同条件分支散布多处
- **霰弹式修改**(Shotgun Surgery):一个逻辑改动被迫散改多处
- **发散式变化**(Divergent Change):一个文件因多个不相关原因被改
- **夸夸其谈通用性**(Speculative Generality):无人使用的抽象/参数
- **过长消息链**(Message Chains):深层导航依赖
- **中间人**(Middle Man):纯转发、无增值的委托
- **被拒绝的遗赠**(Refused Bequest):继承了却大多弃用

## 每条发现先判「类级还是实例级」,再谈怎么修

**判据:把这条发现改写成一句不点名该实例的话。**

- **改不掉**(必须说出是哪个文件 / 哪个实现 / 哪个语言)→ 实例级,就地修完即可。
- **改得掉**——「X 相对基准丢了 Z」「X 把本该分开的两件事合并了」这种句式,主语可换成任何同类实例 → **类级,必须对全部同类实例逐一复查,不得只修被点名的那个**。

**机制**:review 的范围由 reviewer 的视野决定,缺陷的分布不由它决定。工作按实例切分时,一条类级缺陷被切成若干份,每份清单只呈现自己那一份,且没有任何一份能告诉你别处也有——于是清单读起来像"这个实例的待办",被当成待办逐条划掉即漏。**清单的边界是视野,不是缺陷的边界。**

**触发条件**:凡工作按实例切分——同一契约的 N 份实现、同一模式的 N 个调用点、按模块拆分的审查——一律适用。

**做法**:类级发现落地前,必须用一条不依赖覆盖率的手段枚举全部同类实例(类型系统、目录清单、注册表),逐个核对,并**把核对结果写进产出**:"其余 N 个已查,其中 M 个同样命中"。只写"已修复"不得视为完成。

## 产出(三类,处理方式不同)

**错误处理类发现先按故障逃逸面分类,再定归属**(2026-08-01 定案,勿用发生率开脱):降级会向**同层**(清空/污染其他条目,含跨条目计算)或**上层**(聚合/整次流程)逃逸的 → 是 bug,当场修;只影响**自身条目**展示的 → 进重构清单缓办。发生率低不改变逃逸类的定性——单点故障波及无辜就是要修。

- **bug——当场修**:修掉并补成测试(先让新测试对着 bug 红一次,验证测试有效)。
- **重构——只整理,不执行**:把实现循环攒下的重构项、坏味道/约定冲突命中项、缺 seam 补注入项(被迫 cast 才能测的)汇成清单,每项写明:内容、理由(命中哪条/违反哪个约定)、**影响面(首要按故障逃逸面写:自伤/同层/上层)**、建议处理(现在做/另开任务/不做)。**提交用户确认,按其决定处理**;确认执行的,安全网是已攒的测试。
- **分层结论报告**:四层各自的发现与结论。
