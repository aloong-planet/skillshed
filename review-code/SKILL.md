# Review 代码

审查对象是一段 commit 范围,读时不带作者的上下文:目标是找真 bug,不是走形式确认。

- **受交接执行独立审查的**(交接给出检出的绝对路径、审查范围的起点与交出的 commit,要求载入本 skill 与 `/review-tests`):必须完整读取 [independent-review.md](independent-review.md) 并按其执行;下文「产出」节里改代码与提交用户确认的做法,改为按该文件交回。
- **在写这次改动的会话里运行的**(写改动的一方自审这次改动):审的是本会话的这次改动——从分叉点(`git merge-base HEAD origin/<默认分支>`)到 `HEAD` 的 commit 范围,加上工作区里未提交的改动;读时同样不得拿实现时的推理代替重读改动本身。

## 分层扫查(自底向上,层间有依赖)

1. **底层前提**〔事实层〕:有没有"从没质疑、默认它对但没验"的假设。这次改动依赖的事实还成立吗。**注释、测试与文档是这类假设最常见的载体**——它们只能证明"当时有人这么决定",不能证明"现在仍然对";通过的测试尤其有欺骗性,绿只说明实现与**当时的理解**一致。判据是这些载体记录的理由能否用当前事实复现,不能就是过期依据。
   **本层同样约束本次新写的注释**:凡陈述因果的注释("这样写是为了避免 X"、"改成 Y 是因为 Z"),其因果**须已坐实**;未坐实的只写做法与目的,不写归因。一条错误归因比没有注释更坏——后人会拿它当已验证的事实往下推,而它在字面上与坐实过的注释毫无区别,不会有任何东西提示它可疑。
2. **可运行性**〔事实层〕:API/库的**真实行为** vs 假设的行为,尤其没实测就写进方案的。race / 资源泄漏 / 状态错乱路径逐条走;涉及状态/effect 的,把"该状态能从哪些路径进入/退出"列全,逐条对照实现(对照 spec 失败模式节,但不局限于它)。错误/降级路径逐条标注**故障逃逸面**(基准是该路径每次处理的单个条目):自伤(只影响该条目自身)/ 同层逃逸(清空或污染其他条目,含遮蔽判定这类跨条目计算)/ 上层逃逸(拖垮聚合或整次流程)——这个标注决定它在产出里的归类。
3. **安全正确性**〔逻辑层〕:建立在事实之上的逻辑——race/TOCTOU、"假安全"绕过口、错误路径也是攻击面;输入边界、路径穿越、注入、权限、敏感信息落盘/日志。
4. **一致性**〔表层〕:反查"**本次改动破坏了哪些原有不变量或路径**"(回归高发区,重构时尤其);与既有约定(错误处理风格、命名、协议语义、仓库成文规范文档)冲突处,要么服从,要么写明有意不一致的理由——但若该约定的依据是一条注释/测试/文档所记录的理由,先按①核它是否仍成立,别直接服从;对照下方**坏味道基线清单**,命中项进重构清单。

**迭代规则**:事实层(①②)有发现 → 修正后**重扫上层(③④)**——它们的结论建立在被推翻的前提上;上层(③④)的发现不触发事实层重扫(依赖单向)——④ 对单条约定依据的回核是层内动作,不算重扫。不是平行四遍。受交接执行、不修正的,事实层的发现推翻了哪条前提,上层就按推翻后的前提重扫。
**实测规则**:不确定的事实层假设必须**实测坐实**,不靠读代码猜(终端时序、库的错误包装这类,读代码+推理都不可靠,要抓真实行为);环境或工具确实做不到的,按 [false-greens.md](./false-greens.md) 的「处理方式」节办,不得用推理顶替实测。两条配套:
- **优先横向对照**:同类物件在同一环境下跑同一条检查,差异直接指出问题所在——同机的同类 app、同批产物里正常的那个、同一接口的另一个实现。比纵向读代码快一个数量级,且不依赖对实现的理解是否正确。
- **实测本身也会假绿**:一次实测算不算数,判据与形态清单见 [false-greens.md](./false-greens.md)。

## 坏味道基线清单(一致性层用)

坏味道是信号不是判决:命中 = 需要一个"为什么这样是对的"的答案,答得出即豁免。
**范围规则**:只对**本次改动引入或实质触碰**的代码判定;改动之外既有代码的坏味道只进重构清单、默认不做(除非用户点名),与「窄而完整」的"不顺手改进邻近代码"一致。
仓库成文规范与本清单冲突时,以成文规范为准——前提是该规范的依据按①核过仍成立;核不过的不直接服从。

- **名不达意**(Mysterious Name):标识符看不出用途
- **重复代码**(Duplicated Code):多处出现同一逻辑
- **依恋情结**(Feature Envy):过度访问其他对象的内部状态
- **数据泥团**(Data Clumps):总是结伴出现的参数/字段
- **基本类型偏执**(Primitive Obsession):原始类型硬扛领域概念
- **重复的条件级联**(Repeated Switches):相同条件分支散布多处
- **霰弹式修改**(Shotgun Surgery):一个逻辑改动被迫散改多处
- **发散式变化**(Divergent Change):一个文件因多个不相关原因被改
- **夸夸其谈通用性**(Speculative Generality):无人使用的抽象/参数
- **过长消息链**(Message Chains):深层导航依赖
- **中间人**(Middle Man):纯转发、无增值的委托
- **被拒绝的遗赠**(Refused Bequest):继承了却大多弃用

## 每条发现先判「类级还是实例级」,再谈怎么修

**判据:把这条发现改写成一句不点名具体实例的话。**

- **改不掉**(必须说出是哪个文件 / 哪个实现 / 哪个语言)→ 实例级,只处理被点名的这一处,不必扩查同类;修还是缓办按下方**产出**分类定。
- **改得掉**(主语可换成任何同类实例,如「X 相对基准丢了 Z」「X 把本该分开的两件事合并了」)→ **类级,必须对全部同类实例逐一复查,不得只修被点名的那个**。

**机制**:review 的范围由 reviewer 的视野决定,缺陷的分布不由它决定。工作按实例切分时,一条类级缺陷被切成若干份,每份清单只呈现自己那一份,且没有任何一份能告诉你别处也有——于是清单读起来像"这个实例的待办",被当成待办逐条划掉即漏。**清单的边界是视野,不是缺陷的边界。**

**触发条件**:凡工作按实例切分——同一契约的 N 份实现、同一模式的 N 个调用点、按模块拆分的审查——一律适用。

**做法**:类级发现落地前,必须用一条不依赖覆盖率的手段枚举全部同类实例(类型系统、目录清单、注册表),逐个核对,并**把核对结果写进这条发现**:"其余 N 个已查,其中 M 个同样命中"。只写"已修复"不得视为完成。

## 产出(两类,处理方式不同)

每条发现都必须按 [independent-review.md](independent-review.md)「交回」节第 1、2 项写;不得为没有发现的层写结论。

**错误处理类发现先按故障逃逸面分类,再定归属**:判为**同层**或**上层**逃逸的 → 是 bug,当场修;判为**自伤**的 → 进重构清单缓办。发生率低不改变逃逸类的定性——单点故障波及无辜就是要修。

- **bug——当场修**:修掉并补成测试(先让新测试对着 bug 红一次,验证测试有效);**该红没红时先判是测试无效还是 bug 已不在**,不得直接把断言调松到能红。
- **重构——只整理,不执行**:把实现循环攒下的重构项与上文各处判入清单的发现汇成清单,每项写明:内容、理由(命中哪条/违反哪个约定)、**影响面(首要按故障逃逸面写:自伤/同层/上层)**、建议处理(现在做/另开任务/不做)。**提交用户确认,按其决定处理**;确认执行的,安全网是已攒的测试。受交接执行的,每项按一条发现交回,它描述的失败写成会因此出错的那处改动(如只改了散落各处中的一处)或那条自伤路径。
