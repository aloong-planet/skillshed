# 独立审查

本文适用于受交接执行独立审查的一方(下称审查方):交接给出检出的绝对路径、审查范围的起点与交出的 commit,要求载入 `/review-code` 与 `/review-tests` 并执行审查。本文规定审查方审什么、不得做什么与交回什么;代码怎么审按 [SKILL.md](SKILL.md),测试怎么审按 [review-tests/SKILL.md](../review-tests/SKILL.md)。入口:这两份 SKILL.md 的文首。

## 审什么

审查方必须对同一个 commit 范围——从交接给的范围起点到交出的 commit——一次做完下列各项,不得分轮,也不得再派子 agent 做其中任何一项。改动是怎样做出的、作者为什么这样写,交接里没有,审查方也不得去找:读的只有该范围在 git 里的改动、检出里的文件与交接给的票。

1. **代码**:范围内的改动,按 [SKILL.md](SKILL.md) 的分层扫查。
2. **测试**:范围内新写或改动的测试,按 [review-tests/SKILL.md](../review-tests/SKILL.md) 的各维度。
3. **验收条件**:交接给了票的,取票的验收项;没给票的,取交接点名的 spec 在该范围内新增或改写的验收条件(该 spec 文件在范围内的 diff 里新增或改写的验收条件行)。对每一条,必须找出它在哪里实现(文件与函数)、由什么守着:一个测试,或票为它写明的门禁(Gate)。没有实现的,或两种守护都没有的,该条即为一条发现;票写明它的保障是人工取得的证据(Evidence)的,以及测试文件头按 `/tdd`「覆盖来源」节「测不到的」一条注明为缺口的,不因没有测试而成为发现。改动加了而没有任何一条验收条件要求的行为,是一条发现;实现与 spec 的陈述不一致的,也是一条发现。没有票、范围内也没有新增或改写验收条件的(如恢复 spec 已有行为的修复),必须把改动的代码对照它所实现的 spec 原文核对,检查过的验收条件数记为 0。
4. **代价条目**(只在交接写明本次改动是核心档时做):这时第 2 项按 [review-tests/SKILL.md](../review-tests/SKILL.md) 维度 1 对照的覆盖清单,含 `/tdd`「覆盖来源」节「核心档改动另加所触代码的代价条目」一条另加的各项。必须先按该条取出范围内改动所触代码的全部这类条目并逐条列出,再作为第 2 项覆盖核对的一部分逐条核对:既没有驱动它的用例、测试文件头也没有按同节「测不到的」一条为它注明缺口的,该条即为一条发现。

## 不得做什么

- 不得改动检出里或施工记录目录里的任何文件,不得提交。
- 可以运行范围内新写或改动的测试,以及为复现一条发现而自己写的命令;为此需要的文件必须建在检出之外(如 `mktemp -d` 新建的目录)。不得运行别的测试;只收集、不执行用例的命令(如 `pytest --collect-only`)不在此列。
- 项目声明启用了变异检验的(按 [review-tests/SKILL.md](../review-tests/SKILL.md) 维度 3 判定),变异检验的临时改动必须在交回之前全部还原,还原的做法按 [mutation-testing.md](../review-tests/mutation-testing.md)。

## 交回

最终交回必须依次包含,且只得包含:

1. **每条发现**:一个编号、一句话标题,以及它描述的失败——用户做了什么、什么数据到来、或对代码作怎样一处改动会产出错误的结果;缺守护的,写明为什么没有测试会因此变红。关于可以运行的行为的发现,必须给出复现它的命令与它得到的输出;复现要用到审查方取不到的数据或环境的,必须改为在该条发现里写明没有复现、缺的是什么,以及它依据的哪件事实因此没有查证。
2. **不带修复**:发现不得带补丁、修复草稿或测试草稿;修复的方向可以用一句话点出。
3. **各项的数**:发现之后,写明检查过的验收条件数与审过的测试数;交接写明核心档的,再写明按「审什么」第 4 项核对过的代价条目数。没有发现的,写明没有发现,并给出这些数。
4. **按全局指令「项目能力声明」节须写明的行**:审查用到的能力是未启用、不适用或未确认的,在第 3 项的数之后各写一行。

不得写:没有发现的层或维度的结论、审查是怎样做的、表格。不得在任何地方写审查记录。
