# 先红与变异

本文的条文只在项目能力 `red-green-mutation` 启用时适用(ID 定义见 [capabilities-registry.md](../repo-scaffold/capabilities-registry.md))。是否启用,由引用本文的 `/tdd`「循环规则」节与 `/review-tests` 维度 3 先行判定;未启用时不得执行本文任何一条。

本文只管两件事:修 bug 以外的测试先红,以及对测试做变异检验。修 bug 的测试对着未修的代码先红一次(`/tdd`「循环规则」节),以及门禁与测试运行体制本身的变异验证(新建或改动门禁、切换测试运行体制后重放变异),都不归本文管辖,照各自所在的 skill 执行,不因本能力未启用而跳过。

## 先红

- **红先于绿**:修 bug 以外的每个测试,必须先写成并跑出失败,再写刚好让它过的代码。完成判据按 `/tdd`「循环规则」节的「红要红得对」与「红的来源必须是真实可达的状态」两条;未过判据的红不算数。

## 变异

- **红过一次不等于有效。** 用例在开发途中确实失败过,只证明它对**某个**条件敏感,不证明它对**设计要捕捉的那个**失败模式敏感——两者经常不是一回事。判据:说得出用例当初红的成因,且该成因正是本用例要防的;说不出、或成因另有其事(编译不过、所断言的取值当时尚不存在、环境未就绪),则有效性**尚未验证**,须补一次变异——把实现改成该用例要防的那种错法,确认它转红,再还原。把偶然的红当作设计有效的红,得到的是一条自己给自己发的合格证。
- **变异检验自己也会假绿,三条缺一不可**(形态与成因见 [review-code/false-greens.md](../review-code/false-greens.md) 形态四):①**到达**——变异后没红时,先用独立于该断言的证据确认变异真的落在被测路径上(同名符号改错对象、构建产物陈旧都会让它没到达),再判断言是否恒真;②**归因**——变异后红了,须核对报错位置就在变异处,否则红的可能是别的东西;③**还原**——只撤销变异本身,不得用把文件恢复到版本库的命令去还原,那会连未提交的正式改动一并丢弃,而其后的一切红绿都失去意义。
- **读构建产物的用例,变异后必须先重新构建再跑**:端到端、烟测这类用例读的是构建输出,不重新构建,变异根本进不了产物——「变异不生效」与「测试确实无效」在结果上完全一样。

同名符号改错对象的样例(上面「到达」一条):

```typescript
// BAD: 项目里有两处同名 key,只替换"第一处"改的是另一个对象;
//      测试照绿,而结论被记成"用例无效"
// GOOD: 改完先确认变异真的落在被测路径上(打印/断点/临时抛错),再判红绿
```
