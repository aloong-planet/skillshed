# Test-Driven Development

TDD 是测试与实现交替推进的纵切循环,哪些测试必须先红见「循环规则」节。本 skill 是让循环产出**值得留下的测试**的参考:什么是好测试、测试站在哪、用例落在哪一层、用例与 helper 放在哪里、不写重复的用例、覆盖来源、测试资源复用、反模式、循环规则。每个循环前后都对照,不要事后补看。
探索代码库时按全局指令「读项目词汇表 `CONTEXT.md`」查 CONTEXT.md(测试名与接口词汇对齐领域语言),尊重所触及区域的 ADR。

## 什么是好测试

经**公开接口**验证**行为**,不碰实现细节。代码可以整个重写,测试不该动。好测试读起来像规格说明——"user can checkout with valid cart" 直接告诉你存在什么能力——并在重构后存活。
样例见 [tests.md](./tests.md)。

**基础要求**,每个测试三条都必须满足:①孤立可复现——单独运行、在整套里运行与重复运行,结果都相同;②驱动目标行为并断言它的效果,不得只调用一下而不断言;③断言对象必须是该测试声称验证的那个结果,不得换成别的对象(同一行为的其他产物、与该行为无关的对象)。

## Seam——测试站在哪

**seam** 是测试所站的公开边界:在此观察行为,不把手伸进内部。测试只写在 seam 上,永不对着内部写。

- **预定 seam**:写任何测试前先写下要测的 seams。既有 seam 能承载要测的行为的,必须复用;**seam 不明或需新建时才问用户,否则自己定**。
- **缺 seam 是设计信号**:被迫 cast 私有成员/直写内部状态才能测 = 模块缺注入 seam——**先补构造注入**(时钟/网络/存储/随机数经构造参数注入)**再测,不许 cast 凑**。想测到接口背后,说明模块形状不对(interface is the test surface)。
- **可达状态规则**:测试构造的一切状态(含 cast 绕过可见性、直写内部状态造出的 setup)必须经**公开路径可达**。公开接口到不了的状态,测它就是测幻觉——找该状态的真实入径改写,找不到就说明该断言守的是不存在的场景。**判据**:这份 setup 换成"经公开接口一步步做到该状态"能不能做到?做不到,就是手工摆出来的。

## 用例落在哪一层

本节约束计划新写或改动的两类用例:穿过整个应用的用例(端到端、浏览器驱动、经真实进程的命令行验收)与断言测试基建本身的用例。

- **规则放单元测试**:用例的期望值只由一条规则的输入决定(解析、判定、计算、取值回退),且这条规则能写成纯函数的,规则的每个分支必须写成该纯函数的单元测试,不得写成穿过整个应用的用例;规则写在别处而能抽出的,必须先抽出纯函数再测。穿过整个应用重测一个分支,付的是启动整个应用的代价,这个分支的错误单元测试都已能发现。
- **接线只留接线用例**:有行为触发点的接线(规则的输入经真实链路到达规则、结果经真实链路生效)必须由穿过整个应用的用例证明,每条接线一个用例。用例的输入必须能分辨接线完好与接线被改坏:只有一个元素的列表分辨不出「传了整个列表」与「只传了第一项」,与默认值相同的输入分辨不出「传了」与「没传」。
- **判据**:断言规则的穿过整个应用的用例,必须说得出「把纯函数以外的哪一处接线改坏,只有它会红」;说不出的属于重测规则,不得写。
- **测试基建的自测放在基建旁边**:断言对象是测试基建本身(启动器、fixture、测试替身、断言辅助函数、钉住环境的机制)的用例,必须写在基建所在目录的测试文件里,不得写进功能的测试文件。**判据**:这个用例红了,要修的是测试基建还是产品?要修测试基建的,属于本条。

## 用例与 helper 放在哪里

本节约束计划新写、改动或移动的穿过整个应用的用例放进哪个测试文件,以及这些用例用到的测试辅助函数(下称 helper)放在哪里。断言测试基建本身的用例按「用例落在哪一层」节「测试基建的自测放在基建旁边」一条放,不在本节。

- **按功能归档**:用例必须放进以它所断言的规则所属功能的 spec slug 命名的测试文件(slug 与 `docs/specs/` 的文件名对齐;拆出子主题文件的按本节「拆分只按子主题」一条)。**判据**:说得出这条规则写在或将写进 `docs/specs/` 的哪份 spec。下列情形按各条办:
  - 只为到达被断言处而在页面间跳转的,跳转不算被断言的规则,用例放进被断言的那个功能的文件;跳转本身就是被断言的规则的,放进这条规则所属功能的文件,不论从哪里跳起。
  - 一条规则由两个功能的 spec 各写一部分的,各部分的断言放进各自功能的文件。
  - 其余断言了几个功能的规则的用例,放进用例名所描述的那个功能的文件;移动这样的既有用例时,不得为换文件而拆它。
  - 规则不属于任何功能、而是整个应用怎样启动、刷新或保持缓存的,放进项目为这类用例指定的那个文件;项目还没指定的,先与用户定下。
- **拆分只按子主题**:一个功能的测试文件只在其中一部分是能单独陈述的子主题时才拆,拆出的文件以 `<slug>-<子主题>` 命名;不得因文件大小而拆,也不得为测试文件设行数上限。**判据**:说得出拆出的部分对应该功能 spec 里的哪几条需求;说不出的不得拆。
- **共用的 helper 放共享目录**:两个及以上功能的测试文件用到的 helper,必须放进这类用例共用的 helper 目录,由各文件导入;只有一个功能用到的,留在该功能的测试文件里。另一个功能的文件也要用某个 helper 时,必须先把它移进共享目录再导入,不得复制。项目还没有共享目录的,在这类用例所在的测试目录下新建一个。**判据**:每个 helper 说得出用到它的功能测试文件有几个;两个及以上的,必须在共享目录里且只有这一份定义。

## 不写重复的用例

本节约束计划新写或改动的用例,以及被它们覆盖的既有用例。比较对象是覆盖同一 spec 条目(没有 spec 的,同一条成功标准)的其他用例,以及经同一 seam 公开接口的既有用例。

- **只差取值的合并**:与某个比较对象只有字面量或传入取值不同的用例,必须与它合并成一个参数化用例;测试框架不支持参数化的,不受本条约束。
- **红的情形已被覆盖的不写**:一个用例会红的每种情形,都指得出某个比较对象里同样会红的断言的,不得写,已写的必须删除。两个方向各判一次:新用例覆盖了既有用例的,删既有用例。下列情形不算覆盖:
  - 覆盖它的用例运行条件更苛刻(只在 CI、需要真实账户或需要独占桌面才运行):它的红来得更晚。
  - 它是「用例落在哪一层」节「规则放单元测试」一条要求的单元测试,覆盖它的是穿过整个应用的用例:它留下,那个用例该不该留按该节「判据」一条判。
- **互相覆盖时只删一个**:保留运行条件宽松的;运行条件相同的,保留其中一个。
- **判据**:每个计划新写或改动的用例(参数化用例的每一组取值各算一个),必须说得出「被测代码的哪一种改坏会让它红,而比较对象里没有一个断言会红」;说不出的,必须指得出它属于「红的情形已被覆盖的不写」一条列出的哪一种不算覆盖的情形;两样都说不出的即为已被覆盖,必须按该条与「互相覆盖时只删一个」一条处置。

## 覆盖来源

覆盖清单 = 本次改动交付的每条验收条件各一项,加上本次新增或改动的「失败模式与边界」条目中、处理错会造成 `/to-spec`「失败模式与边界的写入条件」节所列四种代价之一的每条各一项;其余条目不要求用例。逐项转为纵切循环直到清空。覆盖清单之外的既有用例,不因不在清单里而删。「用例落在哪一层」节定的是清单各项的用例放在哪一层(含证明接线的那一个),不为清单之外的分支另要求用例。
没有 spec 的改动,覆盖清单是动手前写下的成功标准。
**声称覆盖的边界必须真被驱动**:用例名或注释声称覆盖某个分支或状态的,构造的输入必须把执行带进该分支或状态。**判据**:指得出该用例里哪个输入把执行带进了它;指不出的,这条覆盖在清单上记为完成,实际为零。
**测不到的**(无行为触发点的接线、需真实环境才走得到的路径)不得硬测,也不得用私测内部状态凑覆盖率:必须在测试文件头注明缺口与补测条件——诚实的缺口好过造假的绿。
**读外部数据的用例,fixture 至少一例照真实样本的形态造**:功能读取外部或他方产生的数据(用户文档、agent 生成物、第三方配置、外部 API)的,必须至少有一份 fixture 照真实样本造:去真实数据目录看实际长什么样,照着造;可脱敏、可裁剪,结构与特征必须保留。看真实样本时查明的、spec 没写的数据事实(结构特征、取值形态),必须写进 spec,写成对该数据的陈述,不写成测试怎样设计。覆盖清单来自 spec,fixture 若也来自“我以为数据长什么样”,两者同源——spec 的盲点被 fixture 原样继承,测再多只是把同一个想象验证多遍;真实样本是唯一与 spec 独立的样本源。
**fixture 形态的判据**:对每份 fixture 问“它的形态是我想出来的,还是看过真实数据后照着造的?”——前者与 spec 同源,不构成独立验证。核对的是形态而非数值:真实数据里有而没想到的**结构特征**(嵌套、引用、链接、混合类型、异常但合法的写法)才是盲点所在;字段值随便造无妨。

## 测试资源复用

本节约束新写或改动的测试所用的昂贵资源。

**昂贵资源**:一次加载或构建耗时 1 秒以上的测试资源,如模型、建好的数据库与索引、编译产物、替身服务进程、大体积 fixture;耗时不确定的,必须先实测一次再判。

- **只加载一次**:内容由同一组参数决定的同一份昂贵资源,必须在测试框架允许共享的最大范围内只加载或构建一次:框架能跨文件共享的(如 pytest 的 session fixture,或写到磁盘、由 Jest/Vitest 的 globalSetup 构建的模板),按整个测试进程共享;框架按文件隔离内存对象的,按文件共享(如 beforeAll)。不得在每个用例里重新加载或构建;例外只有本节的「被测构建」与「独立标识」两条。
- **可写资源用复制品**:用例会改动的资源(写入的库、目录、文件,或会改其属性、配置的对象)必须从只建一次的模板复制一份给该用例,不得为它从头重建(「独立标识」一条的情形除外),也不得改共享的那份;不能确认是否会被写的,按会被写处理。
- **被测构建**:被测行为本身就是某个加载或构建步骤时,用例必须执行该步骤;它的前置状态非空的,必须从模板复制,不得为准备前置状态重跑前面的构建。
- **独立标识**:复制品与模板共享内部标识(ID、版本号、创建时间);断言依赖两份资源各自独立构建、标识不同的用例,必须各自构建,不得用复制品。
- 被测代码在内部自行加载昂贵资源、外部无法传入已加载实例的,即为缺 seam:必须在被测代码侧补注入或进程内复用,复用的键必须覆盖决定资源内容的全部参数,否则参数不同的调用会拿到同一份资源;补注入的做法按「Seam——测试站在哪」节「缺 seam 是设计信号」一条。补 seam 会改变 spec 已定义的行为时,必须先经用户确认并回写 spec,再写依赖它的测试。
- 设计前必须检索本仓库测试中已有的共享 setup 与复制模板;已有同类资源的共享或复制做法的,必须沿用,不沿用的必须说得出理由。
- **执行顺序取自收集结果**:进程内共享的昂贵资源(进程级缓存、session 范围 fixture 的产物)会被某个用例清空或释放时,其余用例对它是复用还是重新加载取决于执行顺序。哪些用例会清掉它,必须检索全部测试里清空或释放该资源的调用得出;它们与用到该资源的用例的先后,必须取自测试框架实际收集出的顺序(如 pytest 的 `--collect-only`;收集只导入测试代码并列出用例,不执行任何用例),不得由框架源码、文档、注释、文件名或标记约定推出——测试框架可按 fixture 参数等重排用例,推出的顺序与实际可以不同。
- **判据**:对每份昂贵资源,说得出它在一个测试进程里加载或构建几次、由哪个共享 setup 提供;说不出,或次数随用例数增长,即违反本节。

## 反模式(样例见 tests.md)

- **实现耦合**:mock 只得按 [mocking.md](./mocking.md) 的范围用;不得测私有方法、断言调用次数/顺序,不得绕过接口旁路验证(读文件、查库、读内部字段,代替经公开接口读回);测试名不得描述实现怎么做(HOW,如 `checkout calls paymentService.process`),必须描述能力(WHAT)。征兆:重构没改行为,测试却碎;旁路验证还会掩盖缺陷:经接口读回的结果错了,测试照样通过。
- **假通过**:每个测试都必须答得出「它在什么情况下会红」,答不出的即为嫌疑假通过。下列形态是答不出的已知成因,写测试时必须逐一避开;清单不穷尽,不在清单里的仍按本条的问题判:
  - **恒真断言**:断「不超过阈值」的,造的数据量必须超过该阈值(5 条数据断 ≤200 恒成立);不得写恒成立的断言,包括用 `toBeTruthy` 断一个恒为真值的结果。
  - **同义反复**:期望值按实现同款方式重算,构造性恒真。**期望值三禁**——禁与实现同算法重算;禁复用输入对象作期望;禁断言 import 进来的同一常量。期望值必须来自独立真值:已知字面量、手算例、规格。
  - **守旧路径**:断言对象必须在生产代码的活路径上,不得是废弃常量或已被取代的行为——锁着旧路径的测试一直绿,现行为却没有测试守。**判据**:检索生产代码,断言对象仍被引用、仍在被执行的路径上;已被取代的,必须把断言挪到取代它的现行为上。
  - **条件跳过静默绿**:环境不满足而不能运行的测试,必须用测试框架的显式跳过(如 `test.skip`)标出,不得在测试体里提前 `return`——提前返回的测试在报告里记为通过。
  - **断言可能不执行**:异步调用的结果必须 await 后再断言;断言不得只写在可能不被调用的回调里;循环里逐项断言的,必须先断言集合非空——零次迭代即零次断言,测试照样记为通过。
- **横切**:先写完所有测试再写实现。批量测试验证的是**想象**的行为,并在理解实现前就锁死测试结构。改用纵切:一测→一实现→重复,每个测试都是回应上个循环所学的 tracer bullet。

## 循环规则

- **动手前列出计划的用例**:一次改动写或改第一个测试之前,必须在回复里列出计划的用例,一个用例一行,写明:它证明的验收条件或边界条目(没有 spec 的,写它证明的那条成功标准)、把执行带到那里的输入、期望值从哪里来。这份清单不得写进文件,用例变了也不回头更新它。
- **哪些测试必须先红**:先红指测试在它覆盖的代码写成或改动之前就跑出失败。复现 bug 的测试——修 bug 时写的、在未修的代码上重现该 bug 的那个测试——一律必须先对着未修的代码红一次再修;其余测试(新功能、行为变更、修 bug 时顺带补的边界测试等)不要求先红。
- **红要红得对**(凡上一条要求先红的测试,这是先红的完成判据,不是额外建议):红是三重验证——①代码确实没有该行为 ②测试确实能失败 ③失败原因确实是预期的那个断言(不是 setup 崩溃/typo/import 错)。**「测试跑出红色」不等于先红已完成**,未过判据的红不算数。**预期红却绿了 = 重要发现**:要么行为已存在(你理解错了现状,别写重复实现),要么测试是坏的(断言过弱/没 await/测错对象)。读失败信息,不要只看见红色就满足。
- **测穿构建产物的用例,跑之前先确认产物是本次改动的**:端到端、烟测这类读构建输出的检验,若运行器不触发构建,量到的是上一次的产物——此时"红"与"绿"都与本次改动无关。
- **一次一纵切**:一个 seam、一个测试、一个最小实现;不预写未来的测试,不加投机功能。判据是每条测试都说得出它在回应上一循环学到的什么;说不出,就是在横切——代价见「反模式」节,不在此复述。
- **不得为了变绿而删改测试**。
